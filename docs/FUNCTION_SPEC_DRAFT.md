## 1. 서비스 소개

### ① 서비스명

**SafeHour** (2026-08-15 확정)

요강은 지정과제형 특성상 수식어·타깃을 넣으라고 권고하지만, `SafeHour` 는 조어 브랜드명이라
같은 과제를 고른 팀과 겹칠 위험이 낮다. 차별점은 **② 개요**가 담는다.

**확인할 것**: 접수 시스템(콘텐츠랩)에 이미 등록된 서비스명과 **철자·대소문자까지 일치**시킨다.
FAQ 상 서비스명은 1차 심사 전까지 기능설명서에 최종 변경사항을 반영해 수정할 수 있다.

### ② 서비스 유형

**웹(WEB)** — 접속 가능한 URL 제출. 앱스토어 등록 절차가 필요 없다.

- 서비스 URL: `https://safehour.vercel.app`
- 테스트 계정: **SNS 연동 로그인** (Google · Kakao)
  - 심사 환경에서 소셜 로그인이 막힐 경우를 대비해 **데모 진입 경로**를 함께 제공한다

### ③ 서비스 타깃

**1차 사용자**: 성형외과·피부과 시술 후 회복 중인 **외국인 환자**
**2차 사용자**: 동반 **보호자**(가족·통역·의료관광 코디네이터)
**공급 주체**: 시술 병원의 코디네이터·의료진 (회복 지침 발행)

체류 기간이 정해져 있고, 한국어 안내문을 읽지 못하며, 회복 중에도 시간을 쓰고 싶은 사람들이다.

### ④ 서비스 개요

SafeHour 는 시술 후 관광 추천 앱이 아니다.

> **병원이 발행한 회복 지침을 환자와 보호자가 함께 확인하고, 지침을 지킬 수 있을 때만
> 안전한 외출 선택지를 제공하는 회복 동행 서비스**다.

병원이 외출 허용 여부·보행 한도·복귀 시각 같은 **제한조건**과 사람이 읽는 **주의 안내**를
발행하면, SafeHour 는 한국관광공사 OpenAPI 로 주변 후보를 모아 그 조건을 통과하는 활동만
보여준다. 조건을 지킬 수 없으면 **추천하지 않는 것이 정상 결과**다.

현장에서 휴무·기상 악화·교통 지연·진료시간 변경·환자 호출·지침 만료가 생기면 알림만 띄우지
않고 **코스를 처음부터 다시 판정**한다.

### ⑤ 선택 지정과제

**1번** — 「여행 중 발생하는 실시간 변수(날씨 변화, 혼잡도 상승, 동선 꼬임 등) 대응의 어려움」

접수 화면의 과제번호와 반드시 대조한다. 과제번호 혼동은 요강상 불이익 사유다.

### ⑥ 지정과제 선택 이유

> **같은 문제를, 실패 비용이 가장 큰 집단에서 푼다.**
>
> 과제 1번의 해결과제는 「여행 중 발생하는 실시간 변수 대응의 어려움」이다. 이 문제는
> 모든 여행자에게 있지만, 실패했을 때의 결과가 같지 않다. 일반 자유여행객에게
> 날씨 변화·혼잡도 상승·동선 꼬임은 **일정이 어긋나는 문제**다. 그러나 시술 후 회복 중인
> 환자에게는 **병원 복귀 시각을 놓치는 안전 문제**가 된다.
>
> 그리고 이 집단에게 실시간 대응이 특히 어려운 이유가 하나 더 있다. **무엇이 자신에게
> 변수인지 판단할 근거가 없다.** 병원 안내문은 한국어이고, 병원은 밤에 닫으며, 일반 관광
> 앱은 "돌아올 수 있는가" 를 묻지 않는다. 비가 오는 것이 누구에게는 불편이고 누구에게는
> 금지인데, 그 구분을 스스로 해야 한다.
>
> SafeHour 는 그 판단 근거를 **병원이 발행하게** 하고, 변수가 생기면 알림을 띄우는 대신
> **코스를 처음부터 다시 판정**해 유지·축소·대체·취소 중 하나로 확정해 준다. 공사 OpenAPI 의
> 관광정보는 그 판정 안에서만 꺼내 쓴다. 관광 데이터의 가치를 **소비 촉진이 아니라
> 안전한 소비 가능 범위 확정**에 쓰는 접근이다.
>
> 참고로 5번(만성질환자 건강 제약)의 관점을 일부 결합했으나, **심사 기준은 1번**이다.
> 5번의 핵심인 맞춤형 식당 정보는 SafeHour 의 범위가 아니다 — 병원이 식음 제한을 걸면
> 식음 활동을 제외할 뿐 식당을 추천하지 않는다.

**과제가 든 변수 3가지를 모두 다루고, 회복기 고유 변수 3가지를 더한다.**

| 과제가 든 변수 | SafeHour 의 대응 | 데이터 |
| --- | --- | --- |
| 날씨 변화 | 기상 실황으로 실외 후보 제외 | 기상청 초단기실황 |
| 혼잡도 상승 | 교통 지연을 이동시간에 누적 반영 | `TRAFFIC_SURGE` |
| 동선 꼬임 | 휴무 장소 제거 + 다음 안전 후보 자동 승격 | TourAPI 후보 재판정 |
| *(회복기 고유)* 진료시간 변경 | 복귀 마감을 앞당기고 코스 축소·취소 | `APPOINTMENT` |
| *(회복기 고유)* 환자 호출 | 모든 추천 무효화 + 즉시 복귀 | `PATIENT_RECALL` |
| *(회복기 고유)* 지침 만료·철회 | 추천 무효화 + 즉시 복귀 자동 전환 | 연결 게이트 |

### ⑦ 지정과제 기반 서비스 기획 방향

**과제 1번을 "재판정" 으로 해석했다.** 공고문 참고 예시는 자유여행객 대상 **대화형 AI
가이드**지만, 대화형 답변은 최종 판단을 사용자에게 남긴다. 회복기 사용자에게는 그것이
부담이자 위험이다. 그래서 세 가지 원칙으로 기획했다.

**1. 판단은 병원이, 적용은 앱이.**
초기 설계는 환자가 병원 안내를 체크박스로 옮겨 적는 방식이었다. 그러나 한국어를 못 읽는
사용자가 "자외선 회피" 를 체크할지 스스로 판단하는 순간 안전 판정 전체가 무너진다.
그래서 병원이 **제한조건(코드값)** 을 발행하고 앱은 적용만 하도록 구조를 바꿨다.
앱이 보유하는 정보를 다음과 같이 나눴다.

| 채널 | 내용 | 판정에 쓰나 | 서버로 가나 |
| --- | --- | --- | --- |
| A · 제한조건 | 외출허용·보행한도·복귀마감·복약시각 등 코드값 | **쓴다** | 간다 (비식별, 계산 후 폐기) |
| B · 병원 안내문 | 병원이 쓴 주의 문장 | **쓰지 않는다** | **가지 않는다** (단말 표시 전용) |

시술명·약물명·진단명은 **애초에 받지 않는다.** 복약은 시각만 받는다 — 외출 창을 자르는 데
필요한 것은 시각이지 약 이름이 아니다.

**2. 추천하지 않는 것도 결과다.**
안전 서비스에서 "무언가는 추천해야 한다" 는 압력이 가장 위험하다. 조건을 통과한 후보가
없으면 미추천을 **오류가 아닌 정상 화면**으로 보여주고, 병원 연락·숙소 대기를 안내한다.

**3. 변화는 알림이 아니라 재판정이다.**
현장 변화가 생겼을 때 알림만 띄우고 기존 코스를 유지하면, 사용자는 이미 위험해진 계획을
그대로 실행한다. 변화가 오면 안전 게이트부터 다시 통과시키고 **유지·축소·대체·취소** 중
하나를 근거와 함께 보여준다.

| 한국관광공사 | 무장애 여행정보 (KorWithService2) | `locationBasedList2` `detailWithTour2` | 접근성 신호 → **보행부담 계산에 최대 20% 반영** |

### 함께 적을 문장 (감점 방지)

> 공공 API 응답을 로컬 DB 에 적재하지 않고 **매 판정마다 실시간 호출**한다. 응답 캐시(TTL 15분)와
> 변화 이벤트 재계산 0콜 구조는 **동일 조건의 중복 조회를 막아 공공 API 부하를 낮추기 위한
> 설계**이며, 오퍼레이션별 800회 경고·1,000회 자체 차단으로 호출량을 통제한다.
> 홈 화면은 판정 상태만 계산하므로 공공 API 호출이 0건이다.

> 무장애 여행정보는 배지 표시용이 아니라 보행부담 계산에 반영되고, 기상 실황은 실외 후보
> 제외의 판정 근거로 쓰인다. **두 데이터 모두 화면 장식이 아니라 판정 입력이다.**

### 출처 표기

화면 상시 노출: `관광정보 출처: ⓒ한국관광공사` · `기상정보 출처: ⓒ기상청`
사진 캡션에 저작권 구분(제1유형/제3유형) 표시. 이미지는 다운로드하지 않고 **원본 URL 참조만** 한다.

## 6. 서비스 차별성 & 발전계획

### ① 서비스 차별성

**1. 변화에 알림이 아니라 재판정으로 답한다. (과제 1번 정면)**
변수가 들어오면 안전 게이트부터 다시 통과시켜 **유지·축소·대체·취소** 중 하나로 확정한다.
알림만 띄우고 기존 코스를 유지하는 동작은 코드 수준에서 금지돼 있다. 재판정에 공공 API 를
다시 부르지 않으므로 이벤트를 여러 번 주입해도 호출량이 늘지 않고, 외출 중 지침이
만료되면 추천을 비우고 **즉시 복귀로 자동 전환**한다.

**2. 조건의 출처가 병원이라는 것을 구조로 보장한다.**
"의료 판단을 하지 않는다" 는 문구가 아니라 설계다. 시술명·약물명·진단명을 받지 않고,
병원이 쓴 안내문은 **서버로 전송하지 않으며**, 판정에 쓰는 것은 병원이 발행한 코드값뿐이다.
판단 주체·시각·계획 버전이 발행 기록으로 남는다. **무엇이 자신에게 변수인지 판단할 근거**를
여기서 얻는다.

**3. 추천하지 않는 것을 제품의 정상 출력으로 만들었다.**
지침이 없거나·만료·철회면 관광지를 아예 표시하지 않는다. 미확인 중요 안내는 차단이 아니라
**대기로 강등**해 사용자가 읽으면 풀리게 했다 — 확인이 형식적 클릭이 되지 않도록.
실시간 대응의 결과가 언제나 대안 제시일 필요는 없다.

**4. 공공 데이터를 판정 입력으로 쓴다.**
무장애 여행정보는 보행부담 계산에, 기상 실황은 실외 후보 제외에 직접 반영된다.
확인되지 않은 값은 사실로 표시하지 않는다 — 이동시간에는 "추정" 배지가 붙고, 운영시간
원문으로 "지금 영업 중"을 단정하지 않는다. 다만 **닫혔다는 근거가 명백한 경우**
(끝난 행사, 오늘과 맞는 정기 휴무 요일)에는 후보에서 제외한다 — 회복기 환자를
헛걸음시키지 않기 위해서이며, 근거가 불확실하면 제외하지 않는다.

**5. 대상 사용자가 실제로 읽을 수 있다.**
영어권 브라우저는 조작 없이 영어로 열린다. 안전 판정 문구는 **두 언어를 함께** 보여준다 —
언어를 못 바꾼 사용자와, 환자·보호자의 언어가 다른 경우를 위해서다.

**6. 광고·순위·평점·제휴 추천이 없다.**
병원을 고르게 하지 않고, 관광지에 순위를 매기지 않는다. 수수료 기반 추천이 없다.

### ② 서비스 발전계획

**1단계 — 병원 파일럿 (연동 실증)**
지금은 가상 병원 연동 어댑터로 동작한다. 게이트웨이는 어댑터 패턴이라 병원 인터페이스를
갈아 끼울 수 있다. 첫 파일럿은 **병원 전용 어댑터(웹 발행 폼)** 로 시작한다 — 타깃이
의원급 성형외과·피부과라 대형 EMR 을 전제할 수 없기 때문이다.

**2단계 — 표준 연동 (FHIR)**
HL7 FHIR 의 `CarePlan`(관리 계획)·`Consent`(공유 동의)·`Provenance`(발행 이력)·
`AuditEvent`(접근 감사)로 매핑하고, SMART App Launch 로 접근 범위를 제한한다.
적용 버전과 프로파일은 연동 병원의 HIS 지원 범위를 확인한 뒤 결정한다.

**3단계 — 보호자 앱**
보호자용 축약 payload 는 이미 게이트웨이가 발행한다(병원 안내문 제외, 6개 필드만).
남은 것은 환자 동의 범위 설정 화면과 보호자 기기 연결이다.

**4단계 — 이동 정확도**
지도·경로 API 는 위치정보 사전검토가 끝나기 전까지 연결하지 않는다. 검토 완료 후 연동하면
"추정" 이 실제 경로 시간으로 바뀌고 복귀 SLA 정확도가 올라간다.

**5단계 — 확장**
병원별 어댑터, 병원 원문 다국어 발행, 실시간 계획 변경 알림, 운영 대시보드.
