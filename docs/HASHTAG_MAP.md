> 기능설명서에 작성해야 한다. 태그만 나열하면 배점을 받지 못한다.

## 1. 해시태그 목록 (기능설명서 1-⑧)

| # | 해시태그 | 한 줄 정의 | 과제 1번과의 연결 |
| --- | --- | --- | --- |
| H1 | `#실시간_변화대응` | 날씨·혼잡·동선 변수가 생기면 알림이 아니라 **코스를 다시 판정**한다 | **과제 정면.** 과제가 든 3가지 변수(날씨 변화·혼잡도 상승·동선 꼬임)를 모두 다루고, 회복기 고유 변수 3가지를 더한다 |
| H2 | `#병원지침_연동` | **무엇이 변수인지 판단할 근거**를 병원이 발행한다 | 회복기 환자에게 실시간 대응이 어려운 근본 이유는 "지금 내 몸에서 무엇이 문제인지" 를 판단할 근거가 없어서다 |
| H3 | `#복귀시간_보장` | 복귀·복약·진료 중 **가장 이른 마감**을 역산해 외출 창을 정한다 | 변수가 생겼을 때 **지켜야 할 기준선**. 이것이 없으면 "대응" 의 성공 여부를 판정할 수 없다 |
| H4 | `#안전한_미추천` | 대응 결과가 **"가지 마세요"** 일 수 있다 | 실시간 대응이 언제나 대안 제시로 끝나야 한다는 전제를 깬다 |
| H5 | `#무장애_접근성` | 무장애 여행정보를 **보행부담 계산에 반영**한다 | 같은 변수라도 이동 부담이 큰 사용자에게는 영향이 다르다 |
| H6 | `#환자_보호자_분리` | 역할별로 다른 코스를 판정하고 **정보 공개 범위도 분리**한다 | 변수 발생 시 환자와 보호자가 해야 할 행동이 다르다 |

### 과제 1번을 어떻게 다르게 풀었나

공고문 참고 예시는 **자유여행객 대상 대화형 AI 가이드**(`#실시간` `#여행 가이드`
`#연관 관광지 추천` `#카드뉴스형 답변`)다. SafeHour 는 같은 문제를 두 가지 축에서 다르게 푼다.

**1. 실패 비용이 가장 큰 집단에서 푼다.**
실시간 변수 대응에 실패했을 때 일반 자유여행객은 일정이 어긋나지만, **시술 후 회복 중인
환자는 복귀 시각을 놓치는 안전 문제**가 된다. 같은 과제의 가장 날카로운 지점이다.

**2. 대화로 답하지 않고 재판정한다.**
대화형 답변은 최종 판단을 사용자에게 남긴다. 회복기 사용자에게는 그것이 부담이자 위험이다.
SafeHour 는 변수가 들어오면 안전 게이트부터 다시 통과시켜 **유지·축소·대체·취소 중 하나로
확정**해 준다. 알림만 띄우고 기존 코스를 유지하는 동작은 금지돼 있다 (D07-BAN008).

| 과제가 든 변수 | SafeHour 의 대응 | 데이터 |
| --- | --- | --- |
| 날씨 변화 | 기상 실황으로 실외 후보 제외 | 기상청 초단기실황 |
| 혼잡도 상승 | 교통 지연을 이동시간에 누적 반영 | `TRAFFIC_SURGE` (누적 총량) |
| 동선 꼬임 | 휴무 장소 제거 + **다음 안전 후보 자동 승격** | TourAPI 후보 재판정 |
| *(회복기 고유)* 진료시간 변경 | 복귀 마감을 앞당기고 코스 축소·취소 | `APPOINTMENT` |
| *(회복기 고유)* 환자 호출 | 모든 추천 무효화 + 즉시 복귀 | `PATIENT_RECALL` |
| *(회복기 고유)* 지침 만료·철회 | 추천 무효화 + 즉시 복귀 자동 전환 | 연결 게이트 |

FAQ 는 *"선택하신 지정과제의 해결과제 해소에 필요하다면 여러 과제의 요소를 결합하여
개발하는 것은 가능"* 하다고 밝힌다. 5번(만성질환자 건강 제약)의 관점을 결합했으나
**심사 기준은 1번**임을 기능설명서에 명시한다.

## 2. 태그별 연계 기능 (기능설명서 1-⑨ · 2-①)

### H1 `#실시간_변화대응`

| 항목 | 내용 |
| --- | --- |
| 연계 기능 | 6종 변화 재판정 — 유지 / 축소 / 대체 / 취소·복귀 |
| 화면 | `/result` 변화 전후 비교 시트 + 결과 화면에 **변화 요약 잔존** |
| 내부 API | `POST /api/recalculate` — **공공 API 추가 호출 0건** |
| 이벤트 | `CLOSURE` `WEATHER` `TRAFFIC_SURGE` `APPOINTMENT` `PATIENT_RECALL` + **지침 만료·철회** |
| 구현 요지 | 수치 이벤트는 **누적 총량**으로 판정한다. 외출 중 지침이 만료·철회되면 추천을 비우고 **즉시 복귀로 자동 전환**하며, 그 뒤에는 변화 시연으로 추천을 되살릴 수 없다 |
| 차별점 | 알림이 아니라 **재판정**이다. 재계산에 공공 API 호출이 늘지 않아 시연에서 이벤트를 여러 번 줘도 호출량이 그대로다 |
| 증거 | `test/api-contract.test.js`, `e2e/core-flow.spec.js`, `lib/usePlanExpiry.js` |

### H2 `#병원지침_연동`

| 항목 | 내용 |
| --- | --- |
| 연계 기능 | 병원 발행 지침 연결 → 제한조건 자동 적용 → 읽기 전용 안내 열람 |
| 화면 | `/link` 병원 연결 · `/guide` 병원 회복 안내 · `/plan` 계획 확인 |
| 내부 API | `POST /api/plan/link` (게이트웨이), `POST /api/today` |
| 구현 요지 | 병원이 **제한조건(코드값)** 과 **안내문(원문)** 을 발행하고, 앱은 조건을 적용하고 안내문은 그대로 보여준다. 사용자는 조건을 타이핑하지 않고 **고칠 수도 없다** |
| 경계 | 게이트웨이가 허용목록 밖(진단명·시술기록·전체 약물목록)을 잘라낸다. 안내문은 **서버로 전송되지 않는다** |
| 차별점 | "앱이 의료 판단을 하지 않는다" 를 **구조로** 보장한다 — 판단 주체·시각·버전이 발행 기록으로 남는다 |
| 증거 | `src/recovery/plan.js`, `src/recovery/gateway.js`, 단위 48건 |

### H3 `#복귀시간_보장`

| 항목 | 내용 |
| --- | --- |
| 연계 기능 | 가장 이른 마감 산출 → 복귀 SLA 역산 → 출발 마감 표시 |
| 화면 | `/today` 오늘 외출 · `/result` 복귀 정보 · 즉시 복귀 시트 |
| 내부 API | `POST /api/recommend`, `POST /api/recalculate` |
| 구현 요지 | 복귀 시각뿐 아니라 **복약 시각·다음 진료**가 외출 창을 자른다. 셋 중 가장 이른 것을 마감으로 쓰고 **무엇이 마감을 정했는지 화면에 적는다** |
| 경계 | 지도·경로 API 미연동. 보수적 직선거리 추정(도심 우회계수 1.4, 회복기 보행속도)이며 "추정" 배지를 반드시 표시 |
| 차별점 | 복약 시각을 마감으로 쓰되 **약물명은 받지 않는다** — 필요한 것은 시각뿐이다 |
| 증거 | `effectiveDeadline`, `src/engine/slaCalculator.js` |

### H4 `#안전한_미추천`

| 항목 | 내용 |
| --- | --- |
| 연계 기능 | 2단 게이트 — **연결 게이트** → 안전 게이트 |
| 화면 | `/today` 상태 배너 · `/result` 미추천 화면 · `/plan` 차단 화면 |
| 구현 요지 | 지침이 없거나·만료·철회면 관광지를 아예 표시하지 않는다. **확인하지 않은 중요 안내는 차단이 아니라 STANDBY 강등**이라 읽으면 풀린다. 위험신호는 해석 없이 입력 사실만으로 차단한다 |
| 사유 코드 | `NO_HOSPITAL_PLAN` `PLAN_EXPIRED` `PLAN_REVOKED` `PLAN_UNCONFIRMED_UPDATE` + 기존 20종 |
| 운영 | `SAFEHOUR_KILL_RECOMMENDATION=1` 로 코드 배포 없이 전면 미추천 전환 |
| 차별점 | 추천 0건이 오류 화면이 아니다. **미추천을 제품의 정상 출력으로 설계** |
| 증거 | `gateDecisionPayload`, `src/engine/safetyGate.js`, `e2e/recovery.spec.js` |

### H5 `#무장애_접근성`

| 항목 | 내용 |
| --- | --- |
| 연계 기능 | 무장애 여행정보 매칭 → 보행부담 보정 → 장소 상세 접근성 근거 |

| 차별점 | 접근성 데이터를 배지로만 쓰지 않고 **판정 수치에 반영**한다 |
| 증거 | `src/tour-api/candidate-service.js` |

### H6 `#환자_보호자_분리`

| 항목 | 내용 |
| --- | --- |
| 연계 기능 | 역할별 판정(4상태) + **보호자 정보 공개 범위 분리** |
| 화면 | `/result` 환자·보호자 코스 탭 · 상태 배너 |
| 상태 | `NO_TOURISM` / `STANDBY` / `SPLIT_NEARBY` / `TOGETHER` |
| 구현 요지 | 환자에게는 보수적 이동 버퍼를, 보호자에게는 호출 시 복귀 SLA 를 적용한다. **필수 동행이면 보호자 단독 관광을 제안하지 않는다.** 보호자용 payload 는 **게이트웨이가 따로 발행**해 병원 안내문을 통째로 뺀다 |
| 차별점 | 동반 보호자를 별도 사용자로 설계하고, 건강정보 공개 범위까지 분리한 관광 서비스 |
| 증거 | `src/domain/states.js`, `companionView()` |

## 4. 기능설명서 4번에 함께 적을 문장

데이터 활용 적절성(20점)에서 오해를 사기 쉬운 것을 **먼저 설명한다.**

> SafeHour 는 공공 API 응답을 로컬 DB 에 적재하지 않고 매 판정마다 실시간 호출한다.
> 응답 캐시(TTL 15분)와 변화 이벤트 재계산 0콜 구조는 **동일 조건의 중복 조회를 막아
> 공공 API 부하를 낮추기 위한 설계**이며, 오퍼레이션별 800회 경고·1,000회 자체 차단으로
> 호출량을 통제한다.

> 무장애 여행정보는 배지 표시용이 아니라 **보행부담 계산에 최대 20% 반영**되고,
> 기상 실황은 실외 후보 제외의 판정 근거로 쓰인다. 두 데이터 모두 화면 장식이 아니라
> **판정 입력**이다.

> 홈 화면(`/today`)은 판정 상태만 계산하므로 **공공 API 호출이 0건**이다. 하루에 여러 번
> 열어도 호출량이 늘지 않는다.
