# ADR-0002: 계측 범위와 동의 경계

- 상태: Proposed
- 날짜: 2026-08-11
- 작업 ID: AX-008
- 연결 문서: D02-EVT001–EVT007, D02-UNRESOLVED-001(release_blocker), D07-POL008, D09-KPI
- 결정자: 지정 필요 (플랫폼 PO · 개인정보 담당)

## 맥락

D02는 계측 이벤트 7종(EVT001–EVT007)을 정의했고 **PII 를 넣지 않는 규칙**까지 갖췄다.
그러나 D02-UNRESOLVED-001 "필수 운영 로그와 선택 분석 이벤트의 동의·보존 경계"가
`release_blocker` 로 남아 있어 구현에 착수할 수 없다.

이 결정이 없으면 KPI 를 측정할 수 없고, AX-201(대시보드)도 시작할 수 없다.

### 현재 사실

- **서버는 아무것도 저장하지 않는다.** 판정은 stateless 이고, 세션·조건·판정 결과가
  서버에 남지 않는다 (`docs/API_CONTRACT.md`).
- 지금 남는 기록은 두 가지뿐이다.
  - TourAPI **호출 로그**(`logs/tour-api/`) — 오퍼레이션·성공여부·소요시간·일일 카운트.
    인증키·query·개인정보 없음. **운영에 필요한 로그**다.
  - 예외 발생 시 `console.error` — Vercel 런타임 로그로 흘러간다.
- **사용자 행동 계측은 0건이다.** 화면 진입·이탈·CTA 클릭 어느 것도 기록하지 않는다.
- Vercel 서버리스는 인스턴스마다 파일시스템이 독립이라, 파일 기반 집계는 흩어진다
  (`docs/DEPLOYMENT.md` 1.3).

### D02 이벤트의 성격

EVT001–EVT007 의 필수 property 는 이미 비식별로 설계돼 있다.

- `session_id` — 임시 식별자, 사용자와 연결되지 않음
- `role_mode` `decision_state` `reason_codes` — 분류값
- `return_window_bucket` `elapsed_bucket` — 구간값
- `anchor_type` — **원좌표 대신** 기준점 유형만
- 명시적 금지: 현재 GPS, 병원 원문, 건강 상세, 이름·연락처, 인증키, 전체 URL

즉 설계상 개인정보를 담지 않는다. 다만 **행태정보 수집**에 해당하는지, 동의가
필요한지는 법적 판단이 필요하다 — 그것이 이 ADR 이 결정할 것이다.

## 선택지

### A. 계측하지 않는다 (현행 유지)

- **하는 일**: 없음. 운영 로그(TourAPI 호출)만 유지.
- 장점: 동의·보존 문제가 발생하지 않는다. stateless 원칙이 유지된다.
  개인정보 signoff 에서 확인할 항목이 줄어든다. 추가 비용 0.
- 단점: KPI-05(완료율) 등 **사용자 행동 지표를 측정할 수 없다.** 심사에서
  "지표를 어떻게 측정하나"를 물으면 "측정하지 않는다"고 답해야 한다.
  D02-EVT001–007 이 문서로만 남는다.

### B. 운영 로그만 정리한다 (분석 계측 없음)

- **하는 일**: 이미 남는 서버 로그를 판정 결과까지 확장한다.
  `decision_state`·`reason_codes`·`candidate_count`·`engine_version` 을
  **요청 처리 로그로** 남긴다 (Vercel 런타임 로그). 사용자 행동은 기록하지 않는다.
- 장점: 서비스 제공·장애 대응에 필요한 **운영 로그** 성격이라 분석 동의와 분리된다.
  판정 분포(미추천 비율 등)와 안전 게이트 발동 현황을 볼 수 있다 —
  **위험 추천 0건을 증명하는 데 직접 쓰인다** (D09 성공 기준).
  저장소를 새로 만들지 않고, stateless 원칙도 유지된다.
- 단점: 화면 퍼널·이탈률은 여전히 알 수 없다. Vercel 로그 보존기간에 종속되고
  인스턴스별로 흩어져 정밀 집계에 한계가 있다.

### C. D02 전체 계측을 구현한다

- **하는 일**: EVT001–EVT007 을 모두 구현하고 저장소(외부 분석 도구 또는 DB)를 붙인다.
  선택 분석 로그에 대한 동의 UI 를 추가한다.
- 장점: KPI 전부 측정 가능. 퍼널·재계산 변화율·API 성공률 대시보드가 가능하다.
- 단점: **동의 UI·처리방침 화면·보존 정책이 모두 선행돼야 한다**(AX-104 와 연동).
  저장소가 새로 생겨 stateless 설계가 바뀌고, 개인정보 signoff 범위가 크게 늘어난다.
  2026-09-18 동결까지 남은 일정에서 이 셋을 다 닫기 어렵다.

## 권고 (사람 승인 전)

**선택지 B** 를 권고한다.

판단 기준은 "심사에서 무엇을 증명해야 하는가"다. SafeHour 가 증명할 것은
사용자 참여도가 아니라 **안전 판정이 실제로 작동한다는 것**이다. D09 성공 기준의
첫 줄도 "위험 추천 0건, 확인된 복귀 SLA 위반 0건"이다.

- B 는 그 증명에 직접 쓰이는 데이터(판정 상태 분포, 게이트 발동 사유)를 남기면서
  동의·보존 문제를 만들지 않는다. 서비스 운영에 필요한 로그이기 때문이다.
- C 가 주는 추가 정보(퍼널·이탈률)는 **심사 통과에 직접 기여하지 않는다.**
  반면 동의 UI·처리방침·보존 정책이라는 세 개의 선행 조건을 만든다.
- A 는 안전 증명 데이터마저 포기한다. "위험 추천 0건"을 주장하려면 판정이 어떻게
  나왔는지 기록이 있어야 한다.

### B 를 채택할 경우 함께 정할 것

1. **로그에 남길 필드 확정** — 권고: `decision_state`, `reason_codes`,
   `candidate_count`, `excluded_count`, `engine_version`, 처리 소요시간.
   session_id 는 **남기지 않는다** (요청 간 연결이 불필요하고, 남기면 행태 추적이 된다).
2. **보존기간** — Vercel 런타임 로그 기본값을 따를 것인지, 별도 정책을 둘 것인지
   (AX-104 와 함께 결정).
3. **D02 문서 처리** — EVT001–EVT007 을 "2차 범위"로 이동하고 UNRESOLVED-001 을
   이 ADR 로 종결 표시.
4. **심사 답변 준비** — "행동 지표는 수집하지 않으며, 그 이유는 최소 수집 원칙과
   동의 부담 회피"라고 답할 수 있게 근거를 문서에 남긴다.

## 결정

_사람 승인 대기._ 승인 시 이 절에 선택과 이유를 적고 상태를 `Accepted` 로 바꾼다.
에이전트는 승인자를 대신하지 않는다.

## 영향

- **B 채택 시**: 구현은 API 라우트에 로그 한 줄씩 추가하는 수준(반나절). 동의 UI·
  처리방침·저장소가 불필요하다. AX-201(대시보드)은 "Vercel 로그 조회"로 축소된다.
- **C 채택 시**: 동의 UI + 처리방침 화면 + 저장소 + 이벤트 7종 구현이 필요하다.
  AX-104(보존 정책) 결정이 선행돼야 하고, signoff 2번 영역의 확인 항목이 늘어난다.
- **A 채택 시**: 추가 작업 없음. D09 성공 기준의 "위험 추천 0건" 증명 방법을
  다른 수단(수동 QA 기록)으로 대체해야 한다.
- 어느 선택이든 **현재 GPS·병원 원문·이름·연락처를 남기지 않는다는 규칙은 불변**이다.

## 검증과 재검토

- 증거: D02-EVT001–007 정의, `docs/API_CONTRACT.md`(stateless 계약),
  `docs/DEPLOYMENT.md` 1.3(서버리스 로그 한계).
- 재검토 조건:
  - 실사용자 트래픽이 생기면 B → C 를 재검토한다. 그때는 동의·보존이 어차피 필요하다.
  - 심사 요구사항에 사용자 행동 지표가 명시되면 즉시 재검토한다.
  - 2026-09-18 기능 동결 이후에는 변경하지 않는다.
