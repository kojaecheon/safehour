# ADR-0002: 계측 범위와 동의 경계

- 상태: **Accepted**
- 제안: 2026-08-11 · 승인: 2026-08-11
- 작업 ID: AX-008
- 연결 문서: D02-EVT001–EVT007, D02-UNRESOLVED-001(release_blocker), D07-POL008, D07 4절, D09-KPI
- 결정자: 운영자(플랫폼 PO 역할)

## 맥락

D02는 계측 이벤트 7종(EVT001–EVT007)을 정의했고 **PII 를 넣지 않는 규칙**까지 갖췄다.
그러나 D02-UNRESOLVED-001 "필수 운영 로그와 선택 분석 이벤트의 동의·보존 경계"가
`release_blocker` 로 남아 있어 구현에 착수할 수 없다.

이 결정이 없으면 KPI 를 측정할 수 없고, AX-201(대시보드)도 시작할 수 없다.

### 현재 사실

먼저 용어를 나눈다. 이하에서 **저장**은 나중에 다시 조회할 수 있는 형태로 상태를
보존하는 것이고, **운영 로그**는 되읽지 않는 쓰기 전용 기록이다. 이 구분이 없으면
"서버는 저장하지 않는다"와 "로그를 남긴다"가 모순처럼 보인다.

- **서버는 아무것도 저장하지 않는다.** 판정은 stateless 이고, 세션·조건·판정 결과를
  다시 조회할 수 있는 형태로 보존하지 않는다 (`docs/API_CONTRACT.md`).
- 지금 남는 기록은 두 가지뿐이다.
  - TourAPI **호출 로그**(`logs/tour-api/`) — 오퍼레이션·성공여부·소요시간·일일 카운트.
    **운영에 필요한 로그**다.
  - 예외 발생 시 `console.error` — 배포 플랫폼 런타임 로그로 흘러간다.

> **초안 정정.** 이 문서의 초안은 호출 로그에 "개인정보 없음"이라고 적었으나 사실이
> 아니었다. 위치기반 조회의 `mapX`/`mapY`(사용자가 선택한 기준점 좌표)가 호출 시각과
> 함께 그대로 기록되고 있었다. 저장소에는 올라가지 않고(`.gitignore`) 서버리스에서는
> `/tmp` 라 휘발되지만, POL008 이 요구한 "로그 redaction"이 빠진 자리였다.
> 이 ADR 구현과 함께 좌표를 `REDACTED` 로 가리도록 고쳤다 (`src/tour-api/client.js`).
- **사용자 행동 계측은 0건이다.** 화면 진입·이탈·CTA 클릭 어느 것도 기록하지 않는다.
- Vercel 서버리스는 인스턴스마다 파일시스템이 독립이라, 파일 기반 집계는 흩어진다
  (`docs/DEPLOYMENT.md` 1.3).

### D02 이벤트의 성격

EVT001–EVT007 의 필수 property 는 이미 비식별로 설계돼 있다.

- `session_id` — 임시 식별자, 사용자와 연결되지 않음
- `role_mode` `decision_state` `reason_codes` — 분류값
- `return_window_bucket` `elapsed_bucket` — 구간값
- `anchor_type` — **원좌표 대신** 기준점 유형만
- 명시적 금지: 현재 GPS, 병원 원문, 건강 상세, 이름·연락처, 인증키, 전체 URL

즉 설계상 개인정보를 담지 않는다. 다만 **행태정보 수집**에 해당하는지, 동의가
필요한지는 법적 판단이 필요하다 — 그것이 이 ADR 이 결정할 것이다.

## 선택지

### A. 계측하지 않는다 (현행 유지)

- **하는 일**: 없음. 운영 로그(TourAPI 호출)만 유지.
- 장점: 동의·보존 문제가 발생하지 않는다. stateless 원칙이 유지된다.
  개인정보 signoff 에서 확인할 항목이 줄어든다. 추가 비용 0.
- 단점: KPI-05(완료율) 등 **사용자 행동 지표를 측정할 수 없다.** 심사에서
  "지표를 어떻게 측정하나"를 물으면 "측정하지 않는다"고 답해야 한다.
  D02-EVT001–007 이 문서로만 남는다.

### B. 운영 로그만 정리한다 (분석 계측 없음)

- **하는 일**: 이미 남는 서버 로그를 판정 결과까지 확장한다.
  `decision_state`·`reason_codes`·`candidate_count`·`engine_version` 을
  **요청 처리 로그로** 남긴다 (Vercel 런타임 로그). 사용자 행동은 기록하지 않는다.
- 장점: 서비스 제공·장애 대응에 필요한 **운영 로그** 성격이라 분석 동의와 분리된다.
  판정 분포(미추천 비율 등)와 안전 게이트 발동 현황을 볼 수 있다 —
  **위험 추천 0건을 증명하는 데 직접 쓰인다** (D09 성공 기준).
  저장소를 새로 만들지 않고, stateless 원칙도 유지된다.
- 단점: 화면 퍼널·이탈률은 여전히 알 수 없다. Vercel 로그 보존기간에 종속되고
  인스턴스별로 흩어져 정밀 집계에 한계가 있다.

### C. D02 전체 계측을 구현한다

- **하는 일**: EVT001–EVT007 을 모두 구현하고 저장소(외부 분석 도구 또는 DB)를 붙인다.
  선택 분석 로그에 대한 동의 UI 를 추가한다.
- 장점: KPI 전부 측정 가능. 퍼널·재계산 변화율·API 성공률 대시보드가 가능하다.
- 단점: **동의 UI·처리방침 화면·보존 정책이 모두 선행돼야 한다**(AX-104 와 연동).
  저장소가 새로 생겨 stateless 설계가 바뀌고, 개인정보 signoff 범위가 크게 늘어난다.
  2026-09-18 동결까지 남은 일정에서 이 셋을 다 닫기 어렵다.

## 권고 (사람 승인 전)

**선택지 B** 를 권고한다.

판단 기준은 "심사에서 무엇을 증명해야 하는가"다. SafeHour 가 증명할 것은
사용자 참여도가 아니라 **안전 판정이 실제로 작동한다는 것**이다. D09 성공 기준의
첫 줄도 "위험 추천 0건, 확인된 복귀 SLA 위반 0건"이다.

- B 는 그 증명에 직접 쓰이는 데이터(판정 상태 분포, 게이트 발동 사유)를 남기면서
  동의·보존 문제를 만들지 않는다. 서비스 운영에 필요한 로그이기 때문이다.
- C 가 주는 추가 정보(퍼널·이탈률)는 **심사 통과에 직접 기여하지 않는다.**
  반면 동의 UI·처리방침·보존 정책이라는 세 개의 선행 조건을 만든다.
- A 는 안전 증명 데이터마저 포기한다. "위험 추천 0건"을 주장하려면 판정이 어떻게
  나왔는지 기록이 있어야 한다.

### B 를 채택할 경우 함께 정할 것

_아래 네 가지는 승인 시점에 함께 정리했다. 결과는 「결정」 절에 있다._

1. 로그에 남길 필드 확정
2. 보존기간 (AX-104 와 연동)
3. D02 문서 처리 — EVT001–EVT007 을 "2차 범위"로 이동, UNRESOLVED-001 종결 표시
4. 심사 답변 준비

## 결정

**선택지 B 를 채택한다.** 운영 로그에 판정 결과를 남기고, 사용자 행동 분석 계측은
구현하지 않는다.

승인 후 D07 을 다시 읽으며 확인한 것이 두 가지 있고, 둘 다 B 를 뒷받침한다.

1. **D07 4절 "정책 강제·감사"가 감사 증적으로 `engine decision log` 를 이미 요구한다.**
   B 는 새로운 데이터 종류를 만드는 것이 아니라, 정책이 이미 요구했으나 아직 만들지
   않은 증적을 만드는 것이다. 이 사실이 "운영 로그인가 분석 계측인가"라는 경계
   질문(D02-UNRESOLVED-001)에 답을 준다 — **정책이 감사 목적으로 요구한 로그이므로
   운영 로그다.**
2. **D07-POL001(의료 판단 경계)의 위반 탐지 수단이 "런타임 reason code 검사"다.**
   판정 사유를 남기지 않으면 이 정책은 강제 수단 없이 문서로만 존재한다. 즉 B 는
   있으면 좋은 것이 아니라, 이미 선언한 통제를 작동시키는 데 필요하다.

### 확정한 구현 범위

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 기록 위치 | **stdout 한 줄**(JSON). 파일·DB·외부 도구를 새로 만들지 않는다 | 저장소를 만들면 보존 정책(AX-104)이 선행 조건이 된다. stdout 은 플랫폼 로그로 흘러가 우리가 보존 주체가 되지 않는다 |
| `session_id` | **남기지 않는다** | POL008 최소 후보에는 익명 session ID 가 있으나, 요청 간 연결이 판정에 불필요하다. D07 1절 "충돌하면 더 보수적인 결정을 적용" |
| 조건 발행시각 | 원값 대신 **경과 구간**(`conditionAge`) | POL001 은 `issuedAt` 감사를 요구하지만, "조건이 오래됐는데 추천이 나왔는가"는 구간으로 확인된다. D02 의 bucket 원칙과 같은 방향이고 더 보수적이다 |
| reason code | **닫힌 enum 통과분만** 기록 | `src/domain/states.js` 의 `REASON` 에 없는 값은 버린다. 미래 변경으로 자유 문자열이 섞여도 로그로 새지 않는다 |
| 장소 이름·주소 | **남기지 않는다** | D02-EVT005 가 "장소 원문 전체"를 금지한다. 후보 식별자와 개수만으로 감사 목적이 충족된다 |
| 좌표·병원 원문·역할 조합 | **남기지 않는다** | POL008·BAN002 |

### 사유 코드는 "건강 상세"인가

이 결정의 가장 미묘한 지점이다. 위 표는 건강 상세를 남기지 않는다고 하면서
`FASTING_REQUIRED`·`OUTING_FORBIDDEN`·`RISK_SIGNAL`·`PATIENT_RECALLED` 같은 코드를
남긴다. 이 코드들은 환자 상태를 어느 정도 드러낸다.

그럼에도 남기는 이유는 세 가지다.

1. **POL001 이 이것을 위반 탐지 수단으로 지정했다.** "런타임 reason code 검사"가
   의료 판단 경계 정책의 강제 수단이다. 코드를 지우면 통제가 사라진다.
2. **가장 거친 표현이다.** 조건 값 자체(무엇을 얼마나 제한했는지)나 원문이 아니라,
   판정이 어느 규칙에서 멈췄는지를 가리키는 코드 하나다.
3. **요청 간에 이어붙일 수 없다.** session 식별자도, `condition.version`(클라이언트가
   제출마다 새로 만드는 값이라 사실상 세션 키다)도 남기지 않는다. 코드 하나가
   시각과 함께 남을 뿐 한 사람의 이력으로 묶이지 않는다.

**개인정보 담당자 확인이 필요한 항목이다.** 만약 이 판단이 받아들여지지 않으면
차단 사유를 단일 코드(예: `BLOCKED`)로 뭉개는 선택지가 있고, 그 경우 POL001 의
탐지 정밀도가 떨어진다는 대가를 함께 기록해야 한다.
(`docs/SIGNOFF_CHECKLIST.md` 2번 영역에서 확인)

### 남은 것 — 보존기간

D07-UNRESOLVED-002(데이터 보존기간, release_blocker)는 이 결정으로 닫히지 **않는다.**
다만 위험은 낮다. 이 로그에는 개인정보가 없고(위 표), 우리가 저장소를 운영하지 않으므로
보존 주체는 배포 플랫폼이다. AX-104 에서 "플랫폼 기본값을 따른다"를 확인만 하면 된다.

### 심사 답변

"사용자 행동 지표는 수집하지 않습니다. 최소 수집 원칙(D07-POL008)에 따라,
안전 판정이 올바르게 작동했는지 확인하는 데 필요한 판정 결과만 운영 로그로 남깁니다."

## 영향 (B 채택 결과)

- **stateless 계약은 유지된다.** 서버는 여전히 세션·조건·판정 결과를 저장하지 않는다.
  stdout 한 줄은 저장이 아니라 관측이고, 그것으로 요청을 복원할 수 없다
  (좌표·조건 원문·session 식별자가 없으므로).
- **동의 UI·처리방침 화면·저장소는 필요 없다.** 선택 분석 로그를 두지 않음으로써
  POL008 의 "필수 서비스 처리와 선택 분석 분리" 요구를 충족한다.
- **AX-201(대시보드)은 "플랫폼 로그 조회 절차"로 축소된다.** 별도 대시보드를 만들지 않는다.
- **D02-EVT001–EVT007 은 2차 범위로 이동한다.** 문서에서 삭제하지 않는다 — 실사용자
  트래픽이 생기면 그대로 쓸 수 있는 설계이기 때문이다.
- **D07-UNRESOLVED-002(보존기간)는 여전히 열려 있다.** AX-104 에서 닫는다.
- 어느 선택이든 **현재 GPS·병원 원문·이름·연락처를 남기지 않는다는 규칙은 불변**이다.

## 검증과 재검토

- 증거: D02-EVT001–007 정의, D07 4절(감사 증적 `engine decision log`),
  D07-POL001(위반 탐지 = 런타임 reason code 검사), D07-POL008(최소수집),
  `docs/API_CONTRACT.md`(stateless 계약), `docs/DEPLOYMENT.md`(서버리스 로그 한계).
- **구현이 이 결정을 지키는지 확인하는 방법**: `test/decision-log.test.js` 가
  개인정보를 잔뜩 담은 요청을 넣고 로그 출력에 그 값들이 하나도 나타나지 않음을
  단언한다. 필드를 늘릴 때 이 테스트가 먼저 막는다.
- 재검토 조건:
  - 실사용자 트래픽이 생기면 B → C 를 재검토한다. 그때는 동의·보존이 어차피 필요하다.
  - 심사 요구사항에 사용자 행동 지표가 명시되면 즉시 재검토한다.
  - 2026-09-18 기능 동결 이후에는 변경하지 않는다.
