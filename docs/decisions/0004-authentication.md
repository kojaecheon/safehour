# ADR-0004: 소셜 로그인 도입과 서버 상태 경계

- 상태: Accepted
- 날짜: 2026-08-14
- 작업 ID: AX-219
- 연결: `docs/PRODUCT_DEFINITION.md` §2·§8, D07-POL008, SIGNOFF_CHECKLIST 2절, ADR-0003
- 결정자: 구현 결정. **민감정보 동의 설계와 개인정보 책임자 지정은 여전히 사람 승인 사항**

## 맥락

병원이 발행한 회복 지침을 환자·보호자가 다시 불러오려면 **"같은 사람이 다시 왔는가"** 를
알아야 한다. 그런데 SafeHour 의 핵심 설계는 지금까지 이랬다.

> 서버는 아무것도 저장하지 않는다. 판정은 stateless 이고 세션·조건·결과가 서버에 남지 않는다.

로그인은 이 원칙과 정면으로 부딪친다. 계정은 곧 서버가 사용자를 기억한다는 뜻이다.

동시에 **로그인을 넣지 않으면 회복 지침 연동이 성립하지 않는다.** 병원이 발행한 계획을
누구에게 줄 것인지 결정할 수 없기 때문이다.

## 결정

**소셜 로그인(Google · Kakao)을 도입하되, 서버 데이터베이스를 만들지 않는다.**
사용자 신원은 **서명된 쿠키** 안에만 존재한다.

```
[일반적인 로그인]              [SafeHour]

브라우저 ──세션ID──▶ 서버 DB    브라우저 ──서명 쿠키(신원 포함)──▶ 서버
                     └ 사용자 테이블                              └ 검증만 하고 버린다
                     └ 세션 테이블                                   테이블 없음
```

### 세부 규칙

| # | 규칙 | 이유 |
| --- | --- | --- |
| 1 | **최소 범위만 요청한다.** Google 은 `openid` 만, Kakao 는 선택 동의 항목 0개 | 이메일·이름·프로필을 받지 않으면 `/privacy` 의 "받지 않습니다" 가 계속 사실로 남는다 |
| 2 | **식별자 하나만 보관한다** (`provider` + `sub`) | 회복 지침을 다시 불러오는 데 그 이상이 필요 없다 |
| 3 | **액세스·리프레시 토큰을 저장하지 않는다** | 교환 직후 식별자만 꺼내고 버린다. 유출될 토큰 자체가 없다 |
| 4 | **세션은 HMAC-SHA256 서명 쿠키** (httpOnly · SameSite=Lax · 운영 Secure · 12시간) | 서버 세션 테이블을 만들지 않기 위해 |
| 5 | **PKCE(S256) + state** 를 두 공급자 모두에 적용 | 인가 코드 가로채기와 CSRF 방어 |
| 6 | **redirect_uri 는 `SAFEHOUR_BASE_URL` 로 조립한다** | 요청 헤더로 만들면 호스트 헤더 주입에 열린다 |
| 7 | **returnTo 는 같은 출처의 절대 경로만** 허용 | 열린 리다이렉트 방어 |
| 8 | **로그아웃은 POST 전용** | GET 이면 `<img src>` 한 줄로 남을 로그아웃시킬 수 있다 |
| 9 | **"내 정보 지우기" 가 로그아웃까지 수행한다** | 세션 쿠키는 httpOnly 라 클라이언트가 못 지운다. 안 그러면 그 버튼이 거짓말이 된다 |
| 10 | 서명 키(`SAFEHOUR_SESSION_SECRET`)가 없으면 **로그인 기능 자체가 비활성** | 서명 없는 세션은 위조 가능하므로 켜지 않는 편이 안전하다 |

## 결과 — 무엇이 지켜지고 무엇이 바뀌나

### 지켜지는 것

- 서버에 **회원 테이블·세션 테이블이 없다.** stateless 원칙의 실질이 유지된다
- 이메일·이름·프로필 미수집. `/privacy` 의 "무엇을 받지 않나요" 가 계속 사실이다
- 판정 API 는 변함없이 stateless — 로그인 여부와 무관하게 계산하고 버린다

### 바뀌는 것

| 항목 | 변화 |
| --- | --- |
| `/privacy` | "회원가입·로그인·계정 없음" 문장을 **삭제**하고 "로그인은 무엇을 가져가나요" 절을 신설했다 |
| 쿠키 | `safehour.session`(12시간), `safehour.oauth`(10분, 인가 왕복 중에만) |
| 제3자 | Google·Kakao 인증 서버와 통신이 생긴다. 이것도 `/privacy` 에 적어야 한다 |
| 공모전 제출 | 테스트 계정 항목이 **"로그인 불필요" → "SNS 연동 로그인"** 으로 바뀐다 (§리스크) |

## 로그인은 본인 확인이 아니다

이것이 가장 오해하기 쉬운 지점이라 화면과 고지에 모두 명시했다.

> 소셜 로그인이 보장하는 것은 **"같은 계정이 다시 왔다"** 뿐이다.
> **"이 사람이 그 환자다"** 는 병원이 발급한 코드가 확인한다.

`docs/PRODUCT_DEFINITION.md` §9-1 에서 지적한 대로, 한국 본인인증(PASS·휴대폰)은 외국인
환자에게 작동하지 않는다. 인증 주체는 **병원**이고 SafeHour 는 검증만 한다.

## 카카오에 대한 현실 인식

카카오는 한국 서비스다. **대상 사용자(외국인 환자)의 상당수는 카카오 계정이 없다.**

- **Google 이 환자의 주 경로**다
- **Kakao 는 보호자 경로**다 — 동반 가족·통역·의료관광 코디네이터는 한국인일 가능성이 높다
- 둘 다 두는 것은 맞지만, 화면 순서에서 Google 을 위에 둔다

## 남은 위험

| # | 위험 | 대응 |
| --- | --- | --- |
| 1 | **심사위원이 로그인을 통과 못 하면 서비스를 볼 수 없다** — 구현성 30점이 걸린다 | `SAFEHOUR_ALLOW_DEMO_LOGIN=1` 로 데모 경로를 연다. 명시적으로 켤 때만 동작 |
| 2 | 공모전 제출 항목 3-② 가 "SNS 연동 로그인" 으로 바뀐다 | `docs/COMPETITION_SUBMISSION.md` 반영 필요. SNS 연동만으로 이용 가능하면 테스트 계정 생성은 불필요 |
| 3 | 서명 키 유출 시 세션 위조 가능 | 키를 환경변수로만 두고 로테이션 절차를 배포 문서에 남긴다 |
| 4 | 쿠키에 신원이 담기므로 **쿠키 크기·수명이 곧 보안 경계** | 12시간 만료. 담는 필드를 5개로 제한하고 테스트로 고정했다 |
| 5 | 민감정보 별도 동의는 **아직 없다** | 회복 지침(채널 B)을 붙일 때 반드시 필요. AX-213 과 함께 처리 |

## 대안과 기각 사유

| 대안 | 기각 이유 |
| --- | --- |
| NextAuth/Auth.js 도입 | 세션 저장소·어댑터를 전제한다. 의존성 하나로 "서버 무저장" 이 조용히 깨진다 |
| 이메일 매직링크 | 이메일 주소를 받아야 한다. 최소수집 원칙에서 후퇴 |
| 병원 발급 코드만으로 로그인 없이 운영 | 코드가 유출되면 누구나 그 계획을 본다. 계정에 묶어야 재사용을 통제할 수 있다 |
| 서버 세션 테이블 | 회원 DB 가 생기고 `/privacy` 전체를 다시 써야 한다. 얻는 것은 없다 |

## 검증

`test/auth.test.js` 32건 — 서명 위조·만료·키 불일치·형식 파손 거부, state 타이밍 안전 비교,
열린 리다이렉트 6종 차단, 최소 scope 고정, **토큰 교환 결과에 이메일·토큰이 새지 않음**,
쿠키 속성(HttpOnly·SameSite·Secure·Max-Age=0).
