# ADR-0006: 체류 일정 엔진 — 전체 확정, 변화 대응, 편집, 단일 외출 흐름 퇴역

- 상태: Accepted
- 날짜: 2026-09-18
- 작업 ID: AX-301
- 연결 문서: `docs/platform/ITINERARY_RULES.md` 7–10장, `docs/platform/IA_AND_FLOWS.md` 1.3절·2.3–2.4절·4–6장,
  `docs/PRODUCT_DEFINITION.md`(v2) 9-5절, ADR-0001(라우트 계약), ADR-0002(운영 로그), ADR-0005
- 결정자: 운영자 (대화 결정)

## 맥락

v2의 추천은 회복 대기 중 **단일 외출 하나**를 판정한다(`/plan` → `/result`, `POST /api/recommend`·`/api/recalculate`·`/api/today`).
대중형 제품은 입국부터 출국까지 체류 전체를 다뤄야 한다.

지켜야 할 것도 분명하다.

- 판정 경로가 두 벌이 되면 결과가 어긋난다. v2 9-5절이 이것을 이 제품에서 가장 위험한 결함으로 꼽았다.
- 기존 원칙: 변화가 생기면 게이트부터 다시 판정하고, 필요한 변화가 화면에 반영되지 않으면 실패다(알림만 하는 재계산 금지).
- 서버는 상태를 저장하지 않는다. 일정은 기기에 둔다(ADR-0009).
- 체류는 최대 45박이다. 날짜마다 숙소, 병원 일정, 조건이 다르다.

## 선택지

1. **장소 목록 + 짧은 코스** — 조건을 통과한 장소를 목록으로 보여주고, 짧은 코스를 곁들인다.
2. **전체 초안 + 당일 재판정** — 미리 초안을 보여주고, 그날 다시 판정해 확정한다.
3. **하루 일정 자동 생성 + 전체 확정(채택)** — 체류 설정 후 날짜별 하루 일정을 한 번에 만들어 확정하고,
   변화가 감지될 때만 영향받은 날짜를 다시 짠다.

## 결정

**선택지 3을 채택한다.** 운영자가 추천안(1, 2) 대신 골랐다.

### 전체 일정을 한 번에 확정한다

- 체류 설정을 마치면 전체 일정을 한 번 만들어 **확정 일정**으로 기기에 저장한다.
  조건 입력 전이면 경계일 이후 날짜는 입력 필요로 두고 나머지만 만든다.
- 변화가 감지되지 않으면 당일에도 확정 일정을 그대로 쓴다.
- 엔진은 **결정적 함수**다. 같은 입력이면 같은 결과가 나오고, 언어가 달라도 정거장과 상태가 같다.
  기존 안전 게이트와 복귀 계산을 재사용·확장하며, 판정 경로를 새로 복제하지 않는다.
- AI는 일정 배치에 관여하지 않는다(ADR-0008).

### 변화가 생기면 자동으로 대체하고 전후 비교를 남긴다

- 변화 원천(입력 수정, 조건 수정·동의 철회, 매일 확인 '바뀌었어요', 기상, 연동 지침 갱신, 데모 사건)을
  앱을 열 때, 화면으로 돌아올 때, 사용자가 조작할 때 감지한다.
- 영향받은 날짜만 **게이트 1단계부터** 다시 판정한다.
  - 지난 날짜와 이미 시작된 정거장은 건드리지 않는다.
  - 고정 장소는 여전히 통과하면 유지하고, 삭제한 장소는 다시 넣지 않는다.
  - 통과하지 못한 정거장은 **자동 대체 → 체류 축소 → 정거장 삭제 → 외출 취소** 순으로 처리한다.
- 날짜별 전후 비교(빠진 곳, 들어온 곳, 대체된 곳, 줄어든 곳, 취소된 외출, 상태 변경, 새 마감, 사유)를 기록하고,
  사용자가 볼 때까지 '변경됨'을 표시한다. **변화가 필요한데 전후 비교가 비어 있으면 실패다.**
- 언어 변경은 재판정하지 않고 표시만 다시 쓴다(ADR-0007).

### 오늘 게이트는 저장 일정에 넣지 않고 덧씌운다

- 매일 확인 대기(`DAILY_CHECK_PENDING`)와 확인하지 않은 병원 중요 안내(`PLAN_UNCONFIRMED_UPDATE`)는
  저장된 확정 일정을 바꾸지 않는다. 오늘 일정을 보여줄 때 같은 순수 함수로 `STANDBY`와 사유를 덧씌우고 이동 동작을 막는다.
- '확정 일정을 그대로 쓴다'와 '확인 전에는 외출 동작을 막는다'를 함께 지키기 위한 구조다.

### 즉시 복귀와 데모 사건

- 환자 호출(데모 사건), 외출 중 지침 철회·만료가 일어나면 오늘 남은 일정을 비우고 즉시 복귀 시트를 자동으로 띄운다.
  끌 수 없고, 뒤로가기는 시트만 닫는다(기존 AX-220, AX-011).
- 기존 `/api/recalculate` 사건 계약을 하루 단위 데모 사건 6종으로 옮기고, 오늘에만 적용한다
  (`ITINERARY_RULES.md` 9.3절).

### 사용자 편집

- 교체: 같은 시간 자리의 게이트 통과 후보를 최대 5개 보여주고, 고르면 외출 전체를 다시 검증한다. 교체한 장소는 '고정'이다.
- 삭제: 외출 시각을 다시 계산한다. 식사 칸 식당을 지우면 그 칸은 '비움'으로 두고 다시 채우지 않는다.
- 다시 만들기: '이 날짜' 또는 '오늘 이후 전체'. 확인 대화 후 고정·삭제 기록을 지우고 새로 만든다.
- 지난 날짜와 매일 확인 전의 오늘은 편집할 수 없다.

### 엔진이 조건을 적용하는 방식

| 결정 | 내용 |
| --- | --- |
| 보행 한도는 외출 1회 누적 | 정거장 보행 부담 추정과 도보 이동을 외출 단위로 더해 한도와 비교한다 |
| 복약 마감은 '숙소에서 복용'일 때만 | 시각마다 '숙소에서 복용'(기본 예)을 고르고, 예일 때만 숙소 복귀 마감이 된다 |
| 식이 필터는 항목별 기준 | 술: 주점 유형 제외. 매운 음식·날음식: 단서가 없으면 제외(`MENU_UNKNOWN`). 뜨거운 음식·딱딱한 음식: 제외하지 않고 한국어 주문 카드 연결 |
| 열 노출·수중 활동을 판정에 적용 | 단서가 있는 장소를 제외한다(`HEAT_EXPOSURE`, `WATER_ACTIVITY`). v2에서는 표시만 했다 |
| 이동수단은 제한일 택시, 자유일 대중교통 | 모든 이동 시간은 '추정'으로 표시한다 |
| 장소 데이터는 관광공사 TourAPI만 | 평점·리뷰·인기·광고·제휴 점수가 없다. 순위는 관심사 → 복귀 여유 → 보행 부담 → 유형 다양성 |
| 식사 칸이 비는 것은 정상 결과 | 통과한 식당이 없으면 '추천 장소 없음'과 사유를 보여주고 다른 정거장으로 채우지 않는다 |

### 단일 외출 흐름을 퇴역한다

- 화면 `/plan`·`/result`는 `/today`로 보낸다.
- `POST /api/recommend`, `POST /api/recalculate`, `POST /api/today`를 없애고
  `POST /api/itinerary/plan`, `POST /api/itinerary/alternatives`로 바꾼다.

## 대안과 버린 이유

| 대안 | 버린 이유 |
| --- | --- |
| 장소 목록 + 짧은 코스(추천안) | 운영자가 하루 일정 자동 생성을 골랐다 |
| 전체 초안 + 당일 재판정(추천안) | 운영자가 전체 확정을 골랐다. 변화가 없으면 확정 일정을 그대로 쓰고, 변화가 감지되면 자동 대체와 전후 비교로 대응한다 |
| 단일 외출 흐름을 새 일정과 함께 유지 | 판정 경로가 두 벌이 되면 결과가 어긋난다. 이 제품에서 가장 위험한 결함이다 |
| 변화를 알림으로만 알리고 사용자가 다시 짜게 함 | 기존 '알림만 하는 재계산 금지' 원칙에 어긋난다 |
| 매일 확인·중요 안내 대기를 저장 일정에 직접 반영 | '확정 일정을 그대로 쓴다'는 결정과 부딪친다. 오늘 화면에 덧씌우는 방식으로 두 결정을 함께 지킨다 |
| 보행 한도를 장소 하나마다 적용(기존) | 여러 곳을 묶으면 한 번 외출의 총 보행이 한도를 넘어도 막지 못한다 |
| 복약 시각을 항상 복귀 마감으로 둠(기존) | 하루 3회 복약이면 일정이 잘게 끊긴다 |
| 식이 5항목을 모두 '단서가 없으면 제외' | 관광공사 데이터에는 메뉴 정보가 드물어 수술 후 식사 칸이 거의 빈다 |
| 제한일에도 대중교통으로 추정 | 지하철 계단·환승 보행을 정확히 잴 수 없다. 회복기에는 택시로 가정한다 |
| 관광공사 + 구글 장소 정보(추천안) | 운영자가 관광공사 데이터만 쓰기로 골랐다. 평점·리뷰는 두지 않는다 |

## 영향

- **엔진**: 하루 일정 함수와 체류 전체 조립·재계획·교체 후보·다시 만들기가 생긴다. 기존 `test/scenarios.test.js`는 계속 통과해야 하며,
  바뀐 결정(보행 한도 단위 등) 때문에 기존 단언을 고치면 이유를 남긴다.
  (후속, 2026-11-03: 단일 외출 판정 모듈과 `test/scenarios.test.js`를 지웠다. 시나리오가 지키던 규칙은 일정 엔진
  테스트가 이어받았고, 이어받지 않은 규칙과 그 근거는 `docs/tracking/findings.md`의 4번에 있다.)
- **API**: 단일 외출 API 3개가 퇴역하고 일정 API로 바뀐다. 해당 계약 테스트도 일정 API 계약 테스트로 바꾼다.
  서버는 여전히 무상태 계산기다.
- **ADR-0001**: 라우트 계약 중 `/plan`·`/result`가 퇴역한다. 다시 만들 수 없는 화면(전후 비교, 즉시 복귀)을
  모달 시트로 두고 뒤로가기가 시트만 닫는다는 원칙은 새 화면에서도 그대로 유지한다.
- **ADR-0002**: 판정 운영 로그를 넓힌다. 일정 생성·재계획 한 번마다 한 줄을 남기며, 엔진 버전, 요청 날짜 수,
  상태별 날짜 수, 사유 코드 집합, 출처 종류별 개수, 언어만 담는다. 좌표, 날짜, 장소 이름, 주소, 조건 값,
  계정 키, 병원 정보는 남기지 않는다.
- **운영 안전장치**: 추천 중단 스위치(`SAFEHOUR_KILL_RECOMMENDATION=1`)는 일정 생성·재계획·교체 후보 조회에서
  모든 날짜를 정거장 없이 `NO_TOURISM` + `SERVICE_PAUSED`로 돌려준다. 긴급 연락·카드·조건 화면은 계속 동작한다.
- **E2E**: 퇴역 화면을 전제한 기존 E2E는 새 흐름에 맞춰 다시 쓴다.
- **rollback**: 퇴역한 단일 외출 코드는 더 이상 참조되지 않으면 삭제된다. 되돌릴 기준은 병합 전 main(공모전 제출본)이다.

## 검증과 재검토

- 증거: 결정성(같은 입력 두 번), 언어 무관성, 마감 이유, 보행 누적·이동 한도, 식사 칸, 식이·열·물 필터,
  재계획(고정·삭제·지난 날짜·전후 비교), 데모 사건 6종, 교체 후보 최대 5개와 재검증을 단위 테스트로 고정한다.
  45박 입력의 처리 시간을 측정해 기록한다.
- 재검토 조건
  - 의료진이 버퍼·보행·식이 기준을 확정하면 값을 반영한다(`HUMAN_ACTIONS.md` 4번).
  - 위치정보 검토가 끝나 경로 API가 들어오면 이동 추정 방식을 다시 본다.
