## 시간대 없는 시각 문자열이 실행 환경 시간대로 해석된다

- **증상**: 시간대가 한국이 아닌 환경(`TZ=America/New_York` 등)에서 일정 테스트가 무더기로 깨진다.
  같은 코드가 개발 기기에서는 통과한다.
- **원인**: `2026-09-21T09:00` 처럼 오프셋이 없는 문자열을 `Date.parse`가 **실행 환경의 지역 시간**으로
  읽는다. 이 제품의 모든 시각은 한국 표준시 기준이므로 해석이 통째로 어긋난다.
- **대응**: 시각 문자열을 밀리초로 바꿀 때는 오프셋이 없으면 `+09:00`을 붙인 뒤 파싱한다
  (`src/stay/time.js`의 파싱 함수가 이미 그렇게 한다). 날짜·시각을 직접 `new Date(...)`로 만들지 말고
  이 함수를 쓴다.
- **확인**: `TZ=America/New_York npm test`로 돌려 본다. 시간대 의존이 있으면 여기서 드러난다.

## 도심 택시 추정기로 공항 이동을 재면 4시간이 나온다

- **증상**: 입국일 일정이 저녁에야 시작되고, 출국일은 외출이 하나도 만들어지지 않는다.
- **원인**: 도심 이동 추정기는 정체를 감안한 낮은 평균 속도를 쓴다. 인천공항–강남처럼 50km가 넘는
  구간에 그대로 적용하면 240분대가 나온다. 실제로는 공항철도·고속도로로 1시간 안팎이다.
- **대응**: 공항 구간은 별도 추정기를 쓴다(우회 계수 1.3, 60km/h, 터미널 이동 15분). 이 값들은
  숫자 기본값 파일이 아니라 공항 모듈에 있고, 일반 이동 버퍼와 **더하지 않는다.**
- **확인**: 두 공항 각각에 대해 도심 숙소까지 80분대·40분대가 나오는지 본다. 세 자리 분이면 잘못된 것이다.

## 외부 응답 캐시 본문에 기준점 좌표가 남는다

- **증상**: 캐시 파일을 열면 요청에 쓴 숙소 좌표가 그대로 보인다. 파일 이름은 요청 해시라 안전해 보인다.
- **원인**: 응답을 저장할 때 요청 매개변수를 함께 넣어두면 디버깅은 편하지만, 그 매개변수에 기준점
  좌표가 들어 있다. 파일 이름만 해시로 가려도 본문이 그대로면 의미가 없다.
- **대응**: 저장 전에 매개변수에서 좌표를 지운다. 캐시에 넣는 값은 "나중에 이 파일이 유출돼도
  괜찮은가"를 기준으로 고른다.
- **확인**: 캐시를 만든 뒤 파일 안에 좌표 값이 없는지 단언하는 테스트가 있다. 새 캐시를 도입하면
  같은 모양의 테스트를 함께 만든다.

## 검증 명령 묶음이 취약점 점검에서 통째로 멈춘다

- **증상**: `npm run check`가 코드와 무관하게 실패한다. lint·test·build는 통과했는데 결과만 실패다.
- **원인**: 묶음의 마지막이 의존성 취약점 점검이고, 현재 잠금 파일에 해결되지 않은 권고가 남아 있다.
  고칠 방법이 없는 게 아니라 **지금은 잠금 파일을 바꾸지 않기로 한 상태**다. 묶음은 `&&`로 이어져
  있어 마지막이 실패하면 전체가 실패한다.
- **대응**: 코드 변경의 통과 여부를 볼 때는 `npm run lint`, `npm test`, `npm run build`를 따로 돌린다.
  묶음 실패를 "내 변경이 깨뜨렸다"로 읽지 않는다.
- **확인**: 실패 출력이 권고 목록이면 코드 문제가 아니다.

## 화면 테스트가 예전 빌드로 통과한다

- **증상**: 코드를 고쳤는데 화면 테스트가 그대로 통과한다. 또는 고치기 전의 오류가 계속 난다.
- **원인**: 화면 테스트는 빌드 결과를 **띄우기만** 한다. 앞서 빌드하는 단계가 없어서, 남아 있는
  예전 빌드 결과가 그대로 실행된다. 자동 검증 파이프라인은 빌드를 먼저 돌리므로 여기서는 드러나지 않는다.
- **대응**: 로컬에서 화면 테스트를 돌리기 전에 `npm run build`를 먼저 돌린다.
- **확인**: 통과가 의심스러우면 화면에 보이는 문구를 일부러 바꿔 빌드하지 않고 돌려 본다.
  그래도 통과하면 예전 빌드를 보고 있는 것이다.

## 숨은 디렉터리 안의 빌드 산출물까지 lint가 훑는다

- **증상**: 손대지 않은 파일에서 lint 오류가 수백 개 쏟아진다. 경로가 작업용 임시 디렉터리 안이다.
- **원인**: lint 설정의 무시 목록에 없는 디렉터리는 숨김이어도 훑는다. 그 안에 빌드 산출물이 있으면
  생성된 코드가 전부 검사 대상이 된다.
- **대응**: 저장소 안에 작업용·산출물용 디렉터리를 새로 만들면 lint 무시 목록에 함께 넣는다.
  무시 목록은 `eslint.config.mjs` 한곳이다.

## 화면 테스트가 외부를 부르지 않게 하는 방법

- 관광공사 응답은 캐시 씨앗 스크립트가 미리 심는다. 캐시가 적중하므로 키는 실제로 쓰이지 않지만,
  **키 검사를 통과해야 캐시까지 도달**하므로 가짜 키 값을 넣어둔다.
- 기상 조회는 키 값에 **공백 한 칸**(또는 `off`)을 넣어 끈다. 빈 문자열로 두면 관광공사 키로 대신
  시도하기 때문에 외부 호출이 나간다. 이 구분을 모르면 차단기가 걸린다.
- 네트워크 감시 모듈을 서버 프로세스에 미리 붙여 외부 요청을 실패로 만든다. 이미 떠 있는 서버를
  재사용하면 감시가 붙지 않으므로 테스트는 늘 서버를 새로 띄운다.
- 사용 통계 전송도 외부 호출이다. 끄는 환경변수가 설정에 들어 있다.

## 정거장 식별자는 날짜·역할·장소로 결정된다

- 정거장 id는 `날짜:역할:장소id` 형태다(역할은 환자/보호자). 무작위 id를 쓰면 같은 입력을 두 번 넣었을
  때 결과가 달라 보이고, 전후 비교가 "전부 바뀜"으로 나온다.
- 새로 만드는 식별자도 같은 원칙을 따른다 — **결정적으로** 만든다.

## 복귀 마감과 예상 귀가 시각은 다른 값이다

- 마감은 "이 시각까지는 돌아와야 한다"는 안전선이고, 예상 귀가는 "계획대로면 이 시각에 도착한다"는
  값이다. 화면에는 둘 다 보여준다.
- 모든 외출에서 예상 귀가 ≤ 마감이 성립해야 한다. 이 관계가 깨지면 계산이 잘못된 것이다.
- 마감만 보여주면 사용자는 마감 직전까지 놀아도 되는 줄 안다.

## 병원 일정 직전 외출의 블록 계산

- 마지막 외출이 병원에서 끝나는 경우, 병원 일정 블록은 **일정 시작 시각부터** 시작한다. 숙소→병원
  이동을 블록에 넣으면 외출의 마지막 구간과 이중으로 계산된다.
- 병원에서 끝나는 외출을 만들 수 없어 숙소로 돌아오는 경우에만 블록이 '시작 − 이동 − 도착 여유'부터다.
- 45분 최소 창은 이렇게 정해진 블록 시작까지로 잰다.

## 병원 복귀 외출은 마감이 곧 외출 끝이다

- **증상**: 즉시 복귀(경우 2)가 풀린 재계획에서 이미 출발한 병원 복귀 외출이 '돌아온 외출'로 남고, 그 시간 위에
  병원 외출이 하나 더 짜인다. 숙소 복귀 외출은 같은 상황에서 멀쩡하다.
- **원인**: `occupancyEnd`는 병원으로 돌아가는 외출이면 `returnBy`(마감), 숙소로 돌아가는 외출이면 `plannedReturnAt`
  (예상 귀가)을 쓴다. `overdueSafe`가 마감을 지금·출발 시각으로 당기면 병원 복귀 외출은 그 순간 외출 끝이 지나
  `repairDay`가 다시 검증하지 않는 기록(`done`)이 된다.
- **대응**: 마감을 당긴 외출을 다시 쓸 때는 `occupancyEnd`로 끝났는지 판단하지 말고 마감부터 다시 잰다
  (`tripPlan.js`의 `remeasure`). 남은 시간 일정(`freshFrom`)은 하루 정거장 한도를 모르고 짜므로, 환자 외출이
  `repairDay`에서 잘리면 보호자 몫 장소까지 비어 있을 수 있다. `planStructural`은 해제·다시 만들기·새로 짜기 모두에서
  지금 입력으로 만든 전체 하루(`fresh`)의 보호자 외출로 한 번 더 채운다(findings 9·14). 이 단계 때문에 `repairDay`가 두 번
  돌 수 있으니 기록은 `carryLog`로 새로 받아 끝에서 `mergeLog`로 합친다. 첫 결과의 기록을 그대로 쓰면 버린 대체·사유가 섞인다.
  다시 채우기는 외출을 통째로만 더한다. 같은 장소가 이미 쓰였으면(예: 교통 지연 사건으로 지금 입력의 오전 보호자 외출이
  다른 장소를 골라 저녁 외출과 장소가 엇갈림) 그 보호자 외출은 더하지 않는다.

## 보호자 링크 길이

- 스냅샷은 정규 JSON → 압축 → 인증 암호화 → base64url 순으로 만든다. 압축 전후 차이가 4배 가까이 난다.
- 현재 크기(2026-11-08, 7일 범위 규칙 뒤): 최악 크기 7일 링크가 체류 길이와 무관하게 약 6,450~6,490자(메신저 기준 8KB 안).
  규칙 전에는 14박 12,249자, 45박 33,966자였다. 스냅샷에 필드를 더하면 이 숫자가 바로 커진다. 필드를 더하기 전에 길이 측정 테스트를 돌려 본다.
- 7일 범위 규칙 전에 가져온 사본은 복호화·정규화 때 범위로 잘린다(만든 날 또는 그 뒤 첫 날짜부터 7일). 공개 전이라 영향은 무시할 만하다.

## 확인 대화상자가 닫힌 뒤 초점이 body로 떨어진다

- **증상**: 목록의 행을 지우거나 해제하거나 동의를 철회하는 확인 뒤, 초점이 화면 맨 앞(body)으로 간다.
  키보드 사용자는 다음 Tab이 화면 처음부터 다시 시작하고, 화면 읽기 사용자는 지금 어디인지 잃는다.
- **원인**: 확인 대화상자(`AlertDialog`)는 닫힐 때 열기 전에 초점이 있던 요소로 돌려보낸다. 확인한 일이
  그 요소를 DOM에서 지우면(지운 행의 삭제 버튼, 철회로 통째로 사라진 철회 블록) 돌려보낼 곳이 없다.
- **대응**: 살아남는 화면에서 `lib/useRefocusAfterDialog.js`를 쓴다. 초점을 받을 후보를 앞에서부터
  `useRefocusAfterDialog(() => [목록 제목, 입력칸])`으로 주고, 확인한 일이 성공한 직후 돌려받은
  `armRefocus()`를 부른다. 후보는 `tabIndex={-1}` 제목이나 입력칸이다. 사라지는 부품 안에서는 훅이 돌지
  않으므로 그 부품은 콜백(`ConsentWithdraw`의 `onWithdrawn`)으로 화면에 알리고, 훅은 화면이 가진다.
- **확인**: `e2e/focus-flows.spec.js`의 '확인 대화상자 뒤 초점'. 새 확인 대화상자를 만들면 확인 뒤
  `document.activeElement`가 body가 아니고 main 안인지 같은 모양으로 단언한다.
- **함께 걸리는 것(스크롤)**: 대화상자는 열 때 history 한 칸을 쌓고 닫을 때 `history.back()`으로 되돌린다
  (`lib/useModalSheet.js`). 그 popstate 뒤 브라우저가 스크롤을 대화상자를 연 자리로 되돌린다. 확인한 일로
  화면이 크게 줄면(동의 철회로 철회 블록이 통째로 사라짐) 초점을 받은 제목이 화면 밖에 남는다. 초점은 맞아도
  보이지 않는다. 보여야 할 것이 있으면 popstate 뒤 다음 그리기에서 `scrollIntoView`로 데려온다
  (조건 화면의 철회 완료 문구, `app/conditions/page.js`의 `handleWithdrawn`). 확인은 `toBeInViewport()`로 한다.

## 가로 flex 줄의 아이콘 칸이 0폭까지 줄어든다

- **증상**: 글자 옆 아이콘이 좁은 칸에서 찌그러지거나 아예 사라진다. 아이콘은 16px로 정했는데 잰 폭은
  6px, 0px이다. 넓은 화면에서는 보이지 않는다.
- **원인**: 전역 규칙 `svg { max-width: 100% }` 때문에 svg를 감싼 flex 항목의 최소 폭(min-content)이 0이다.
  flex 항목은 기본이 `flex-shrink: 1`이라 글자가 길면 감싼 칸이 0까지 밀려난다. `svg.ui-icon`에 준
  `flex: none`은 svg 자신에게만 걸려, 감싼 칸에는 닿지 않는다.
- **대응**: 아이콘을 감싼 칸(flex 항목)에 `flex: none`을 준다. 같은 줄에 글자가 있는 새 아이콘 칸은
  처음부터 준다. 이미 그렇게 한 곳: 앞 아이콘 칸 `.ui-list-item-leading`, 답 칩의
  체크 표시 `.ui-answer-mark`.
- **확인**: 가장 좁은 폭(320px)에서 언어별로 아이콘 칸의 `getBoundingClientRect().width`가 정한 크기와
  같은지 잰다. 답 칩의 체크 표시는 이제 모든 언어에서 `.ui-answer-mark { flex: none }`이다(운영자 결정 2026-10-30).
  넣을 자리가 모자라는 칸은 아이콘을 줄이지 말고 줄을 바꾼다: 답 칩은 `flex-wrap`으로 체크를 글자 위 줄로 올린다.
  이때 글자 칸에 `min-width: 0`을 주지 않는다. 글자 칸이 낱말 폭 밑으로 줄면 body 의 `overflow-wrap: break-word`가
  'Allowe/d'처럼 낱말을 꺾는다.

## 서버 알림 (ADR-0012)

아래는 서버 알림 기반(A-1)을 만들며 알게 된 것이다. 코드는 `src/push/`와 `lib/server/watch/`에 있다.

### 푸시가 조용히 버려진다

- **증상**: 푸시 서비스가 201로 받았는데 보호자 기기에 알림이 뜨지 않는다. 오류도 기록도 없다.
- **원인**: RFC 8291(aes128gcm)은 평문 끝에 구분 바이트를 붙여야 한다. 레코드가 하나뿐이면 마지막 레코드 표시 `0x02`다.
  빠지면 브라우저가 복호화 뒤 본문을 버리고 서비스 워커의 `push` 이벤트가 오지 않는다. 푸시 서비스는 본문을 풀지 않으므로
  서버 쪽에서는 성공으로 보인다.
- **대응**: `src/push/encrypt.js`가 평문 뒤에 `LAST_RECORD_DELIMITER`(`0x02`)를 붙인다. `0x01`(중간 레코드)은 쓰지 않는다.
  평문 상한 3993바이트는 이 1바이트를 빼고 센 값이다.
- **확인**: 단위 테스트가 RFC 8291 부록 A의 시험 벡터와 본문을 바이트 단위로 맞춘다. 구분 바이트가 빠지면 이 테스트가 깨진다.

### VAPID 개인키를 읽지 못한다

- **증상**: `generate-push-secrets.mjs`나 다른 도구로 만든 VAPID 개인키(base64url 32바이트)를 `createPrivateKey`에 넣으면
  형식 오류가 난다.
- **원인**: VAPID 개인키는 P-256 스칼라 원시 32바이트다. Node의 `createPrivateKey`는 PEM·DER·JWK만 받고 원시 스칼라는 받지 않는다.
- **대응**: 공개키(비압축 65바이트)의 x·y와 개인키 d를 JWK(`{ kty: 'EC', crv: 'P-256', x, y, d }`)로 묶어 들인다
  (`src/push/vapid.js`). 들이기 전에 `createECDH`로 개인키에서 공개키를 다시 만들어 짝이 맞는지 본다.
- **확인**: 단위 테스트가 짝이 아닌 개인키를 넣으면 `PUSH_VAPID` 오류이고 메시지에 키 값이 없는지 본다.

### 예약 처리가 같은 마감에 두 번 온다

- **증상**: 같은 마감의 예약 처리 요청이 두 번 들어온다(마감을 뺐다가 다시 넣은 뒤, 또는 QStash 재시도).
- **원인**: QStash의 `Upstash-Deduplication-Id`는 10분 창 안에서만 같은 id를 막는다. 게다가 취소한 메시지에도 그 창이 걸려,
  같은 id를 쓰면 다시 넣은 마감의 새 예약이 삼켜진다. 중복 제거 id만으로는 '한 번만'을 지킬 수 없다.
- **대응**: 중복 제거 id는 마감마다 같은 머리 뒤에 예약마다 다른 무작위 꼬리를 붙인다(보조 장치). 주 장치는 날짜 기록의
  `HSETNX p:<시각>` 권리다. 권리를 얻은 요청만 보내고, 나머지는 `SKIP_DUP`으로 끝난다. `a:<시각>` 표시는 같은 마감에 예약을
  두 번 걸지 않게 한다.
- **확인**: 예약 처리 테스트가 같은 예약을 차례로 두 번, 동시에 두 번 불러 한 번만 보내는지 본다.

### 미리보기에서 예약 처리 경로가 401이다

- **증상**: 미리보기 배포에서 QStash 콘솔에 `/api/watch/due` 배달 실패(401)가 쌓인다. 앱 기록에는 그 요청이 없다.
- **원인**: 미리보기 배포는 Vercel 배포 보호가 걸려 있어 앱에 닿기 전에 막힌다. QStash는 Vercel 로그인을 할 수 없다.
- **대응**: Vercel의 자동화 우회 비밀(`VERCEL_AUTOMATION_BYPASS_SECRET`)을 만들고, 예약을 걸 때 `Upstash-Forward-x-vercel-protection-bypass`
  헤더로 싣는다. QStash가 접두사를 떼고 `x-vercel-protection-bypass`로 전달한다. 직접 부를 때(curl)도 같은 헤더를 붙인다.
- **확인**: 미리보기에서 Bearer와 우회 헤더를 붙여 `/api/watch/due`를 부르면 401이 아니라 판정표의 결과가 나온다
  (`docs/operations.md` '서버 알림 켜기').

### 보낼 권리를 얻은 뒤 함수가 죽으면 그 알림은 나가지 않는다

- **증상**: 마감 지남 알림이 한 번도 나가지 않았는데 날짜 기록에는 `p:<시각>`이 남아 있고, 뒤이은 QStash 재시도는 모두 `SKIP_DUP`이다.
- **원인**: 보내기는 '많아야 한 번'이다. `HSETNX`로 권리(`'1'`, 보내는 중)를 얻은 뒤 함수가 시간 초과로 죽거나 저장소가 실패해
  표시를 지우지 못하면, 재시도는 권리를 얻지 못한다. 두 번 보내는 것보다 놓치는 쪽을 골랐다.
- **대응**: 받아들인 한계다. 보내지 못한 결과(구독 없음, 한도, 구독 만료, 거절, 다시 시도)는 표시를 지우므로, 남는 경우는 권리와
  표시 정리 사이에서 함수가 죽는 때뿐이다. 기기 알림(갈래 1)은 이와 별개로 동작한다.
- **확인**: 기록에는 마감 시각이 남지 않아 줄 하나로는 가릴 수 없다. `watch.due`의 `SKIP_DUP`이 평소보다 많고 함수 시간 초과가
  함께 보이면 이 경우를 의심한다.

### 마감을 뺐다가 다시 넣으면 다시 보낸다

- **증상**: 이미 마감 지남 알림이 나간 마감을 환자가 일정에서 뺐다가 다시 넣자 같은 알림이 한 번 더 온다.
- **원인**: 마감 목록에서 빠진 시각은 `c:`·`a:`·`p:`·`k:` 표시가 함께 지워진다(`replaceDays`). 다시 넣으면 새 마감으로 다룬다.
- **대응**: 의도한 동작이다. 다시 보내는 알림은 같은 `tag`(`sh-watch-<날짜>-<시각>`)와 같은 `Topic`을 실으므로 보호자 기기와
  푸시 서비스는 앞 알림을 갈아 끼운다. 알림이 두 줄로 쌓이지 않는다.
- **확인**: 문구 테스트가 `tag`를 `sh-watch-<날짜>-<시각>`으로 고정한다. Topic은 저장 키·날짜·시각의 HMAC이라 같은 마감이면 같다.

### 구독 만료(404·410) 뒤에 새 구독이 지워질 수 있는 짧은 틈

- **증상**: 보호자가 기기를 바꿔 다시 구독한 직후 새 구독이 사라진다(드물다).
- **원인**: 푸시 서비스가 404·410을 주면 구독을 지운다. 지우기 전에 지금 구독을 다시 읽어 `subId`가 보낸 것과 같을 때만 지우지만,
  읽기와 지우기는 별도 요청이라 그 사이에 새 구독이 들어오면 함께 지워진다.
- **대응**: 틈이 저장소 요청 두 번 사이로 짧아 받아들였다. 다시 읽은 구독의 `subId`가 다르면 지우지 않고 `RETRY`(statusClass
  `404/410`)로 끝낸다. 예약 처리는 걸림 표시를 남긴 채 권리만 돌려놓고 다시 불리며, 그때 새 구독으로 보낸다. 보호자 화면(A-3)은
  상태 조회의 `subscriptionActive`가 거짓이면 그 지켜보기를 `MOVED`로 그리고 '이 휴대폰에서 다시 받기' 버튼을 보인다. 저절로 다시
  구독하지는 않는다(원인을 가릴 수 없고, 두 기기가 저절로 다시 구독하면 서로에게 '기기가 바뀌었어요'를 주고받는다).
- **확인**: 테스트가 404·410을 받는 사이 새로 구독한 경우 새 구독을 지우지 않고, 다시 불린 예약 처리가 새 기기로 한 번만 보내는지
  본다(검토 N2). 다시 읽은 뒤 지우기 전의 틈은 테스트로 덮지 않는다.

### 어제 23:55 마감의 예약 실패는 00:55 전에 하루 1회 예약이 돌아야 살아난다

- **증상**: 23:55 마감의 예약을 거는 데 실패한 날, 보호자에게 알림이 가지 않는다.
- **원인**: 보낼 시각은 다음 날 00:05, 늦은 한도는 00:55다. 실패한 예약은 다음 업로드나 하루 1회 예약이 다시 거는데,
  하루 1회 예약은 00:10 KST에 잡혀 있고 Vercel Hobby는 실행 시각을 59분까지 흔든다. 01:00쯤 돌면 이미 늦은 한도가 지나 걸지 않는다.
- **대응**: 하루 1회 예약은 어제·오늘·내일 색인을 함께 본다. 그래도 00:55 전에 돌지 않으면 그 마감은 놓친다. 마감 올리기 응답의
  `armFailed`가 0보다 크면 환자 기기가 잠시 뒤 전체를 다시 올려(A-2) 이 틈을 줄인다.
- **확인**: Vercel Cron 기록에서 하루 1회 예약의 실행 시각을, 응답에서 `failed` 수를 본다.

### 00:01에 '오늘 함께 있음'을 켜도 어제 23:55 마감의 알림은 00:05에 나간다

- **증상**: 보호자가 자정 직후 '오늘 함께 있음'을 켰는데 5분 뒤 마감 지남 알림이 온다.
- **원인**: '오늘 함께 있음'은 오늘(KST) 날짜 기록에만 적힌다. 어제 23:55 마감은 어제 날짜 기록에 속하고 보낼 시각이 오늘 00:05다.
- **대응**: 받아들인 한계다. 날짜를 넘는 마감까지 끄려면 어제 기록도 건드려야 해 '오늘'의 뜻이 흐려진다. 보호자 화면(A-3)은
  함께 있음 스위치 아래에 '자정 직전 마감의 알림은 자정 뒤에 올 수 있어요.'(`guardian.muteMidnight`)를 늘 보인다.
- **확인**: 예약 처리 테스트(자정 경계)가 어제 23:55 마감을 다음 날 00:05에 보내는지 본다. 함께 있음과 엮은 테스트는 아직 없다.

### 마감 올리기 둘이 겹치면 표시를 잃는다

- **증상**: 같은 지켜보기에 마감 올리기 둘이 겹치면 확인 표시가 사라지거나 날짜 하나가 통째로 빠진다.
- **원인**: `replaceDays`는 날짜 기록을 읽는 배치와 쓰는 배치, 두 번에 나눠 저장소를 부른다. 원자적이지 않아 겹친 업로드 사이에서
  늦게 쓴 쪽이 앞 쪽의 표시를 덮고, 늦게 쓴 쪽이 빈 목록이면 그 날짜 기록이 통째로 지워진다.
- **대응**: 클라이언트(A-2)는 지켜보기 하나에 업로드를 한 번에 하나만 보내고, 늘 가장 최근 상태 전체를 보낸다. 앞 업로드가
  끝나기 전에 바뀐 것은 끝난 뒤 다시 올린다.
- **확인**: `test/watch-sync.test.js`의 '요청은 하나씩' 시험이 올리는 중에 일정이 바뀌어도 동시에 열린 요청이 하나이고, 끝난 뒤
  최신 전체를 한 번 더 올리는지 본다. 탭이 여럿이면 탭마다 실행기가 있어 이 순서가 깨질 수 있다(아래 '서버 알림 환자 쪽 (A-2)').

### 보낸 직후 저장소가 실패하면 복귀 확인 알림이 나가지 않는다

- **증상**: 보호자는 마감 지남 알림을 받았는데, 환자가 '돌아왔어요'를 눌러도 복귀 확인 알림이 오지 않는다. 날짜 기록의
  `p:<시각>`이 `'s'`가 아니라 `'1'`로 남아 있다.
- **원인**: 푸시 서비스가 받은 뒤 `p:`를 `'s'`로 쓰고 날짜 기록을 다시 읽는 배치(`markSentAndReadDay`)가 저장소 장애로 실패했다.
  예약 처리는 이미 나간 알림이라 `SENT`로 끝내지만, `'돌아왔어요'`는 `'s'`일 때만 복귀 확인 알림을 보내고 `'1'`(보내는 중)은
  예약 처리에 맡긴다. 예약 처리는 이미 끝났으므로 아무도 보내지 않는다. 예약 걸기도 `'1'`인 시각은 다시 걸지 않는다.
- **대응**: 받아들인 한계다. 마감 지남 알림은 나갔고 확인은 기록됐다. 놓치는 것은 뒤따르는 복귀 확인 알림 하나이고, 보호자는
  상태 조회(`confirmed`)로 확인을 볼 수 있다. 그 마감은 다시 걸리지 않으므로 마감 지남 알림이 두 번 나가지는 않는다.
- **확인**: 예약 처리 테스트가 보낸 뒤 저장소가 실패해도 결과가 `SENT`인지 본다.

### 날짜 기록에 표시 하나만 남는 경우가 있다

- **증상**: 저장소에 마감 목록 없이 `p:<시각>` 또는 `a:<시각>` 필드 하나만 든 날짜 기록이 보인다.
- **원인**: 푸시를 보내는 사이 그 마감이 목록에서 빠졌거나 지켜보기가 지워졌다. 예약 처리의 권리 얻기(`HSETNX`)나 표시 쓰기가
  이미 지워진 해시에 필드 하나짜리 기록을 새로 만든다.
- **대응**: 받아들인 한계다. 그 기록에는 시각 표시 하나 말고 다른 내용이 없고, 쓸 때 만료(그 날짜 끝 + 1일)를 함께 걸므로
  날짜로부터 이틀 안에 저절로 사라진다. 예약 처리는 마감 목록이 비어 보이면 권리를 돌려놓고 `SKIP_CHANGED`로 끝낸다.
- **확인**: 해당 키의 TTL이 걸려 있는지(`TTL`이 -1이 아닌지) 본다.

### 하루 한도에 걸리거나 거절된 마감은 다시 걸리지 않는다

- **증상**: `SKIP_CAP` 또는 `SEND_REJECTED`로 끝난 마감은 환자가 다시 업로드하거나 보호자가 다시 구독해도 알림이 가지 않는다.
- **원인**: 이 둘은 예약 표시(`a:<시각>`)를 남긴다. 걸기는 `a:`가 있는 시각을 건너뛴다.
- **대응**: 의도한 동작이다. 지우면 업로드마다 다시 걸려 한도 초과나 거절을 되풀이하고 예약 업체 사용량만 늘어난다. 한도는
  지켜보기당 하루 20건이라 정상 사용에서는 닿지 않고, 거절은 구독이나 키 문제라 다시 걸어도 같은 결과다.
- **확인**: 기록에서 `watch.due`의 `SKIP_CAP`·`SEND_REJECTED` 수를 본다. 늘면 구독·VAPID 설정을 먼저 본다.

### 구독이 없으면 지난 마감이 업로드마다 다시 걸린다

- **증상**: 보호자가 아직 구독하지 않은 날, 같은 마감의 예약 처리가 업로드마다 `SKIP_NO_SUB`로 되풀이된다. QStash 사용량이
  평소보다 많다.
- **원인**: `SKIP_NO_SUB`는 예약 표시를 지운다. 나중에 구독하면 다시 걸 수 있게 하려는 것이다. 그래서 보낼 시각이 지난 마감도
  늦은 한도(마감 + 60분) 전이면 다음 업로드가 '지금'으로 다시 건다. '오늘 함께 있음'인 날은 걸기가 그 날짜를 통째로 건너뛰므로
  이 되풀이가 없다(함께 있음을 끄면 오늘을 다시 건다).
- **대응**: 받아들인 한계다. 되풀이는 늦은 한도까지(보낼 시각부터 50분)이고, 지켜보기당 하루 예약 발행 120건(`arm`)과 마감 올리기의
  횟수 제한(지켜보기당 시간당 60)이 위를 막는다. 클라이언트(A-2)는 일정이 바뀔 때만 업로드하므로 실제 횟수는 이보다 훨씬 적다.
- **확인**: QStash 콘솔의 하루 메시지 수가 무료 한도(하루 1,000건)에 가까워지면 `watch.deadlines` 기록 수를 본다.

### 예약 발행이 지켜보기당 하루 120건에서 멈춘다

- **증상**: 예약 업체 장애가 없는데 마감 올리기 응답의 `armFailed`가 0보다 큰 채로 이어지고, 그날 남은 마감에 알림이 가지 않는다.
- **원인**: 걸기는 예약 업체에 발행하기 직전마다 지켜보기의 하루 발행 횟수(`arm`, 120건)를 엿보고(`peekRate`), 예약 업체가 받은
  발행만 센다(`countRate`, 걸림 표시를 쓰기 전). 한도에 닿으면 그 마감과 이번 호출에서 그 지켜보기의 남은 마감을 모두 `failed`로
  세고 발행하지 않는다. 마감 목록을 바꿔 가며 계속 올려 예약 업체 사용량을 늘리는 요청을 막는 장치다. 하루 창은 UTC 기준이라
  09:00 KST에 새로 시작한다. 엿보기와 세기 사이에 다른 호출이 끼면 한도를 조금 넘을 수 있다.
- **대응**: 의도한 동작이다. 정상 사용(하루 마감 10개 이하, 다시 걸기 몇 번)은 닿지 않는다. 코드에는 모든 지켜보기를 합친 전체
  상한이 없다. 지켜보기를 여럿 만드는 경우는 계정당 지켜보기 수(3)와 만들기 횟수 제한(시간당 10)이 막고, 그 위는 운영자가 예약
  업체·저장소의 월 비용 상한으로 막는다(ADR-0012 결정 20).
  - 실패한 발행은 `arm`에 세지 않는다. 처음에는 발행 전에 세어서, 예약 업체 장애 동안 환자 기기가 `armFailed`를 보고 같은 전체를
    여섯 번쯤 다시 올리면 그날 한도 120건을 실패로 다 썼다. 업체가 돌아와도 다음 업로드와 00:10 하루 1회 예약이 아무것도 걸지 못해,
    09:00 KST 창이 바뀐 뒤 업로드가 올 때까지 하루 이틀 보호자 알림이 나가지 않았다(최종 검토 I1).
  - 실패는 따로 `armFail`(지켜보기당 하루 40건)에 센다. 넘으면 그 호출에서 그 지켜보기의 남은 마감은 시도하지 않고 `failed`로
    센다. 다음 호출은 다시 시도하므로 장애가 이어지는 동안 호출 하나가 쓰는 발행 시도는 한 번이고, 업체가 돌아오면 그날 안에 다시 걸린다.
- **확인**: 테스트가 한 계정이 지켜보기 셋에 마감을 번갈아 올려도 지켜보기마다 120건을 넘지 않는지 본다(검토 B1). 예약 업체가 업로드
  여섯 번 동안 실패한 뒤 돌아오면 다음 업로드와 하루 1회 예약이 모두 거는지도 본다. 운영에서는 QStash 콘솔의 하루 메시지 수와
  `watch.deadlines` 기록의 `failed` 수를 함께 본다.

### 걸림 표시를 지우는 순간 들어온 구독·함께 있음 끄기·마감 다시 넣기

- **증상**: 예약 처리가 `SKIP_NO_SUB`·`SUB_GONE`·`SKIP_MUTED`·`SKIP_CHANGED`로 끝났는데 `retry`가 참이라 QStash가 다시 부른다.
- **원인**: 이 넷은 걸림 표시(`a:`)를 지워 나중에 다시 걸 수 있게 한다. 그런데 구독, 함께 있음 끄기, 마감 다시 넣기는 먼저 쓰고
  그 뒤에 다시 걸기가 날짜 기록을 읽는다. 둘이 엇갈리면 다시 걸기는 아직 남은 `a:`를 보고 건너뛰고, 예약 처리는 그 뒤 `a:`를
  지운다. 아무도 다시 걸지 않아 알림을 놓친다.
- **대응**: 예약 처리는 `a:`를 지우는 `HDEL`과 이유 다시 읽기(구독은 `EXISTS`, 함께 있음·마감 목록은 `HGETALL`)를 한 배치로
  보낸다. 지운 뒤 이유가 사라졌으면 `retry: true`로 끝내 다시 불리고, 그때 보낸다. 반대쪽은 쓰기가 먼저, 다시 걸기의 읽기가
  나중이다. 이 순서 덕분에 어느 한쪽은 반드시 다른 쪽을 본다. 구독은 구독을 쓴 뒤에, 함께 있음 끄기는 `m`을 지운 뒤에 다시 건다.
  순서를 바꾸지 않는다. 권리(`p:`)를 쥔 뒤라면 `p:`도 같은 `HDEL`로 돌려놓는다(따로 지우면 그 사이 다시 걸기가 '보내는 중'을 보고
  건너뛴다). 구독은 남았는데 풀 수 없으면(봉인 키 설정 문제) `EXISTS`가 참이라 늦은 한도까지 다시 불린다. QStash 재시도 횟수와
  늦은 한도(`SKIP_LATE`)가 위를 막는다.
- **확인**: 테스트가 네 경우(검토 N2·N3·N4와 마감 다시 넣기)에서 다시 불린 예약 처리가 살아 있는 구독으로 한 번만 보내는지 본다.

### 다시 등록과 출국일 변경이 겹치면 한쪽 변경이 사라진다

- **증상**: 다시 등록으로 쓰기 토큰을 바꾼 직후, 새 토큰으로 보낸 요청이 `NOT_FOUND`이고 옛 토큰이 다시 통한다. 또는 다시 등록
  둘이 모두 `ok`였는데 토큰 하나만 통하고 등록 횟수는 하나만 늘었다.
- **원인**: 마감 올리기는 출국일이 바뀌면 앞에서 읽은 지켜보기 레코드에 출국일만 바꿔 통째로 쓴다. 그 사이 다시 등록이 쓰기 토큰을
  바꿨으면 옛 토큰으로 되돌린다(검토 N5). 다시 등록도 읽은 레코드로 통째로 쓰므로, 둘이 겹치면 늦게 쓴 쪽만 남는다(검토 N6).
- **대응**: 클라이언트(A-2)는 지켜보기 하나에 등록·출국일 변경을 한 번에 하나만 보내고, 앞 요청이 끝나기 전에는 다음을 보내지
  않는다. 한 기기가 보내는 요청이라 이 순서를 지키면 생기지 않아 저장소에 비교 후 쓰기를 들이지 않았다. 등록 횟수 상한(5)은 겹친
  등록을 하나로 세므로 느슨해질 수 있지만, 등록 횟수 제한(계정당 시간당 10)이 위를 막는다.
- **확인**: A-2 실행기(`lib/trip/watchSync.js`)는 등록, 올리기, '돌아왔어요', 끄기, 서버 지우기를 한 약속 사슬로 줄 세운다.
  `test/watch-sync.test.js`가 동시에 열린 요청이 하나인지(`maxOpen`) 본다.

### 계정당 지켜보기 셋을 넘길 수 있다

- **증상**: 한 계정의 지켜보기가 3개(`maxWatchesPerOwner`)보다 많다.
- **원인**: 새 지켜보기를 만들 때 소유 집합을 세어 본 뒤 만든다. 세기와 만들기가 원자적이지 않아 같은 계정이 새 지켜보기를 동시에
  만들면 둘 다 세기를 통과한다.
- **대응**: 받아들인 한계다. 넘는 수는 만들기 횟수 제한(계정당 시간당 10)이 막는다. 만들기는 소유 집합에 먼저 넣고 그다음 지켜보기를
  만들므로, 응답을 잃어도 내 정보 전체 삭제가 찾아 지운다(검토 E2).
- **확인**: 저장소에서 소유 집합의 크기(`SCARD`)를 본다. 3을 넘는 계정이 잦으면 클라이언트가 등록을 겹쳐 보내는지 본다.

### 구독과 출국일 변경이 겹치면 구독이 옛 만료로 남을 수 있다

- **증상**: 출국일을 늘린 뒤 옛 출국일 + 7일이 지나자 보호자 구독이 사라진다(지켜보기는 남아 있다). 상태 조회의
  `subscriptionActive`가 거짓이다.
- **원인**: 구독 쓰기는 구독을 쓰는 같은 배치에서 지켜보기를 다시 읽고, 출국일이 달라졌으면 구독의 만료를 다시 맞춘다. 이 맞추기는
  따로 보내는 요청이라, 그 사이 출국일이 또 바뀌면 구독이 한 단계 옛 만료로 남는다.
- **대응**: 받아들인 한계다. 마감 올리기는 출국일이 같아도 매번 구독 만료를 다시 맞추므로(`touchExpiry`) 다음 업로드가 고친다.
  보호자 화면(A-3)은 `subscriptionActive`가 거짓이면 '이 휴대폰에서 다시 받기' 버튼을 보이고, 보호자가 누르면 다시 구독한다.
- **확인**: 테스트가 구독과 출국일 연장이 겹쳐도 구독이 늘어난 출국일까지 남는지(검토 E4), 만료 맞추기가 한 번 실패해도 다음
  업로드가 고치는지(검토 E1) 본다.

### 예약 처리 서명은 경로만 맞춰 보고 호스트는 보지 않는다

- **증상**: 서명 검증 코드가 서명의 `sub`(목적지 주소)에서 호스트를 무시한다. 다른 배포로 보낸 예약의 서명도 경로가 같으면 통과한다.
- **원인**: 미리보기 배포는 배포마다 호스트가 다르고, 운영도 사용자 도메인과 `vercel.app` 주소를 함께 쓴다. 호스트까지 맞추면
  기준 주소 설정 하나가 어긋날 때마다 모든 예약이 401이 된다.
- **대응**: 받아들인 한계다. 서명은 본문 SHA-256과 만료(`exp`)·`nbf`에 묶여 있어 본문을 바꿀 수 없다. 다른 환경으로 옮겨도 본문의
  저장 키는 그 환경의 소유 비밀로 만든 것이 아니고 저장소 접두사도 달라 `SKIP_NO_WATCH`로 끝난다. 운영과 미리보기의 QStash 서명
  키를 따로 두면 이 경로도 막힌다.
- **확인**: 서명 검증 테스트가 다른 경로의 서명을 거부하는지 본다.

### 테스트 안에서 stdout을 통째로 가로채면 실행기 보고가 섞인다

- **증상**: 처리기를 부르는 동안 `process.stdout.write`를 가로채 "기록 줄 말고는 아무것도 없다"를 단언하면, 처리기가 아무것도
  쓰지 않아도 알 수 없는 바이트 조각이 잡혀 시험이 실패한다.
- **원인**: `node --test`가 띄운 테스트 파일 프로세스는 같은 stdout에 실행기 보고(직렬화한 `test:start`·`test:pass` 등)를 쓴다.
  보고는 비동기로 흘러가므로 처리기의 `await` 사이에 끼어든다.
- **대응**: 출력 전체를 봐야 하는 시험은 실행기가 없는 별도 프로세스로 돌린다(`test/watch-routes-child.js`를 `spawnSync`로 띄우고
  stdout·stderr를 그대로 받는다. 부모가 쓸 값은 fd 3으로 받는다). 같은 프로세스 안에서는 기록 줄만 골라 모으고 나머지는 흘려보낸다.
- **확인**: 자식 스크립트를 직접 돌려(`node test/watch-routes-child.js 3>/dev/null`) 기록 줄만 나오는지 본다.

### 이 기계의 grep으로는 대시 검사가 늘 통과한다

- **증상**: 문서에 엠대시·엔대시를 넣었는데 `grep '\x{2013}\|\x{2014}'` 같은 검사가 아무것도 찾지 못한다.
- **원인**: 이 기계의 `grep`은 ugrep이다. 기본 문법에서 `\|`를 글자 그대로 읽어 '또는'이 되지 않는다. 그래서 예전 명령은 늘 통과했다.
- **대응**: perl로 검사한다. `git diff -U0 | grep '^+' | perl -CSD -ne 'print if /[\x{2013}\x{2014}]/'`의 결과가 없어야 한다.
- **확인**: 대시가 든 줄을 일부러 넣고 위 명령이 그 줄을 출력하는지 한 번 본다.

### 이 기계의 Node(26)에서 통과한 시험이 CI(Node 22)에서 취소된다

- **증상**: 로컬 `npm test`는 모두 통과하는데 CI의 `quality`에서 응답을 끝없이 미루는 가짜 `fetch` 시험이
  "Promise resolution is still pending but the event loop has already resolved"로 실패하고, 같은 파일의 뒤 시험이 줄줄이
  `cancelledByParent`가 된다. 같은 실행에서 VAPID 키 쌍 확인이 다른 쌍을 받아들인다.
- **원인**: 두 가지다. `AbortSignal.timeout()`의 타이머는 이벤트 루프를 붙잡지 않는다(unref). 기다리는 것이 그 타이머뿐이면
  Node 22 테스트 실행기는 루프가 빈 것으로 보고 약속을 취소한다. 또 Node 22는 JWK(x, y, d)로 개인키를 읽을 때 공개키와
  맞는 쌍인지 확인하지 않는다. 이 기계의 Node 26은 둘 다 다르게 동작해 로컬에서는 드러나지 않았다.
- **대응**: 시간 한도는 `AbortController`와 붙잡는 `setTimeout`으로 걸고 끝나면 지운다(`lib/server/watch/timeout.js`의
  `withTimeout`, `src/push/send.js`). 키 쌍은 `createECDH('prime256v1')`에 개인키를 넣어 만든 공개키와 비교한다
  (`lib/server/watch/config.js`). CI는 `.github/workflows`의 `node-version: 22.x`다.
- **확인**: 이 기계에는 Node 18(`/opt/homebrew/opt/node@18/bin/node`)이 있다. 바깥 호출·암호 관련 시험은
  `/opt/homebrew/opt/node@18/bin/node --test <파일>`로도 돌려 본다(고치기 전 코드는 Node 18에서 CI와 같은 실패 1건, 취소 30건이었다).

'묶인 외출'과 '원래 마감'의 뜻은 `docs/business-rules.md` '서버 알림의 돌아왔어요'에 있다.

### 다음 외출이 없는 날, 일정에서 빠진 나중 외출의 마감이 원래 마감이 된다

- **증상**: 그날 마지막 외출이 묶였는데(당겨짐, 또는 올린 적 없는 지난 마감), 업로드에 일정에서 이미 빠진 나중 외출의 마감이 남고
  그 외출의 '돌아왔어요'가 그 시각을 확인한다.
- **원인**: 원래 마감은 그날 마지막으로 올린 시각 중 출발보다 늦고 다음 외출의 출발보다 이른 가장 이른 시각이다. 다음 외출이 없으면
  범위 끝이 없다. 올린 기록에는 외출 단위 식별이 없어, 빠진 나중 외출의 마감과 당김이 풀린 외출의 원래 마감을 구별할 수 없다.
- **대응**: 받아들인 한계다. 빼면 진짜 원래 마감을 놓쳐 보호자 알림이 사라질 수 있어 남기는 쪽을 골랐다. 남긴 시각은 그 외출의
  '돌아왔어요'가 확인하므로 누를 버튼 없는 알림은 생기지 않는다.
- **확인**: 이 경우만 고정한 시험은 없다. `test/watch-plan.test.js`의 '늦게 등록한 뒤 저녁 외출의 마감이 바뀌면...' 시험이 다음 외출의
  출발이 찾는 범위의 끝이 되는 쪽을 본다. 고치려면 올린 기록에 외출 id를 더해야 한다.

### 올린 적 없는 지난 마감에는 '돌아왔어요' 버튼이 없다

- **증상**: 마감이 지난 외출인데 오늘 카드와 시트에 '돌아왔어요'가 없다.
- **원인**: 마감 뒤에 처음 등록했거나, 오프라인이라 마감 전에 올리지 못한 외출이다. 오늘 지난 마감은 고정이라(D1) 올린 적 없는 지난
  시각을 새로 더하지 않는다. 새로 더하면 올리자마자 보호자 알림이 간다. 그 외출은 묶인 외출이 되고 원래 마감을 찾지 못하면 버튼이 없다.
- **대응**: 받아들인 한계다. 서버에도 그 마감이 없어 보호자 알림이 가지 않으므로 누를 일이 없다. 기기 알림(갈래 1)은 그대로 울린다.
- **확인**: `test/watch-plan.test.js` '처음 등록이 외출 마감 뒤면 지난 마감을 올리지 않고 돌아왔어요 대상도 없다'.

### 자정 뒤에 어제 외출의 '돌아왔어요'를 처음 여는 화면이 없다

- **증상**: 23:50 마감 외출에서 00:02에 돌아온 환자가 앱을 열면 '돌아왔어요'를 누를 곳이 없다. 서버는 어제 23:50 마감을 00:00에
  보낸다(마감 + 10분).
- **원인**: 마감 지남 시트와 오늘 카드는 오늘(KST) 날짜만 본다. 지난 날의 시트를 다시 열어도 버튼을 두지 않는다(화면 검토 반영).
  날짜가 지난 외출을 오늘 화면에서 고르는 규칙이 없다.
- **대응**: 자정 전에 누른 것(대기 포함)은 어제 날짜로 보내고 서버도 받는다. 이미 열려 있는 마감 지남 시트는 자정이 지나도 닫힐 때까지
  버튼 자리를 유지한다. 자정 뒤에 처음 여는 경우만 남는다.
- **확인**: `test/returned-view.test.js` '시트의 날이 오늘(KST)일 때만 둔다'. 자정을 넘긴 열린 시트는 화면 부품의 동작이라 단위
  시험이 닿지 않는다.

### 404는 갈아 끼움, 만료, 다른 곳의 '서버 지우기'를 구분하지 못한다

- **증상**: 설정에 '다른 기기에서 서버 알림을 다시 설정했어요'가 보이는데 다른 기기에서 설정한 적이 없다.
- **원인**: 서버는 모르는 id, 만료, 틀린 토큰을 바이트까지 같은 404로 답한다(어느 쪽인지 알리지 않는 것이 보안 규칙이다). 출국일 끝 +
  7일이 지났거나, 같은 계정이 다른 기기에서 '서버에 남은 내 정보 지우기'를 했어도 같은 404다.
- **대응**: 문구는 운영자 결정(D9)대로 하나다. 어느 경우든 다시 켜는 길(보호자 링크를 새로 만들기)이 같다.
- **확인**: `test/watch-sync.test.js` '404 면 REPLACED 를 쓰고 더 올리지 않으며 대기열의 확인은 FAILED 다', `e2e/server-push.spec.js`의
  갈아 끼움 시험.

### 지난 뒤 늘어난 마감은 예전 시각에도 알림이 갈 수 있다

- **증상**: 외출 중 마감이 18:00에서 19:00으로 늘었는데 보호자에게 18:10에 알림이 간다.
- **원인**: 오늘 지난 마감은 고정이다(D1). 18:00이 이미 지난 뒤에 늘었으면 18:00은 서버에 남고 19:00이 더해진다. 18:00에는 확인이
  없으므로 예약 처리가 보낸다.
- **대응**: 받아들인 한계다(D1이 감수한 것). 지운다면 경우 2 재계획이 마감을 당길 때 서버의 원래 마감과 확인 표시가 함께 사라진다.
  늘어나기 전에 눌렀으면 확인이 남아 있다.
- **확인**: `test/watch-plan.test.js` '지난 마감은 일정에서 빠져도 남기고 지나지 않은 마감은 뺀다 (D1)'.

### 같은 마감의 앞 외출이 있고 나중 외출이 당김으로 빠지면 그 마감이 확인되지 않는다

- **증상**: 앞 외출(A)과 외출 중인 B가 같은 21:00 마감이었는데, B가 당겨져 묶이고 그 뒤 외출(C, 22:30)이 재계획으로 빠진 날이다.
  B의 '돌아왔어요'는 22:30을 확인하고, 21:00에는 환자가 돌아와 눌렀어도 보호자 알림이 갈 수 있다.
- **원인**: B의 원래 마감을 찾을 때 A의 지금 마감(21:00)은 후보에서 빠진다(다른 외출의 지금 마감은 원래 마감이 아니다). C가 빠져
  찾는 범위의 끝도 없다. 남은 후보 중 가장 이른 22:30(빠진 C의 마감)이 원래 마감이 된다.
- **대응**: 받아들인 한계다. 알림을 놓치는 쪽이 아니라 더 보내는 쪽이다. 고치려면 올린 기록에 외출 단위 식별이 필요하다. 제외 규칙을
  없애거나 시간으로 자르면 업로드가 되풀이되거나 고아 시각이 생긴다(검토 시뮬레이터에서 확인).
- **확인**: 이 경우를 고정한 시험은 없다. 원래 마감을 아예 찾지 못한 경우(다르게 정한 것 26)는 `test/watch-plan.test.js` '앞 외출과 하루
  활동 종료(21:00)를 함께 쓰던 나중 외출이 당겨지면...' 시험이 본다.

### 외출 중 늘어난 마감이 올라간 뒤 그 외출이 묶이면 지난 시각이 원래 마감으로 잡힌다

- **증상**: 드문 경우다. 외출 중 마감이 늘어 올라간 뒤 그 외출이 당겨져 묶이면, '돌아왔어요'가 늘어난 마감이 아니라 앞서 지난 시각을
  확인하고 늘어난 마감은 업로드에서 빠진다.
- **원인**: 원래 마감은 후보 중 가장 이른 시각을 고른다. 지난 시각과 늘어난 마감이 둘 다 범위 안에 있으면 지난 시각이 이긴다.
- **대응**: 받아들인 한계다. 지금 이후 후보를 먼저 고르면 흔한 경우(늦은 뒤 묶임)가 깨진다.
- **확인**: 이 경우를 고정한 시험은 없다. 생기면 그날 `lastUploaded`와 외출의 출발·마감을 함께 본다.

### 하루 10개가 차면 버튼이 서버에 없는 시각을 가리킬 수 있다

- **증상**: '돌아왔어요'를 눌렀는데 '전달하지 못했어요'가 보인다. 서버 응답은 `recorded: false`다.
- **원인**: 하루 10개 상한은 지금 마감, 원래 마감, 최근 지난 시각 순으로 남긴다. 지금 마감과 원래 마감으로 10개가 차면 묶이지 않은
  외출의 지난 마감이 업로드에서 빠지지만, 그 외출의 버튼은 여전히 그 시각을 가리킨다.
- **대응**: 받아들인 한계다. 하루 정거장 한도가 5개(`DEFAULTS.stopsPerPace`)라 지금 마감과 원래 마감만으로 10개가 차는 날은 드물다.
  화면은 실패 줄로 직접 연락을 안내한다.
- **확인**: `test/watch-plan.test.js` '하루 10개 상한: 지금 마감, 다음 원래 마감...' 시험.

### 등록 중에 계정이 바뀌거나 다른 탭이 먼저 켜면 방금 만든 지켜보기가 남을 수 있다

- **증상**: A 계정으로 서버 알림을 켜는 도중 로그아웃하고 B 계정으로 들어왔다. 또는 같은 계정의 다른 탭이 먼저 서버 알림을 켰다.
- **원인**: 등록 응답이 오기 전에 계정이나 레코드가 바뀌면 실행기는 그 결과를 쓰지 않는다(다른 계정에 남의 id를 쓰지 않고, 다른 탭의
  결과를 덮지 않는다). 서버에는 방금 만든 지켜보기가 생겼지만 그 쓰기 토큰을 아는 레코드가 없다.
- **대응**: 계정이 바뀐 경우는 그 `{ watchId, writeToken }`을 서버 삭제 대기(기기 키, 계정과 무관)에 넣어 지운다
  (`store.queueServerDelete`). 다시 등록(REPLACED)한 id는 앞 계정의 레코드와 이미 보낸 보호자 링크가 쓰므로 지우지 않는다. 같은
  계정의 다른 탭이 먼저 켠 경우는 남기고 `docs/tracking/findings.md` 19번에 적었다. 링크에 그 `watchId`가 실리지 않아 알림은 가지 않고,
  만료(출국일 끝 + 7일)까지 계정의 지켜보기 한도 하나를 차지한다.
  다시 등록 중에 계정이 바뀐 경우는 서버가 새 토큰을 갖지만 그 토큰을 아는 기기가 없다. 앞 계정으로 돌아오면 404로 갈아 끼움이
  보이고, 다시 등록하면 풀린다.
  등록은 됐는데 기기에 쓰지 못한 경우(기다리는 동안 세션 만료로 보기 전용, 저장 실패 STORAGE_FAILED)도 새 id는 서버 삭제 대기에
  넣는다. 다시 등록(REPLACED)은 넣지 않는다. 레코드는 예전 토큰 그대로라 서버가 아무 기기도 모르는 새 토큰을 들고 있고, 다음에 켤 때
  같은 watchId로 다시 등록하면서 풀린다.
  줄 서 있던 등록이 시작될 때 이미 계정이 바뀐 경우는 아래 '줄 선 등록·끄기·서버 지우기가 시작될 때 계정이 바뀌어 있을 수 있다'에 있다.
- **확인**: `test/watch-sync.test.js` '등록: 응답 사이에 다른 계정으로 바뀌면 그 계정에 레코드를 쓰지 않는다'와 계정 전환 삭제 대기 시험,
  기기 쓰기 실패 시험 둘('세션이 만료돼 기기에 쓰지 못하면', 'STORAGE_FAILED').

### 늦게 돌아와 다음 외출을 건너뛴 날에는 확인이 되돌려져 집에 있어도 알림이 갈 수 있다

- **증상**: 환자가 외출 B에서 다음 외출 D의 계획 출발보다 늦게 돌아와 '돌아왔어요'를 눌렀는데, 그 뒤 마감 시각에 보호자 알림이 간다.
- **원인**: 확인은 누른 외출의 출발 시각을 들고 있고, 같은 마감을 쓰는 더 늦게 출발하는 외출이 있으면 그 확인을 스스로 되돌린다(다르게
  정한 것 25). 재계획이 D를 '외출 중'으로 보고 묶은 뒤 앞 외출의 마감으로 대체하면(다르게 정한 것 26) D가 B보다 늦게 출발하는 외출로
  잡힌다. 누른 시각 대신 출발 시각으로 판단하게 바꾼 것은 누른 직후 1분 안에 생긴 나중 외출을 놓친 문제(검토 P7)를 막기 위해서다.
- **대응**: 받아들인 한계다. 알림을 놓치는 쪽이 아니라 더 보내는 쪽이고, D의 카드에 '돌아왔어요'가 다시 보여 한 번 더 누르면 확인된다.
  검토 시뮬레이터에서 수백 번 실행에 몇 건 수준이다.
- **확인**: `test/watch-plan.test.js`의 같은 분 출발 시험, 검토 시뮬레이터(놓친 알림 0).

### 저장소가 따로 보낸 DELETE와 실행기의 마감 올리기가 겹치면 서버 기록이 다시 생긴다

- **증상**: 동의 철회나 내 정보 지우기 뒤에도 그 지켜보기의 날짜 기록이나 지켜보기 레코드가 서버에 남아 있다.
- **원인**: 서버 삭제 대기는 기기 저장소가 실행기와 따로 보낸다. 같은 지켜보기의 `PUT /api/watch/deadlines`가 이미 나가 있고 서버가
  DELETE 뒤에 그 PUT의 쓰기를 마치면 날짜 기록이 다시 쓰이고, 출국일이 바뀐 업로드였으면 앞서 읽은 지켜보기 레코드도 다시 쓰인다
  (서버의 읽기와 쓰기가 원자적이지 않다).
- **대응**: 받아들인 한계다. 다시 생긴 기록은 TTL로 사라지고(날짜 기록은 그 날짜 끝 + 1일, 지켜보기는 출국일 끝 + 7일), 구독은 DELETE가
  지워 보호자 알림은 가지 않는다(`SKIP_NO_SUB`). 고치려면 실행기가 저장소의 삭제를 같은 요청 줄에 세우거나, 삭제 대기를 보내기 전에
  실행기의 요청이 끝나기를 기다려야 한다.
- **확인**: 이 겹침을 고정한 시험은 없다. 서버 기록에서 그 저장 키의 레코드와 구독 유무를 본다.

### 탭이 여럿이면 요청이 겹치고, 다른 탭의 되돌리기가 기기에서만 취소된다

- **증상**: 두 탭을 열어 둔 기기에서 확인 표시가 사라지거나, 한 탭에서 되돌린 확인이 서버에는 남아 보호자 알림이 가지 않는다.
- **원인**: 실행기는 탭마다 하나다. '한 번에 하나'는 탭 안에서만 지켜져 두 탭의 마감 올리기가 겹칠 수 있다(위 '마감 올리기 둘이
  겹치면 표시를 잃는다'). 또 A 탭이 대기열의 확인을 보내는 동안 B 탭에는 그 항목이 대기(QUEUED)로 보이고, B에서 되돌리면 보내지 않은
  확인으로 보고 요청 없이 대기열에서 뺀다. A의 요청은 이미 서버에 닿아 확인이 남는다.
- **대응**: 받아들인 한계다. 홈 화면 앱은 보통 창이 하나다. 고치려면 탭 사이 잠금(Web Locks)이나 한 탭만 보내는 규칙이 필요하다.
- **확인**: 시험은 없다. 생기면 두 탭의 요청 순서를 브라우저 네트워크 기록으로 본다.

### 줄 선 등록·끄기·서버 지우기가 시작될 때 계정이 바뀌어 있을 수 있다

- **증상**: 링크 만들기의 켜기·끄기, 설정의 끄기·'서버에 남은 내 정보 지우기'가 누른 화면의 계정이 아닌 계정에 닿는다. 고치기 전에는
  B의 지켜보기가 서버에서 모두 지워지거나, 동의하지 않은 B에게 지켜보기가 생겨 A 이름공간에 적히거나, 가려진 A 탭의 마감 올리기가
  B 쿠키로 나가 404를 받고 A의 켜진 지켜보기가 갈아 끼움(REPLACED)으로 바뀌었다.
- **원인**: 둘이 겹친다. 하나, 등록·끄기·서버 지우기는 실행기 한 줄에서 앞선 일 뒤에 줄 선다. 앞선 비우기는 마감 올리기 하나와
  '돌아왔어요' 대기열(최대 20건)을 하나씩 보내고(요청마다 한도 15초), 도는 중에 새 계기가 오면 끝난 뒤 다시 돈다. 그래서 줄 선 일은
  몇 분을 기다릴 수 있고 그 사이 계정이 바뀐다. 둘, `POST /api/watch`와 `DELETE /api/watch { all: true }`는 브라우저에 하나인 세션
  쿠키로 인증한다(마감 올리기도 세션이 있으면 소유자를 맞춰 본다). 다른 탭이 B로 로그인하면 쿠키는 곧바로 B인데, 이 탭의 메모리
  세션은 화면 복귀 때의 조절(1분에 한 번, 가려진 동안 묻지 않음, `components/pwa/sessionUpkeep.js`) 때문에 한동안 A로 남았다.
- **대응**: 두 겹이다.
  - 누른 때의 계정 키를 실행기에 넘긴다(링크 만들기, 설정의 끄기·서버 지우기). 일이 시작될 때 저장소의 지금 계정과 다르면 요청·레코드
    쓰기·삭제 대기·비우기 없이 UNAVAILABLE이다. 누른 화면에 계정이 없었으면(`null`) 그것도 다른 계정으로 본다. 같은 탭에서 세션이 바뀐
    경우를 덮는다.
  - 다른 탭이 마지막 계정 키를 바꾸거나 지우면(다른 계정 로그인, 내 정보 지우기) 저장소가 메모리 세션을 버린다(`recheckAccount`). 탭은
    새 계정의 보기 전용(세션 확인 전과 같은 상태, 안내 배너 없음)이 되고, 저장소가 조절을 거치지 않고 곧바로 세션을 다시 묻는다. 이
    탭의 세션이 아직 없어도(첫 세션 확인 중, 버린 뒤 다시 묻는 중) 버린다. 버리기 전에 보낸 세션 확인의 응답과 늦은 연결 오류는 반영하지
    않는다(이미 새 계정으로 확인된 탭을 앞 계정으로 열거나 오프라인 보기 전용으로 돌리지 않는다). 다시 묻기가 답을 받지 못하면(연결 오류,
    실패 응답) 5초 뒤 한 번만 더 묻고, 그 뒤는 화면 복귀·온라인 계기(`components/pwa/sessionUpkeep.js`)가 맡는다. 그동안은 보기 전용이라
    세션 쿠키로 인증하거나 소유자를 맞춰 보는 요청(등록, 전체 삭제, 마감 올리기)이 나가지 않는다. '돌아왔어요'는 보기 전용에서도
    대기열에서 나가지만 쓰기 토큰으로 인증하므로 계정이 바뀐 것과 상관없다.
  - 대조는 기기의 마지막 계정 키를 이 탭이 마지막으로 본 값과 한다. storage 이벤트를 받을 때, 다시 보일 때(`pageshow`,
    `visibilitychange`: 뒤로·앞으로 캐시에서 돌아온 탭과 얼었던 탭은 이벤트를 받지 못했을 수 있다), 세션 응답을 반영하기 전(이벤트보다
    앞 쿠키의 응답이 먼저 온 경우), 실행기가 일과 비우기를 시작할 때 한다. 다시 보일 때의 대조는 저장소를 만들 때(`getStore()`) 걸어,
    같은 사건에 `lib/trip/useTrip.js`가 건 비우기보다 먼저 돈다. 비우기도 시작할 때 다시 대조한다. 세션 계정이 아니라 본 값과 대조하는
    것은, 이 탭이 마지막 계정 키를 쓰지 못한 기기에서 돌아올 때마다 세션을 버리고 다시 묻지 않게 하려는 것이다. 방금 연 탭은 기기에
    남은 마지막 계정 키를 본 값으로 시작한다(비워 두면 열 때 오는 `pageshow`가 첫 세션 확인을 무르고 한 번 더 묻는다).
  - storage 이벤트가 마지막 계정 키를 바꿨다고 알리면(바뀌기 전과 뒤의 원문이 다르다) 지금 값이 본 값과 같아도 버린다. 이 탭이 사건을
    처리하기 전에 다른 탭이 A에서 B로, 다시 A로 바꿨으면 지금 값은 본 A 그대로인데, 그 사이 B 쿠키로 보낸 세션 확인이 나가 있을 수
    있다. 이미 대조로 받은 바뀜의 사건이 늦게 와도 한 번 더 버리고 묻는다(보기 전용이 요청 한 번만큼 길어질 뿐이다).
  - 다른 탭의 로그아웃 보류 표시와 저장소 전체 비움은 상태와 데이터를, 세션 만료 타이머는 상태를 늘 한 번 알린다
    (`announceOutsideChange`, 함께 한 세션 버리기의 알림도 이 한 번으로 모은다). `transition`은 바꾸기 전 상태를 지금 저장소와 시계로
    다시 읽으므로, 다른 탭이나 시계가 이미 바꾼 것은 알리지 못한다.
  - 그래서 위의 계정 비교가 쿠키의 계정을 따라가고, 보기 전용인 동안은 마감 올리기·등록·끄기·서버 지우기가 나가지 않는다. 응답을
    기다리던 일은 바뀐 계정의 레코드를 다시 읽으므로 앞 계정의 레코드를 쓰지 않는다(404여도 갈아 끼움을 쓰지 않는다). 링크 결과·양식과
    설정의 확인 시트는 계정이 바뀌면 새로 시작한다.
  - 덮지 못하는 것 하나: 이 탭이 다른 탭의 쿠키 바뀜을 알기 전에 나간 요청. 쿠키는 다른 탭의 로그인 응답에서 바뀌는데, 마지막 계정 키는
    그 탭이 로그인 뒤 화면을 열고 첫 세션 응답을 받아야 쓴다(화면 하나를 여는 시간과 요청 한 번). 거기에 이 탭이 이벤트를 받거나 위의
    대조를 할 때까지가 더해진다. 이미 나가 있던 요청도 그대로 끝난다.
  - 덮지 못하는 것 둘: 기기 저장소를 쓸 수 없는 브라우저(사생활 보호 모드·차단 설정, `lib/store/index.js`가 메모리로 대신한다). 탭마다
    저장소가 따로라 마지막 계정 키를 나눠 갖지 않고 storage 이벤트도 없는데 쿠키는 함께 쓴다. 이 탭은 자기 세션 확인(화면 복귀 1분 조절,
    온라인, 앱 열기) 전까지 앞 세션을 들고 있다.
  - 덮지 못하는 것 셋: 마지막 계정 키를 쓰지 못한 탭(저장 공간이 꽉 참 등). 다른 탭은 이 탭의 로그인을 알 길이 없다.
  - 덮지 못하는 것 넷: storage 이벤트를 받지 못한(또는 아직 처리하지 않은) 탭에서 사건 없는 대조 두 번(다시 보일 때, 세션 응답을
    반영하기 전, 실행기가 일을 시작할 때) 사이에 마지막 계정 키가 A에서 B로, 다시 A로 돌아온 경우. 값만 대조하므로 바뀜을 모르고, 그
    사이 B 쿠키로 보낸 세션 확인의 답(B)을 A 쿠키인데 반영한다. 사건을 처리한 탭은 위의 사건 규칙으로 덮인다(뒤늦게 처리한 사건도
    세션을 버리고 다시 묻는다). 마지막 계정 키 기록에 바뀐 횟수를 더하면 덮을 수 있지만 저장 모양을 바꾸지 않았다.
  - 위 넷은 서버가 예상 계정과 세션을 맞춰 보는 확인으로 막는다. 스위치 전 할 일로 적었다(`docs/tracking/status.md` '진행을 막는 것').
  - 덮지 못하는 것 다섯: 서버 지우기 응답을 기다리는 동안 계정이 B로 바뀐 경우(같은 탭의 세션 갱신이든 다른 탭의 로그인이든). A의 서버
    지켜보기는 지워졌는데, 응답 뒤 쓰기가 B의 이름공간을 읽어 레코드가 다르다고 보므로 A의 기기 레코드는 ON으로 남는다. 위의 세션
    버리기는 이 경우를 덮지 않는다(보기 전용이 되어도 A 이름공간에는 쓰지 못한다). A로 돌아오면 다음 마감 올리기가 404를 받아 갈아
    끼움이 보이고, 보호자 링크를 새로 만들면 풀린다.
- **확인**: `test/watch-sync.test.js` 'accountKey 를 넘겼는데 앞선 비우기를 기다리는 사이' 시험 셋(등록, 끄기, 서버 지우기),
  `test/guardian-server-push.test.js` '링크 만들기 중 계정 전환', `test/store-account-switch.test.js`(탭 둘이 저장소를 나눠 쓰고 쿠키를
  변수 하나로 대신한다: 세션 버리기, 늦은 세션 응답, 줄 선 서버 지우기·등록, 뒤에서 도는 올리기, 첫 세션 확인 중의 전환, A에서 B로 다시
  A, 다른 탭의 내 정보 지우기, 늦은 실패, 한 번 더 묻기, pageshow·visibilitychange 대조, 실행기의 대조, 이벤트보다 먼저 온 응답, 다른
  저장 영역의 사건, 계정 키 null, A에서 B로 다시 A를 한꺼번에 받은 사건, 방금 연 탭의 시작 값, 다른 탭의 로그아웃 보류 알림),
  `test/settings-server-push.test.js` '시트를 연 때와 계정이 다르면'과 '확인 시트의 버튼이 부르는 실행기',
  `e2e/server-push.spec.js` '다른 탭이 마지막 계정 키를 바꾸면 보이던 링크 결과가 사라진다'.

### 화면 훅과 포커스 이동에는 단위 테스트가 없다

- **증상**: `lib/trip/useWatch.js`를 고쳐도, `ReturnedConfirm`·`ServerPushSection`·`GuardianCreate`의 포커스 이동을 깨도 `npm test`가 통과한다.
- **원인**: 단위 테스트는 `node --test`로 돌고 DOM이 없다. 표시 규칙은 순수 모듈(`returnedView.js`, `serverPushView.js`,
  `components/guardian/serverPush.js`)로 빼서 시험하지만, 훅과 버튼이 사라질 때 포커스를 상태 줄로 옮기는 일은 React 부품 안에 있다.
- **대응**: 화면 테스트(`e2e/server-push.spec.js`)가 훅을 거친 결과(버튼, 상태 줄, 요청 본문)를 본다. 포커스가 어디로 가는지는 아직
  단언하지 않는다. 포커스 코드를 고치면 키보드로 직접 확인하거나 화면 테스트에 `toBeFocused` 단언을 더한다.
- **확인**: `E2E_PORT=<빈 포트> npm run e2e -- e2e/server-push.spec.js`(빌드 먼저).

### 보기 전용에서는 마감을 올리지 않는다

- **증상**: 세션이 만료된 기기에서 일정 화면을 열어도 `PUT /api/watch/deadlines`가 나가지 않는다. '돌아왔어요'는 나간다.
- **원인**: 일부러 그렇게 정했다(계획 다르게 정한 것 9). 보기 전용에서는 재계획·편집이 막혀 일정이 바뀌지 않으므로 서버는 이미 마지막
  상태를 갖고 있다. 남은 체류 전체를 올려 두므로 날짜가 바뀌어도 새로 올릴 것이 없다. '돌아왔어요'는 쓰기 토큰 권한이라 보기 전용
  예외다(결정 8).
- **대응**: 쓰기 가능으로 돌아오면(`writable` 계기) 올리지 못한 것(`uploadPending`)을 올린다.
- **확인**: `e2e/server-push.spec.js`의 보기 전용 시험이 마감 올리기 0건과 '돌아왔어요' 요청을 함께 본다.

### 스위치가 꺼져 있어도 설정 읽기 요청이 나간다

- **증상**: 서버 알림 스위치가 꺼진 운영에서도 보호자 링크 만들기 화면과 설정 화면을 열면 `GET /api/push/config`가 나간다.
- **원인**: 항목을 보일지 정하려면 서버에 물어야 한다. 스위치 값을 번들에 굽지 않는 것은 켜고 끌 때 다시 빌드하지 않기 위해서다.
- **대응**: 받아들인 비용이다. 저장소를 읽지 않는 공개 경로이고, 실행기가 5분 동안 결과를 기억한다. '돌아왔어요'는 이 기기에 지켜보기
  레코드가 있을 때만 묻는다. `/api/watch*` 요청은 0건이다.
- **확인**: `e2e/server-push.spec.js`의 첫 시험(실제 서버, 스위치 꺼짐)이 설정 응답 모양과 `/api/watch` 요청 0건을 본다.

### Playwright에서 오프라인으로 연 페이지는 다시 연결해도 online 사건이 오지 않는다

- **증상**: 화면 테스트에서 `context.setOffline(true)`로 새로 고친 뒤 '돌아왔어요'를 누르고 `setOffline(false)`로 되돌려도 대기열이 보내지지
  않는다. 실제 브라우저에서는 연결되면 보낸다.
- **원인**: Playwright의 오프라인 흉내에서는 오프라인으로 새로 연 페이지의 `navigator.onLine`이 `true`다. 그래서 다시 연결해도 상태가
  바뀌지 않아 `online` 사건이 오지 않고, 세션 확인 실패로 오프라인이 된 저장소는 오프라인으로 남는다. 저장소는 `navigator.onLine`으로
  시작하므로 오프라인 새로 고침 직후에 '앱 열기' 비우기가 한 번 나가 연결 없음으로 끝나기도 한다(서버에 닿지 않고 대기열에 남는다).
  `context.route`는 오프라인에서도 응답을 주므로 가짜 서버(`stubServerPush`)는 따로 `offline` 표시를 두고 요청을 끊는다.
- **대응**: 시험은 다시 연결한 뒤 `window.dispatchEvent(new Event('online'))`로 실제 브라우저가 보내는 사건을 대신 보낸다. 실제 사용에서는
  `online` 사건과 화면 복귀 때의 세션 확인이 저장소를 온라인으로 되돌린다.
- **확인**: `e2e/server-push.spec.js`의 오프라인 시험.

## 서버 알림 보호자 쪽 (A-3)

아래는 보호자 화면(A-3)을 만들며 알게 된 것과 알고 남긴 틈이다. 코드는 `lib/notify/guardianPush.js`(실행기),
`lib/notify/guardianPushPlan.js`·`pushSupport.js`(순수 규칙), `src/guardian/pushRequests.js`(요청 모양), `lib/store/guardianPush.js`(기기
기록), `public/sw.js`(푸시 받기), `lib/notify/device.js`(R4), `components/guardian/GuardianPushItem.js`·`guardianPushView.js`·
`returnStatus.js`·`PasteLink.js`에 있다. 요청 규칙은 `docs/contracts.md` 'A-3 클라이언트가 지키는 것', 화면 규칙은
`docs/business-rules.md` '서버 알림의 보호자 쪽'에 있다. 기다리는 사이 계정이 바뀌는 경우는 A-2의 '줄 선 등록·끄기·서버 지우기가
시작될 때 계정이 바뀌어 있을 수 있다'와 같은 두 겹(저장소의 세션 버리기, 실행기의 계정 대조)으로 막는다. 덮지 못하는 것과 서버 쪽
예상 계정 확인도 그 절에 있다.

### `renotify`를 `tag` 없이 주면 알림이 뜨지 않는다

- **증상**: 서비스 워커의 `showNotification`이 `TypeError`로 거절되고 푸시가 조용히 끝난다.
- **원인**: `renotify: true`는 `tag`가 있을 때만 받는다. 서버 본문의 `tag`가 빠지거나 형식이 틀린 채 `renotify`만 실으면 생긴다.
- **대응**: `public/sw.js`는 `tag`가 `/^sh-watch-(\d{4}-\d{2}-\d{2}-\d{2}:\d{2}|device)$/`에 맞을 때만 `tag`와 `renotify: true`를 함께
  싣는다. 맞지 않으면 둘 다 빼고 알림은 낸다.
- **확인**: `test/pwa-sw.test.js` 'push: tag 가 형식 밖이면 tag 와 renotify 를 싣지 않는다'.

### Safari는 권한 요청을 누름 안에서만 받는다

- **증상**: 아이폰 홈 화면 앱에서 '앱이 닫혀 있어도 받기'를 눌러도 권한 창이 뜨지 않거나 구독이 거절된다.
- **원인**: Safari는 알림 권한 요청과 푸시 구독을 사용자 동작(누름) 가까이에서만 받는다. 누른 뒤 설정 읽기와 서비스 워커 준비 확인을
  기다린 다음 권한을 물으면 사용자 동작 밖이 된다.
- **대응**: 켜기(`turnOn`)는 첫 `await` 전에 권한 요청(`turnOnDeviceNotifications`)을 시작한다. 설정 읽기와 준비 확인은 항목을 그릴 때
  미리 해 둔다(`prepare`): 준비가 참으로 확인됐으면 누를 때 다시 묻지 않는다. `pushManager.subscribe`는 켜기, 다시 받기, 다시 켜기
  안에서만 부르고, 다시 맞추기는 구독을 만들지 않는다(키가 바뀌면 '다시 켜기' 버튼, 결정 19).
- **확인**: `test/notify-guardian-push.test.js` 'turnOn: 권한 요청이 첫 await 전에 시작되고 ...', 'prepare 는 설정과 준비 확인을 미리 해
  두고 켜기는 다시 기다리지 않는다'. 아이폰에서 실제로 받는지는 실기기 확인 전이다(`docs/tracking/status.md`).

### `push` 처리기가 없는 옛 서비스 워커가 구독을 받으면 푸시가 조용히 사라진다

- **증상**: 구독은 성공했는데 서버 푸시가 와도 알림이 뜨지 않는다. 아이폰은 이런 조용한 푸시가 쌓이면 알림 권한을 거둔다.
- **원인**: 서비스 워커는 페이지보다 늦게 바뀐다. A-3 전의 워커(`push` 처리기 없음)가 활성인 채로 구독하면 그 워커가 받은 푸시는
  `showNotification` 없이 끝난다.
- **대응**: 구독 전에 활성 워커에 `SAFEHOUR_SW_INFO`를 보내 `{ push: true }` 답을 2초(`SW_INFO_TIMEOUT_MS`) 기다린다. 없으면
  `registration.update()` 뒤 컨트롤러 교체를 5초(`SW_UPDATE_TIMEOUT_MS`)까지 기다리고 한 번 더 묻는다. 그래도 없으면 `SW_NOT_READY`이고
  '새로 고침' 버튼을 보인다. 워커의 `push` 처리는 본문이 깨져도 `event.waitUntil(showNotification(...))`을 부른다. `SW_VERSION`은
  `'2026-11-16.1'`이다.
- **확인**: `test/notify-guardian-push.test.js` '준비 확인 답이 없으면 update 뒤 다시 묻고 ...', `test/pwa-sw.test.js` 'push: event.waitUntil 이
  showNotification 약속을 받는다(조용한 푸시 0)'.

### 다시 켜기는 옛 브라우저 구독을 먼저 지운다

- **증상**: 서버의 VAPID 키가 바뀐 뒤 '다시 켜기'를 누르면 구독이 던지거나, 같은 휴대폰에 '알림 받는 기기가 바뀌었어요'가 온다.
- **원인**: 키가 다른 구독이 남은 채 `pushManager.subscribe`를 부르면 브라우저가 던진다(`InvalidStateError`). 옛 주소가 살아 있는 채 새
  주소로 `POST`하면 서버는 주소가 바뀌었다고 보고 옛 주소에 기기 바뀜 알림을 보낸다.
- **대응**: `renew`는 옛 브라우저 구독을 먼저 `unsubscribe()`한 뒤 새로 구독하고, 이 계정의 구독(사본이 살아 있고 `gone`도 `moved`도
  아닌 것)을 모두 다시 `POST`한다. 켜기와 다시 받기도 키가 맞지 않는 브라우저 구독은 지우고 새로 만든다.
- **확인**: `test/notify-guardian-push.test.js` 'renew 는 unsubscribe 를 subscribe 보다 먼저 부르고 모든 구독을 다시 POST 한다'.

### 같은 마감에 기기 늦은 알림과 서버 푸시가 둘 다 온다

- **증상**: 마감과 마감 + 10분 사이에 앱을 연 보호자에게 기기 마감 지남 알림이 오고, 10분 뒤 서버 푸시가 또 온다. 서버 푸시를 눌러
  앱을 열면 같은 마감의 기기 늦은 알림이 한 번 더 울릴 수 있다.
- **원인**: 보호자 기기 알림은 결정 15대로 그대로다(예약과 늦은 알림 창 `returnPassedGraceMin` 60분, 복귀 확인과 무관). 기기 알림은
  마감 도래, 서버 푸시는 확인 없음으로 뜻이 다르다. 알림을 누르면 알림 칸에서 닫히므로, 앱이 열리며 도는 기기 늦은 알림을 같은 태그
  확인으로 막지 못한다.
- **대응**: 받아들였다. 표시만 합친다(R4): 보호자 마감 지남 기기 알림의 태그를 서버 푸시와 같은 `sh-watch-<날짜>-<HH:MM>`로 하고, 서비스
  워커로 낼 때 같은 태그 알림이 떠 있으면 내지 않는다(`deliverToDevice`, 1초 `TAG_CHECK_TIMEOUT_MS` 안에 답이 없으면 낸다). 알림 칸에는
  한 줄이다. 확인된 마감의 기기 알림 건너뛰기(검토안 R1)와 구독 중 늦은 알림 창 줄이기(R3)는 결정 15를 바꾸는 일이고 서버 푸시가
  실패했을 때의 받침을 없애므로 하지 않았다. 겹침을 줄일지는 A-4 실기기 확인 때 운영자에게 묻는다(`docs/tracking/status.md`).
- **확인**: `test/notify-device.test.js` '같은 tag 알림이 떠 있으면 기기 알림을 내지 않는다(서비스 워커 경로)'. 누른 뒤 다시 울리는지는
  실기기에서 본다.

### 마감 태그에 환자가 없어 두 환자의 같은 분 알림이 서로 갈아 끼운다

- **증상**: 한 기기에서 환자 둘을 구독한 보호자에게 같은 날 같은 분 마감의 서버 푸시가 하나만 남는다.
- **원인**: 서버 푸시 태그 `sh-watch-<날짜>-<HH:MM>`에 환자를 가리는 값이 없다(A-1 본문 모양). 같은 태그 알림은 알림 칸에서 한 줄이라
  뒤 알림이 앞 알림을 갈아 끼운다.
- **대응**: 서버 쪽은 받아들인 한계로 두고 스위치 전 할 일로 적었다(`docs/tracking/status.md` '진행을 막는 것'). 기기 늦은 알림은 예약을
  만든 사본과 다른 `watchId`를 가진 사본에 같은 날짜·시각 마감이 있으면 공유 태그 대신 예약 id 태그로 내고 떠 있는지 묻지 않는다
  (`mayShareWatchTag`, `sharedWatchTag`). `watchId`가 없는 사본은 푸시를 받을 수 없어 세지 않는다. 그래도 기기 알림이 공유 태그로 나가
  다른 환자의 푸시 때문에 건너뛰거나 갈아 끼워질 수 있는 때가 셋 남는다: 앞 계정의 구독(이 계정에서 그 사본을 읽을 수 없다)이 같은
  시각 푸시를 보낼 때, 다른 환자 사본이 23:59에 지워진 뒤 늦게 깬 23:5x 타이머가 돌 때, 다른 환자가 링크를 보낸 뒤 일정을 바꿔 서버
  마감만 같은 시각이 됐을 때(판단 근거가 사본에 담긴 마감이다). 앱 안 배너는 그대로 뜬다.
- **확인**: `test/notify-device.test.js` 'mayShareWatchTag: ...', `test/notify-runtime.test.js` '다른 환자 사본에 같은 마감이 있으면 ...'.

### 앱을 열지 않는 동안 구독 주소가 바뀌면 서버 푸시가 닿지 않는다

- **증상**: 보호자가 한동안 앱을 열지 않았는데 서버 푸시가 오지 않는다. 앱을 열면 다시 온다.
- **원인**: 브라우저가 구독 주소를 바꾸면 서비스 워커에 `pushsubscriptionchange`가 온다. 이 처리기와 서비스 워커 IndexedDB를 두지
  않았다(워커가 다시 `POST`하려면 `watchId`·`subId`를 워커 저장소에 둬야 한다).
- **대응**: 받아들인 틈이다. 앱을 열 때 다시 맞추기가 브라우저 구독의 주소 해시를 기록과 견주어, 키가 같고 해시가 다르면 같은 구독으로
  다시 `POST`한다.
- **확인**: `test/notify-guardian-push.test.js` 'endpoint 해시가 다르면 같은 브라우저 구독으로 다시 POST 하고 한 실행에 한 번만 시도한다'.

### 계정을 바꿔도 앞 계정의 구독이 이 기기로 계속 온다

- **증상**: 한 기기에서 다른 계정으로 로그인했는데 앞 계정이 구독한 환자의 서버 푸시가 계속 온다.
- **원인**: 브라우저 구독은 기기에 하나이고 모든 계정이 함께 쓴다. 서버는 구독 주소로 보낼 뿐이고, 알림 문구에 환자 이름이 없다. 실행기는
  지금 계정의 기록만 다시 맞춘다.
- **대응**: 받아들인 틈이다. 앞 계정으로 돌아와 끄거나, '이 기기에서 내 정보 지우기'(모든 계정의 구독을 해지 대기로 옮기고 브라우저
  구독도 지운다)를 하면 멈춘다. 사본이 만료되면 그 구독은 앱을 열 때 저장소가 모든 계정에서 대기로 옮긴다.
- **확인**: `test/store-guardian-push.test.js`(구독이 사본의 수명을 따르는지, 내 정보 지우기).

### 두 탭이 함께 다시 `POST`하면 `MOVED`가 잘못 보일 수 있다 (Web Locks로 막고, 없는 브라우저에만 남음)

- **증상**: 다른 기기를 쓰지 않았는데 '다른 기기가 알림을 가져갔거나 이 휴대폰의 알림 주소가 만료됐어요'가 보이고, 다시 받기 전까지
  서버 푸시가 오지 않는다. 지금은 아래 '남는 틈'의 경우에만 생길 수 있다.
- **원인**: 탭마다 실행기가 따로 돈다. 두 탭이 같은 지켜보기를 거의 같이 다시 `POST`하면(예: 언어를 바꾸면 한 탭은 저장소 알림으로,
  다른 탭은 `storage` 사건으로 다시 맞춘다) 서버는 나중에 받은 구독의 `subId`를 갖는데, 응답이 늦게 온 탭이 기록을 나중에 쓰면 기기
  기록의 `subId`가 서버와 어긋난다. 그 쓰기는 저장소 불변식에 따라 덮인 `subId`(서버의 지금 구독)를 해지 대기에 넣으므로 서버 구독이
  지워진다. 한 탭의 켜기·다시 받기가 다른 탭의 다시 맞추기와 겹쳐도 같다.
- **대응**: 실행기의 줄에 선 일(켜기, 다시 받기, 다시 켜기, 끄기, 함께 있음, 다시 맞추기, 상태 조회)을 Web Locks(`navigator.locks`,
  이름 `safehour-guardian-push`) 안에서 돌려 같은 기기의 탭 사이에서도 한 번에 하나다. 상태 조회도 404면 구독을 빼므로(`gone`) 잠금
  안이다. 일은 잠금을 얻은 뒤 기록, 사본, 언어, 브라우저 구독을 다시 읽어 정하므로 차례를 늦게 받은 탭은 이미 맞은 기록을 보고 다시
  `POST`하지 않는다. 권한 창 기다림과 `forgetBrowser`는 잠금 밖이다. 잠금은 60초(`DEVICE_LOCK_HOLD_MS`)까지만 붙잡는다: 요청은
  `sendWatchRequest`의 15초 한도가 있지만 브라우저 푸시 API(`subscribe`, `unsubscribe`)는 한도가 없어서, 60초가 지나면 일이 끝나지
  않았어도 다른 탭이 차례를 받는다. 일이 실패해도, 탭이 닫혀도 잠금은 풀린다.
  - 남는 틈: Web Locks가 없거나 잠금 요청이 실패하면 예전처럼 탭 안 줄로만 지켜 이 어긋남이 생길 수 있다. 한 탭의 일이 60초를 넘겨
    차례가 넘어간 경우도 같다. 그때는 다음 상태 조회가 `MOVED`를 보이고 '이 휴대폰에서 다시 받기'가 고친다(저절로 다시 구독하지 않는
    규칙, 정한 값 9는 그대로).
  - 지원: Web Locks는 Chrome 69 이상, Edge 79 이상, Firefox 96 이상, Safari 15.4 이상(macOS, iOS·iPadOS)에 있다. 실기기 시험
    대상(`docs/operations.md`: 안드로이드 Chrome, 아이폰 홈 화면 앱, 데스크톱 브라우저)의 지금 버전은 모두 있다. 아이폰 웹 푸시가 되는
    iOS·iPadOS 16.4 이상은 늘 있다. 푸시는 되고 잠금은 없는 것은 Chrome 68 이하, Firefox 95 이하 같은 옛 버전뿐이다.
- **확인**: `test/notify-guardian-push.test.js` '같은 기기의 두 탭(Web Locks)'(함께 다시 맞춰도 `POST` 하나와 서버의 지금 구독, 다른 탭의
  다시 맞추기 중 켜기, 붙잡는 시간과 실패한 일, 잠금이 없거나 요청이 실패할 때, 권한 창은 잠금 밖).

### `MOVED`는 다시 받기로만 풀린다

- **증상**: 다시 맞추기나 '다시 켜기'를 해도 `MOVED` 줄이 남는다. 화면 언어를 바꿔도 그 지켜보기는 다시 `POST`되지 않는다.
- **원인**: `moved` 구독을 다시 `POST`하면 서버가 다른 휴대폰의 구독을 이 휴대폰으로 바꾸고, 두 기기가 저절로 다시 구독하면 서로에게
  '기기가 바뀌었어요'를 주고받는다.
- **대응**: 일부러 정했다. 다시 맞추기와 다시 켜기는 `moved` 구독을 건너뛴다. '이 휴대폰에서 다시 받기'(`takeOver`)만 다시 `POST`해 푼다.
  `moved`만 남은 계정의 다시 켜기는 `UNAVAILABLE`이라, 화면은 그 지켜보기에 다시 켜기 대신 다시 받기 버튼만 보인다.
- **확인**: `test/notify-guardian-push.test.js` 'moved 이면 언어·해시가 바뀌어도 다시 POST 하지 않는다'.

### 켜기가 도는 동안 끄기를 누르면 켜기의 결과가 온다

- **증상**: 권한 창이 열려 있거나 켜기가 도는 동안 끄기·오늘 함께 있음을 누르면 끄기가 아니라 켜기의 결과가 나온다.
- **원인**: 같은 지켜보기의 켜기·끄기·다시 받기·함께 있음이 도는 중이면 실행기는 새 동작을 시작하지 않고 도는 동작의 약속을 돌려준다.
  켜기 중간에 끄기가 끼면 구독과 해지가 엇갈린다.
- **대응**: 일부러 정했다. 그동안 `getState(watchId).busy`가 참이고 화면은 두 스위치를 `aria-disabled`로 잠근다(포커스는 남는다). 켜기가
  끝난 뒤 다시 누르면 끈다.
- **확인**: `test/notify-guardian-push.test.js` '같은 지켜보기의 켜기를 두 번 눌러도 같은 약속이고 권한 요청과 POST 는 한 번이다'(끄기도 같은
  약속인지 함께 본다).

### 기록하지 못한 구독의 직접 해지가 닿지 않으면 서버 구독이 남는다

- **증상**: 켜기가 `UNAVAILABLE`·`READ_ONLY`·`FAILED`로 끝났는데 그 지켜보기의 서버 푸시가 온다(환자 일정이 끝날 때까지).
- **원인**: 서버가 구독 `POST`를 받아들였는데 응답을 기다리는 사이 계정이 바뀌었거나(또는 보기 전용이 됨) 기기 기록 쓰기가 실패하면,
  실행기는 받은 `subId`를 해지 대기로 넘긴다(`queueUnsubscribe`). 대기 상한(10)에 밀려 남지 못하면 해지를 한 번 직접 보내는데, 그 결과는
  보지 않는다. 닿지 않으면 다시 보낼 곳이 없다.
- **대응**: `OFF_UNSENT`와 같은 받아들인 틈이다(끄기에서 대기 상한에 밀린 해지를 직접 보냈는데 닿지 않은 경우, 다시 맞추기의 끄기에서도
  생긴다). 서버 구독은 지켜보기 만료(출국일 끝 + 7일)까지 남는다. 끄기·다시 맞추기는 `OFF_UNSENT` 줄로 알리지만, 이 경우의 결과 줄은 그
  동작의 결과(`UNAVAILABLE`, `READ_ONLY`, `FAILED`)라 남은 구독을 따로 알리지 않는다. 권한을 잃어 다시 맞추기가 끈 것이면 `OFF_UNSENT`
  대신 `PERMISSION_LOST`를 남긴다(권한 없이는 남은 서버 구독이 알림을 띄우지 못한다).
- **확인**: `test/notify-guardian-push.test.js` 'POST 는 받아들여졌는데 기록을 쓰지 못하면 받은 구독을 해지 대기로 넘기고, 대기 상한에
  밀리면 한 번 직접 보낸다', '계정이 바뀐 뒤 받은 구독을 넘길 때 대기 상한에 밀리면 한 번 직접 보낸다'. 직접 보낸 해지가 실패한 경우의
  결과 줄은 시험으로 고정하지 않았다.

### 상태 조회는 최대 5분 묵는다

- **증상**: 환자가 '돌아왔어요'를 되돌렸는데 보호자 화면에 '복귀 확인'이 잠시 남는다.
- **원인**: 받은 일정 화면은 보이는 동안 5분(`STATUS_POLL_MS`)마다, 그 밖에는 앱 열기·화면 복귀·온라인 복귀·마감 타이머 때 묻는다. 앞
  조회(실패한 시도 포함)와 2분(`STATUS_MIN_GAP_MS`) 미만이면 건너뛴다.
- **대응**: 받아들였다. 그날 절 아래 '{시각}에 서버에서 확인한 내용이에요.'로 조회 시각을 보이고, 꼬리표는 늘 '실제로 돌아왔는지는 알 수
  없다'는 안내와 함께 보인다. 기기 알림은 확인과 무관하게 그대로 울린다(결정 15).
- **확인**: `test/notify-guardian-push.test.js` '상태 조회는 앞 조회와 2분 미만이면 건너뛰고 force 면 보낸다'.

### 아이폰 홈 화면 앱에서 로그인 왕복이 돌아오지 않을 수 있다

- **증상**: (실기기 확인 전) 아이폰 홈 화면 앱에서 소셜 로그인을 마쳐도 홈 화면 앱이 로그인되지 않는다. 그러면 사본을 열 수 없고 '앱이
  닫혀 있어도 받기'도 켤 수 없다.
- **원인**: 홈 화면 앱은 Safari와 저장 공간이 따로다. 사본 가져오기, 계정 레코드 쓰기, 구독이 모두 로그인을 요구한다(결정 27).
- **대응**: 실기기에서 확인한다. 돌아오지 않으면 로그인 없는 사본 보관이 필요하고 별도 작업이다(질문 22 후속, `docs/tracking/status.md`
  '진행을 막는 것'). 클라이언트는 `config.guardianLoginRequired`를 읽어 두지만 A-3 동작은 이 값과 무관하다.
- **확인**: 실기기 확인 전이다.

### 서버 푸시의 대체 문구는 한국어와 영어 두 줄뿐이다

- **증상**: 일본어·중국어 보호자에게 한국어 줄과 영어 줄로 된 알림이 뜬다.
- **원인**: 서버 본문이 깨졌을 때(JSON 아님, `title`·`body`가 비었거나 너무 김) 서비스 워커가 대체 문구를 쓴다. 서비스 워커는 사전을 읽지
  않고, 어느 언어로 구독했는지도 모른다.
- **대응**: 받아들였다. 정상 본문은 서버가 구독 언어로 만든다. 대체 문구는 `notifications.serverPushFallback`의 한국어 줄과 영어 줄이다.
- **확인**: `test/pwa-sw.test.js` '대체 본문은 notifications.serverPushFallback 의 ko 줄과 en 줄이다'.

### 앱이 열린 채 사본이 만료되면 그 구독은 다음 앱 열기까지 기록에 남는다

- **증상**: 환자 출국일 23:59가 지났는데 보호자 기기의 구독 기록이 그대로이고 해지 대기에도 없다.
- **원인**: 사본 정리 뒤 구독을 대기로 옮기는 일은 앱을 열 때와 사본 하나를 지울 때 돈다. 사본 읽기는 화면 그리기 길이라 거기서 지우기를
  돌리지 않는다. 다시 맞추기는 쓰기 가능할 때만, 계기가 있을 때만 돈다.
- **대응**: 받아들였다. 그 사이 서버 지켜보기도 만료돼 푸시는 오지 않는다. 다음 앱 열기나 다시 맞추기가 대기로 옮긴다.
- **확인**: 시험으로 덮지 않는다.

### 링크 뒤에 붙은 `-`·`_`가 다른 암호문이 될 수 있다

- **증상**: 링크 바로 뒤에 `-`나 `_`가 붙은 글(PIN 없음)을 붙여 넣으면 링크를 받아들이지만 PIN이 늘 틀렸다고 나온다.
- **원인**: `-`와 `_`는 base64url 글자라 암호문의 일부로 읽힌다. `fragmentFromPasted`는 끝이 정규 base64url 끝(남는 비트 0)이 아니면
  거르므로 대부분 걸리지만, 길이 나머지 3 암호문 뒤의 하나나 나머지 2 암호문 뒤의 둘처럼 길이를 나머지 0으로 맞추면 다른 정규
  암호문이 되어 떼지 못한다. PIN을 이어 붙인 글(`링크-123450`, `링크__123456`)은 PIN 모양 숫자를 뗀 앞부분에서 끝의 `-`·`_`를 0개부터
  3개까지(`MAX_PIN_JOINERS`) 떼어 보고 정규 암호문이 나오면 PIN이 붙은 링크로 보아 받지 않는다(`endsWithPin`).
- **대응**: 받아들인 한계다. 링크만 다시 붙여 넣으면 된다. PIN 잠금은 암호문(SHA-256)마다 따로라 맞는 링크의 횟수를 쓰지 않는다.
  공백·줄바꿈을 건너 이어 붙이지 않는다.
- **확인**: `test/guardian-paste.test.js` '링크 바로 뒤에 붙은 - 와 _ 는 정규 끝 검사로 대부분 거른다(나머지 3 암호문은 알려진 한계)',
  '- · _ 로 이은 PIN: ...'.

### Playwright 기본 헤드리스 셸은 알림 권한을 줘도 `denied`라 알림이 뜨지 않는다

- **증상**: 화면 테스트에서 `context.grantPermissions(['notifications'])`를 줘도 `Notification.permission`이 `'denied'`이고, 서비스 워커가
  받은 푸시의 `showNotification`이 실패해 알림이 하나도 뜨지 않는다. 보호자 항목도 늘 '차단' 상태로 그려진다.
- **원인**: Playwright가 기본으로 띄우는 헤드리스 셸은 알림 권한을 붙이지 않는다(실측). 새 헤드리스 크롬(channel
  `'chromium'`)은 권한이 붙고, CDP `ServiceWorker.deliverPushMessage`로 보낸 푸시가 알림이 된다. channel은 describe 안에서 바꿀 수 없다
  (작업자를 새로 띄운다).
- **대응**: 화면 시험 대부분은 `stubPushApi`(`e2e/helpers.js`)로 `PushManager.prototype`과 `Notification`을 대신해 실행기가 진짜 호출 자리를
  타게 한다. 실제 푸시 수신을 보는 시험 하나(`e2e/guardian-push.spec.js` 'CDP 로 보낸 푸시가 tag 와 함께 알림 하나로 뜬다')만
  `playwright` 고정 장치로 새 헤드리스 크롬을 따로 띄우고, 기본 컨텍스트와 같은 감시(`guardContext`, `expectGuardClean`, 외부 요청 0건·위치
  요청 0건)를 건다.
- **확인**: `E2E_PORT=<빈 포트> npm run e2e -- e2e/guardian-push.spec.js`(빌드 먼저).

### 실제 오프라인(`context.setOffline`)에서는 끄기를 시험할 수 없다

- **증상**: 화면 테스트에서 `context.setOffline(true)` 뒤 '앱이 닫혀 있어도 받기'를 끄려 하면 스위치가 잠겨 있어 끄기 대기(`OFF_PENDING`)
  경로에 닿지 않는다.
- **원인**: 실제 오프라인은 저장소를 보기 전용(이유 오프라인)으로 만들고, 실행기는 쓰기 가능할 때만 끈다(`READ_ONLY`). 화면도 보기 전용이면
  스위치를 잠근다. 끄기 대기는 쓰기는 되는데 서버에 닿지 않는 경우(요청이 끊김)의 길이다.
- **대응**: 끄기 대기 시험은 가짜 서버의 `offline` 표시(`stubServerPush`의 `stub.set({ offline: true })`, 요청을 끊는다)로 연결 끊김을
  흉내 낸다. 다시 연결은 표시를 끈 뒤 `context.setOffline(true)`·`setOffline(false)`로 `online` 사건을 내어 대기의 해지를 보내게 한다.
  A-2의 'Playwright에서 오프라인으로 연 페이지는 다시 연결해도 online 사건이 오지 않는다'와 같은 가짜 서버 표시다.
- **확인**: `e2e/guardian-push.spec.js` '끄기는 DELETE { watchId, subId } 이고, 오프라인이면 대기에 남았다가 연결되면 보낸다'.
