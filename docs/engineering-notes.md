## 시간대 없는 시각 문자열이 실행 환경 시간대로 해석된다

- **증상**: 시간대가 한국이 아닌 환경(`TZ=America/New_York` 등)에서 일정 테스트가 무더기로 깨진다.
  같은 코드가 개발 기기에서는 통과한다.
- **원인**: `2026-09-21T09:00` 처럼 오프셋이 없는 문자열을 `Date.parse`가 **실행 환경의 지역 시간**으로
  읽는다. 이 제품의 모든 시각은 한국 표준시 기준이므로 해석이 통째로 어긋난다.
- **대응**: 시각 문자열을 밀리초로 바꿀 때는 오프셋이 없으면 `+09:00`을 붙인 뒤 파싱한다
  (`src/stay/time.js`의 파싱 함수가 이미 그렇게 한다). 날짜·시각을 직접 `new Date(...)`로 만들지 말고
  이 함수를 쓴다.
- **확인**: `TZ=America/New_York npm test`로 돌려 본다. 시간대 의존이 있으면 여기서 드러난다.

## 도심 택시 추정기로 공항 이동을 재면 4시간이 나온다

- **증상**: 입국일 일정이 저녁에야 시작되고, 출국일은 외출이 하나도 만들어지지 않는다.
- **원인**: 도심 이동 추정기는 정체를 감안한 낮은 평균 속도를 쓴다. 인천공항–강남처럼 50km가 넘는
  구간에 그대로 적용하면 240분대가 나온다. 실제로는 공항철도·고속도로로 1시간 안팎이다.
- **대응**: 공항 구간은 별도 추정기를 쓴다(우회 계수 1.3, 60km/h, 터미널 이동 15분). 이 값들은
  숫자 기본값 파일이 아니라 공항 모듈에 있고, 일반 이동 버퍼와 **더하지 않는다.**
- **확인**: 두 공항 각각에 대해 도심 숙소까지 80분대·40분대가 나오는지 본다. 세 자리 분이면 잘못된 것이다.

## 외부 응답 캐시 본문에 기준점 좌표가 남는다

- **증상**: 캐시 파일을 열면 요청에 쓴 숙소 좌표가 그대로 보인다. 파일 이름은 요청 해시라 안전해 보인다.
- **원인**: 응답을 저장할 때 요청 매개변수를 함께 넣어두면 디버깅은 편하지만, 그 매개변수에 기준점
  좌표가 들어 있다. 파일 이름만 해시로 가려도 본문이 그대로면 의미가 없다.
- **대응**: 저장 전에 매개변수에서 좌표를 지운다. 캐시에 넣는 값은 "나중에 이 파일이 유출돼도
  괜찮은가"를 기준으로 고른다.
- **확인**: 캐시를 만든 뒤 파일 안에 좌표 값이 없는지 단언하는 테스트가 있다. 새 캐시를 도입하면
  같은 모양의 테스트를 함께 만든다.

## 검증 명령 묶음이 취약점 점검에서 통째로 멈춘다

- **증상**: `npm run check`가 코드와 무관하게 실패한다. lint·test·build는 통과했는데 결과만 실패다.
- **원인**: 묶음의 마지막이 의존성 취약점 점검이고, 현재 잠금 파일에 해결되지 않은 권고가 남아 있다.
  고칠 방법이 없는 게 아니라 **지금은 잠금 파일을 바꾸지 않기로 한 상태**다. 묶음은 `&&`로 이어져
  있어 마지막이 실패하면 전체가 실패한다.
- **대응**: 코드 변경의 통과 여부를 볼 때는 `npm run lint`, `npm test`, `npm run build`를 따로 돌린다.
  묶음 실패를 "내 변경이 깨뜨렸다"로 읽지 않는다.
- **확인**: 실패 출력이 권고 목록이면 코드 문제가 아니다.

## 화면 테스트가 예전 빌드로 통과한다

- **증상**: 코드를 고쳤는데 화면 테스트가 그대로 통과한다. 또는 고치기 전의 오류가 계속 난다.
- **원인**: 화면 테스트는 빌드 결과를 **띄우기만** 한다. 앞서 빌드하는 단계가 없어서, 남아 있는
  예전 빌드 결과가 그대로 실행된다. 자동 검증 파이프라인은 빌드를 먼저 돌리므로 여기서는 드러나지 않는다.
- **대응**: 로컬에서 화면 테스트를 돌리기 전에 `npm run build`를 먼저 돌린다.
- **확인**: 통과가 의심스러우면 화면에 보이는 문구를 일부러 바꿔 빌드하지 않고 돌려 본다.
  그래도 통과하면 예전 빌드를 보고 있는 것이다.

## 숨은 디렉터리 안의 빌드 산출물까지 lint가 훑는다

- **증상**: 손대지 않은 파일에서 lint 오류가 수백 개 쏟아진다. 경로가 작업용 임시 디렉터리 안이다.
- **원인**: lint 설정의 무시 목록에 없는 디렉터리는 숨김이어도 훑는다. 그 안에 빌드 산출물이 있으면
  생성된 코드가 전부 검사 대상이 된다.
- **대응**: 저장소 안에 작업용·산출물용 디렉터리를 새로 만들면 lint 무시 목록에 함께 넣는다.
  무시 목록은 `eslint.config.mjs` 한곳이다.

## 화면 테스트가 외부를 부르지 않게 하는 방법

- 관광공사 응답은 캐시 씨앗 스크립트가 미리 심는다. 캐시가 적중하므로 키는 실제로 쓰이지 않지만,
  **키 검사를 통과해야 캐시까지 도달**하므로 가짜 키 값을 넣어둔다.
- 기상 조회는 키 값에 **공백 한 칸**(또는 `off`)을 넣어 끈다. 빈 문자열로 두면 관광공사 키로 대신
  시도하기 때문에 외부 호출이 나간다. 이 구분을 모르면 차단기가 걸린다.
- 네트워크 감시 모듈을 서버 프로세스에 미리 붙여 외부 요청을 실패로 만든다. 이미 떠 있는 서버를
  재사용하면 감시가 붙지 않으므로 테스트는 늘 서버를 새로 띄운다.
- 사용 통계 전송도 외부 호출이다. 끄는 환경변수가 설정에 들어 있다.

## 정거장 식별자는 날짜·역할·장소로 결정된다

- 정거장 id는 `날짜:역할:장소id` 형태다(역할은 환자/보호자). 무작위 id를 쓰면 같은 입력을 두 번 넣었을
  때 결과가 달라 보이고, 전후 비교가 "전부 바뀜"으로 나온다.
- 새로 만드는 식별자도 같은 원칙을 따른다 — **결정적으로** 만든다.

## 복귀 마감과 예상 귀가 시각은 다른 값이다

- 마감은 "이 시각까지는 돌아와야 한다"는 안전선이고, 예상 귀가는 "계획대로면 이 시각에 도착한다"는
  값이다. 화면에는 둘 다 보여준다.
- 모든 외출에서 예상 귀가 ≤ 마감이 성립해야 한다. 이 관계가 깨지면 계산이 잘못된 것이다.
- 마감만 보여주면 사용자는 마감 직전까지 놀아도 되는 줄 안다.

## 병원 일정 직전 외출의 블록 계산

- 마지막 외출이 병원에서 끝나는 경우, 병원 일정 블록은 **일정 시작 시각부터** 시작한다. 숙소→병원
  이동을 블록에 넣으면 외출의 마지막 구간과 이중으로 계산된다.
- 병원에서 끝나는 외출을 만들 수 없어 숙소로 돌아오는 경우에만 블록이 '시작 − 이동 − 도착 여유'부터다.
- 45분 최소 창은 이렇게 정해진 블록 시작까지로 잰다.

## 병원 복귀 외출은 마감이 곧 외출 끝이다

- **증상**: 즉시 복귀(경우 2)가 풀린 재계획에서 이미 출발한 병원 복귀 외출이 '돌아온 외출'로 남고, 그 시간 위에
  병원 외출이 하나 더 짜인다. 숙소 복귀 외출은 같은 상황에서 멀쩡하다.
- **원인**: `occupancyEnd`는 병원으로 돌아가는 외출이면 `returnBy`(마감), 숙소로 돌아가는 외출이면 `plannedReturnAt`
  (예상 귀가)을 쓴다. `overdueSafe`가 마감을 지금·출발 시각으로 당기면 병원 복귀 외출은 그 순간 외출 끝이 지나
  `repairDay`가 다시 검증하지 않는 기록(`done`)이 된다.
- **대응**: 마감을 당긴 외출을 다시 쓸 때는 `occupancyEnd`로 끝났는지 판단하지 말고 마감부터 다시 잰다
  (`tripPlan.js`의 `remeasure`). 남은 시간 일정(`freshFrom`)은 하루 정거장 한도를 모르고 짜므로, 환자 외출이
  `repairDay`에서 잘리면 보호자 몫 장소까지 비어 있을 수 있다. `planStructural`은 해제·다시 만들기·새로 짜기 모두에서
  지금 입력으로 만든 전체 하루(`fresh`)의 보호자 외출로 한 번 더 채운다(findings 9·14). 이 단계 때문에 `repairDay`가 두 번
  돌 수 있으니 기록은 `carryLog`로 새로 받아 끝에서 `mergeLog`로 합친다. 첫 결과의 기록을 그대로 쓰면 버린 대체·사유가 섞인다.
  다시 채우기는 외출을 통째로만 더한다. 같은 장소가 이미 쓰였으면(예: 교통 지연 사건으로 지금 입력의 오전 보호자 외출이
  다른 장소를 골라 저녁 외출과 장소가 엇갈림) 그 보호자 외출은 더하지 않는다.

## 보호자 링크 길이

- 스냅샷은 정규 JSON → 압축 → 인증 암호화 → base64url 순으로 만든다. 압축 전후 차이가 4배 가까이 난다.
- 현재 크기(2026-11-08, 7일 범위 규칙 뒤): 최악 크기 7일 링크가 체류 길이와 무관하게 약 6,450~6,490자(메신저 기준 8KB 안).
  규칙 전에는 14박 12,249자, 45박 33,966자였다. 스냅샷에 필드를 더하면 이 숫자가 바로 커진다. 필드를 더하기 전에 길이 측정 테스트를 돌려 본다.
- 7일 범위 규칙 전에 가져온 사본은 복호화·정규화 때 범위로 잘린다(만든 날 또는 그 뒤 첫 날짜부터 7일). 공개 전이라 영향은 무시할 만하다.

## 확인 대화상자가 닫힌 뒤 초점이 body로 떨어진다

- **증상**: 목록의 행을 지우거나 해제하거나 동의를 철회하는 확인 뒤, 초점이 화면 맨 앞(body)으로 간다.
  키보드 사용자는 다음 Tab이 화면 처음부터 다시 시작하고, 화면 읽기 사용자는 지금 어디인지 잃는다.
- **원인**: 확인 대화상자(`AlertDialog`)는 닫힐 때 열기 전에 초점이 있던 요소로 돌려보낸다. 확인한 일이
  그 요소를 DOM에서 지우면(지운 행의 삭제 버튼, 철회로 통째로 사라진 철회 블록) 돌려보낼 곳이 없다.
- **대응**: 살아남는 화면에서 `lib/useRefocusAfterDialog.js`를 쓴다. 초점을 받을 후보를 앞에서부터
  `useRefocusAfterDialog(() => [목록 제목, 입력칸])`으로 주고, 확인한 일이 성공한 직후 돌려받은
  `armRefocus()`를 부른다. 후보는 `tabIndex={-1}` 제목이나 입력칸이다. 사라지는 부품 안에서는 훅이 돌지
  않으므로 그 부품은 콜백(`ConsentWithdraw`의 `onWithdrawn`)으로 화면에 알리고, 훅은 화면이 가진다.
- **확인**: `e2e/focus-flows.spec.js`의 '확인 대화상자 뒤 초점'. 새 확인 대화상자를 만들면 확인 뒤
  `document.activeElement`가 body가 아니고 main 안인지 같은 모양으로 단언한다.
- **함께 걸리는 것(스크롤)**: 대화상자는 열 때 history 한 칸을 쌓고 닫을 때 `history.back()`으로 되돌린다
  (`lib/useModalSheet.js`). 그 popstate 뒤 브라우저가 스크롤을 대화상자를 연 자리로 되돌린다. 확인한 일로
  화면이 크게 줄면(동의 철회로 철회 블록이 통째로 사라짐) 초점을 받은 제목이 화면 밖에 남는다. 초점은 맞아도
  보이지 않는다. 보여야 할 것이 있으면 popstate 뒤 다음 그리기에서 `scrollIntoView`로 데려온다
  (조건 화면의 철회 완료 문구, `app/conditions/page.js`의 `handleWithdrawn`). 확인은 `toBeInViewport()`로 한다.

## 가로 flex 줄의 아이콘 칸이 0폭까지 줄어든다

- **증상**: 글자 옆 아이콘이 좁은 칸에서 찌그러지거나 아예 사라진다. 아이콘은 16px로 정했는데 잰 폭은
  6px, 0px이다. 넓은 화면에서는 보이지 않는다.
- **원인**: 전역 규칙 `svg { max-width: 100% }` 때문에 svg를 감싼 flex 항목의 최소 폭(min-content)이 0이다.
  flex 항목은 기본이 `flex-shrink: 1`이라 글자가 길면 감싼 칸이 0까지 밀려난다. `svg.ui-icon`에 준
  `flex: none`은 svg 자신에게만 걸려, 감싼 칸에는 닿지 않는다.
- **대응**: 아이콘을 감싼 칸(flex 항목)에 `flex: none`을 준다. 같은 줄에 글자가 있는 새 아이콘 칸은
  처음부터 준다. 이미 그렇게 한 곳: 앞 아이콘 칸 `.ui-list-item-leading`, 답 칩의
  체크 표시 `.ui-answer-mark`.
- **확인**: 가장 좁은 폭(320px)에서 언어별로 아이콘 칸의 `getBoundingClientRect().width`가 정한 크기와
  같은지 잰다. 답 칩의 체크 표시는 이제 모든 언어에서 `.ui-answer-mark { flex: none }`이다(운영자 결정 2026-10-30).
  넣을 자리가 모자라는 칸은 아이콘을 줄이지 말고 줄을 바꾼다: 답 칩은 `flex-wrap`으로 체크를 글자 위 줄로 올린다.
  이때 글자 칸에 `min-width: 0`을 주지 않는다. 글자 칸이 낱말 폭 밑으로 줄면 body 의 `overflow-wrap: break-word`가
  'Allowe/d'처럼 낱말을 꺾는다.

## 서버 알림 (ADR-0012)

아래는 서버 알림 기반(A-1)을 만들며 알게 된 것이다. 코드는 `src/push/`와 `lib/server/watch/`에 있다.

### 푸시가 조용히 버려진다

- **증상**: 푸시 서비스가 201로 받았는데 보호자 기기에 알림이 뜨지 않는다. 오류도 기록도 없다.
- **원인**: RFC 8291(aes128gcm)은 평문 끝에 구분 바이트를 붙여야 한다. 레코드가 하나뿐이면 마지막 레코드 표시 `0x02`다.
  빠지면 브라우저가 복호화 뒤 본문을 버리고 서비스 워커의 `push` 이벤트가 오지 않는다. 푸시 서비스는 본문을 풀지 않으므로
  서버 쪽에서는 성공으로 보인다.
- **대응**: `src/push/encrypt.js`가 평문 뒤에 `LAST_RECORD_DELIMITER`(`0x02`)를 붙인다. `0x01`(중간 레코드)은 쓰지 않는다.
  평문 상한 3993바이트는 이 1바이트를 빼고 센 값이다.
- **확인**: 단위 테스트가 RFC 8291 부록 A의 시험 벡터와 본문을 바이트 단위로 맞춘다. 구분 바이트가 빠지면 이 테스트가 깨진다.

### VAPID 개인키를 읽지 못한다

- **증상**: `generate-push-secrets.mjs`나 다른 도구로 만든 VAPID 개인키(base64url 32바이트)를 `createPrivateKey`에 넣으면
  형식 오류가 난다.
- **원인**: VAPID 개인키는 P-256 스칼라 원시 32바이트다. Node의 `createPrivateKey`는 PEM·DER·JWK만 받고 원시 스칼라는 받지 않는다.
- **대응**: 공개키(비압축 65바이트)의 x·y와 개인키 d를 JWK(`{ kty: 'EC', crv: 'P-256', x, y, d }`)로 묶어 들인다
  (`src/push/vapid.js`). 들이기 전에 `createECDH`로 개인키에서 공개키를 다시 만들어 짝이 맞는지 본다.
- **확인**: 단위 테스트가 짝이 아닌 개인키를 넣으면 `PUSH_VAPID` 오류이고 메시지에 키 값이 없는지 본다.

### 예약 처리가 같은 마감에 두 번 온다

- **증상**: 같은 마감의 예약 처리 요청이 두 번 들어온다(마감을 뺐다가 다시 넣은 뒤, 또는 QStash 재시도).
- **원인**: QStash의 `Upstash-Deduplication-Id`는 10분 창 안에서만 같은 id를 막는다. 게다가 취소한 메시지에도 그 창이 걸려,
  같은 id를 쓰면 다시 넣은 마감의 새 예약이 삼켜진다. 중복 제거 id만으로는 '한 번만'을 지킬 수 없다.
- **대응**: 중복 제거 id는 마감마다 같은 머리 뒤에 예약마다 다른 무작위 꼬리를 붙인다(보조 장치). 주 장치는 날짜 기록의
  `HSETNX p:<시각>` 권리다. 권리를 얻은 요청만 보내고, 나머지는 `SKIP_DUP`으로 끝난다. `a:<시각>` 표시는 같은 마감에 예약을
  두 번 걸지 않게 한다.
- **확인**: 예약 처리 테스트가 같은 예약을 차례로 두 번, 동시에 두 번 불러 한 번만 보내는지 본다.

### 미리보기에서 예약 처리 경로가 401이다

- **증상**: 미리보기 배포에서 QStash 콘솔에 `/api/watch/due` 배달 실패(401)가 쌓인다. 앱 기록에는 그 요청이 없다.
- **원인**: 미리보기 배포는 Vercel 배포 보호가 걸려 있어 앱에 닿기 전에 막힌다. QStash는 Vercel 로그인을 할 수 없다.
- **대응**: Vercel의 자동화 우회 비밀(`VERCEL_AUTOMATION_BYPASS_SECRET`)을 만들고, 예약을 걸 때 `Upstash-Forward-x-vercel-protection-bypass`
  헤더로 싣는다. QStash가 접두사를 떼고 `x-vercel-protection-bypass`로 전달한다. 직접 부를 때(curl)도 같은 헤더를 붙인다.
- **확인**: 미리보기에서 Bearer와 우회 헤더를 붙여 `/api/watch/due`를 부르면 401이 아니라 판정표의 결과가 나온다
  (`docs/operations.md` '서버 알림 켜기').

### 보낼 권리를 얻은 뒤 함수가 죽으면 그 알림은 나가지 않는다

- **증상**: 마감 지남 알림이 한 번도 나가지 않았는데 날짜 기록에는 `p:<시각>`이 남아 있고, 뒤이은 QStash 재시도는 모두 `SKIP_DUP`이다.
- **원인**: 보내기는 '많아야 한 번'이다. `HSETNX`로 권리(`'1'`, 보내는 중)를 얻은 뒤 함수가 시간 초과로 죽거나 저장소가 실패해
  표시를 지우지 못하면, 재시도는 권리를 얻지 못한다. 두 번 보내는 것보다 놓치는 쪽을 골랐다.
- **대응**: 받아들인 한계다. 보내지 못한 결과(구독 없음, 한도, 구독 만료, 거절, 다시 시도)는 표시를 지우므로, 남는 경우는 권리와
  표시 정리 사이에서 함수가 죽는 때뿐이다. 기기 알림(갈래 1)은 이와 별개로 동작한다.
- **확인**: 기록에는 마감 시각이 남지 않아 줄 하나로는 가릴 수 없다. `watch.due`의 `SKIP_DUP`이 평소보다 많고 함수 시간 초과가
  함께 보이면 이 경우를 의심한다.

### 마감을 뺐다가 다시 넣으면 다시 보낸다

- **증상**: 이미 마감 지남 알림이 나간 마감을 환자가 일정에서 뺐다가 다시 넣자 같은 알림이 한 번 더 온다.
- **원인**: 마감 목록에서 빠진 시각은 `c:`·`a:`·`p:`·`k:` 표시가 함께 지워진다(`replaceDays`). 다시 넣으면 새 마감으로 다룬다.
- **대응**: 의도한 동작이다. 다시 보내는 알림은 같은 `tag`(`sh-watch-<날짜>-<시각>`)와 같은 `Topic`을 실으므로 보호자 기기와
  푸시 서비스는 앞 알림을 갈아 끼운다. 알림이 두 줄로 쌓이지 않는다.
- **확인**: 문구 테스트가 `tag`를 `sh-watch-<날짜>-<시각>`으로 고정한다. Topic은 저장 키·날짜·시각의 HMAC이라 같은 마감이면 같다.

### 구독 만료(404·410) 뒤에 새 구독이 지워질 수 있는 짧은 틈

- **증상**: 보호자가 기기를 바꿔 다시 구독한 직후 새 구독이 사라진다(드물다).
- **원인**: 푸시 서비스가 404·410을 주면 구독을 지운다. 지우기 전에 지금 구독을 다시 읽어 `subId`가 보낸 것과 같을 때만 지우지만,
  읽기와 지우기는 별도 요청이라 그 사이에 새 구독이 들어오면 함께 지워진다.
- **대응**: 틈이 저장소 요청 두 번 사이로 짧아 받아들였다. 다시 읽은 구독의 `subId`가 다르면 지우지 않고 `RETRY`(statusClass
  `404/410`)로 끝낸다. 예약 처리는 걸림 표시를 남긴 채 권리만 돌려놓고 다시 불리며, 그때 새 구독으로 보낸다. 보호자 화면(A-3)은
  상태 조회의 `subscriptionActive`가 거짓이면 다시 구독하게 한다.
- **확인**: 테스트가 404·410을 받는 사이 새로 구독한 경우 새 구독을 지우지 않고, 다시 불린 예약 처리가 새 기기로 한 번만 보내는지
  본다(검토 N2). 다시 읽은 뒤 지우기 전의 틈은 테스트로 덮지 않는다.

### 어제 23:55 마감의 예약 실패는 00:55 전에 하루 1회 예약이 돌아야 살아난다

- **증상**: 23:55 마감의 예약을 거는 데 실패한 날, 보호자에게 알림이 가지 않는다.
- **원인**: 보낼 시각은 다음 날 00:05, 늦은 한도는 00:55다. 실패한 예약은 다음 업로드나 하루 1회 예약이 다시 거는데,
  하루 1회 예약은 00:10 KST에 잡혀 있고 Vercel Hobby는 실행 시각을 59분까지 흔든다. 01:00쯤 돌면 이미 늦은 한도가 지나 걸지 않는다.
- **대응**: 하루 1회 예약은 어제·오늘·내일 색인을 함께 본다. 그래도 00:55 전에 돌지 않으면 그 마감은 놓친다. 마감 올리기 응답의
  `armFailed`가 0보다 크면 환자 기기가 잠시 뒤 전체를 다시 올려(A-2) 이 틈을 줄인다.
- **확인**: Vercel Cron 기록에서 하루 1회 예약의 실행 시각을, 응답에서 `failed` 수를 본다.

### 00:01에 '오늘 함께 있음'을 켜도 어제 23:55 마감의 알림은 00:05에 나간다

- **증상**: 보호자가 자정 직후 '오늘 함께 있음'을 켰는데 5분 뒤 마감 지남 알림이 온다.
- **원인**: '오늘 함께 있음'은 오늘(KST) 날짜 기록에만 적힌다. 어제 23:55 마감은 어제 날짜 기록에 속하고 보낼 시각이 오늘 00:05다.
- **대응**: 받아들인 한계다. 날짜를 넘는 마감까지 끄려면 어제 기록도 건드려야 해 '오늘'의 뜻이 흐려진다. 보호자 화면(A-3)에서
  이 경우를 안내할지 정한다.
- **확인**: 예약 처리 테스트(자정 경계)가 어제 23:55 마감을 다음 날 00:05에 보내는지 본다. 함께 있음과 엮은 테스트는 아직 없다.

### 마감 올리기 둘이 겹치면 표시를 잃는다

- **증상**: 같은 지켜보기에 마감 올리기 둘이 겹치면 확인 표시가 사라지거나 날짜 하나가 통째로 빠진다.
- **원인**: `replaceDays`는 날짜 기록을 읽는 배치와 쓰는 배치, 두 번에 나눠 저장소를 부른다. 원자적이지 않아 겹친 업로드 사이에서
  늦게 쓴 쪽이 앞 쪽의 표시를 덮고, 늦게 쓴 쪽이 빈 목록이면 그 날짜 기록이 통째로 지워진다.
- **대응**: 클라이언트(A-2)는 지켜보기 하나에 업로드를 한 번에 하나만 보내고, 늘 가장 최근 상태 전체를 보낸다. 앞 업로드가
  끝나기 전에 바뀐 것은 끝난 뒤 다시 올린다.
- **확인**: A-2 화면 테스트에서 업로드 중 일정을 바꿔도 요청이 겹치지 않는지 본다.

### 보낸 직후 저장소가 실패하면 복귀 확인 알림이 나가지 않는다

- **증상**: 보호자는 마감 지남 알림을 받았는데, 환자가 '돌아왔어요'를 눌러도 복귀 확인 알림이 오지 않는다. 날짜 기록의
  `p:<시각>`이 `'s'`가 아니라 `'1'`로 남아 있다.
- **원인**: 푸시 서비스가 받은 뒤 `p:`를 `'s'`로 쓰고 날짜 기록을 다시 읽는 배치(`markSentAndReadDay`)가 저장소 장애로 실패했다.
  예약 처리는 이미 나간 알림이라 `SENT`로 끝내지만, `'돌아왔어요'`는 `'s'`일 때만 복귀 확인 알림을 보내고 `'1'`(보내는 중)은
  예약 처리에 맡긴다. 예약 처리는 이미 끝났으므로 아무도 보내지 않는다. 예약 걸기도 `'1'`인 시각은 다시 걸지 않는다.
- **대응**: 받아들인 한계다. 마감 지남 알림은 나갔고 확인은 기록됐다. 놓치는 것은 뒤따르는 복귀 확인 알림 하나이고, 보호자는
  상태 조회(`confirmed`)로 확인을 볼 수 있다. 그 마감은 다시 걸리지 않으므로 마감 지남 알림이 두 번 나가지는 않는다.
- **확인**: 예약 처리 테스트가 보낸 뒤 저장소가 실패해도 결과가 `SENT`인지 본다.

### 날짜 기록에 표시 하나만 남는 경우가 있다

- **증상**: 저장소에 마감 목록 없이 `p:<시각>` 또는 `a:<시각>` 필드 하나만 든 날짜 기록이 보인다.
- **원인**: 푸시를 보내는 사이 그 마감이 목록에서 빠졌거나 지켜보기가 지워졌다. 예약 처리의 권리 얻기(`HSETNX`)나 표시 쓰기가
  이미 지워진 해시에 필드 하나짜리 기록을 새로 만든다.
- **대응**: 받아들인 한계다. 그 기록에는 시각 표시 하나 말고 다른 내용이 없고, 쓸 때 만료(그 날짜 끝 + 1일)를 함께 걸므로
  날짜로부터 이틀 안에 저절로 사라진다. 예약 처리는 마감 목록이 비어 보이면 권리를 돌려놓고 `SKIP_CHANGED`로 끝낸다.
- **확인**: 해당 키의 TTL이 걸려 있는지(`TTL`이 -1이 아닌지) 본다.

### 하루 한도에 걸리거나 거절된 마감은 다시 걸리지 않는다

- **증상**: `SKIP_CAP` 또는 `SEND_REJECTED`로 끝난 마감은 환자가 다시 업로드하거나 보호자가 다시 구독해도 알림이 가지 않는다.
- **원인**: 이 둘은 예약 표시(`a:<시각>`)를 남긴다. 걸기는 `a:`가 있는 시각을 건너뛴다.
- **대응**: 의도한 동작이다. 지우면 업로드마다 다시 걸려 한도 초과나 거절을 되풀이하고 예약 업체 사용량만 늘어난다. 한도는
  지켜보기당 하루 20건이라 정상 사용에서는 닿지 않고, 거절은 구독이나 키 문제라 다시 걸어도 같은 결과다.
- **확인**: 기록에서 `watch.due`의 `SKIP_CAP`·`SEND_REJECTED` 수를 본다. 늘면 구독·VAPID 설정을 먼저 본다.

### 구독이 없으면 지난 마감이 업로드마다 다시 걸린다

- **증상**: 보호자가 아직 구독하지 않은 날, 같은 마감의 예약 처리가 업로드마다 `SKIP_NO_SUB`로 되풀이된다. QStash 사용량이
  평소보다 많다.
- **원인**: `SKIP_NO_SUB`는 예약 표시를 지운다. 나중에 구독하면 다시 걸 수 있게 하려는 것이다. 그래서 보낼 시각이 지난 마감도
  늦은 한도(마감 + 60분) 전이면 다음 업로드가 '지금'으로 다시 건다. '오늘 함께 있음'인 날은 걸기가 그 날짜를 통째로 건너뛰므로
  이 되풀이가 없다(함께 있음을 끄면 오늘을 다시 건다).
- **대응**: 받아들인 한계다. 되풀이는 늦은 한도까지(보낼 시각부터 50분)이고, 지켜보기당 하루 예약 발행 120건(`arm`)과 마감 올리기의
  횟수 제한(지켜보기당 시간당 60)이 위를 막는다. 클라이언트(A-2)는 일정이 바뀔 때만 업로드하므로 실제 횟수는 이보다 훨씬 적다.
- **확인**: QStash 콘솔의 하루 메시지 수가 무료 한도(하루 1,000건)에 가까워지면 `watch.deadlines` 기록 수를 본다.

### 예약 발행이 지켜보기당 하루 120건에서 멈춘다

- **증상**: 예약 업체 장애가 없는데 마감 올리기 응답의 `armFailed`가 0보다 큰 채로 이어지고, 그날 남은 마감에 알림이 가지 않는다.
- **원인**: 걸기는 예약 업체에 발행하기 직전마다 지켜보기의 하루 발행 횟수(`arm`, 120건)를 센다. 넘으면 그 마감과 이번 호출에서 그
  지켜보기의 남은 마감을 모두 `failed`로 세고 발행하지 않는다. 마감 목록을 바꿔 가며 계속 올려 예약 업체 사용량을 늘리는 요청을
  막는 장치다. 하루 창은 UTC 기준이라 09:00 KST에 새로 시작한다.
- **대응**: 의도한 동작이다. 정상 사용(하루 마감 10개 이하, 다시 걸기 몇 번)은 닿지 않는다. 코드에는 모든 지켜보기를 합친 전체
  상한이 없다. 지켜보기를 여럿 만드는 경우는 계정당 지켜보기 수(3)와 만들기 횟수 제한(시간당 10)이 막고, 그 위는 운영자가 예약
  업체·저장소의 월 비용 상한으로 막는다(ADR-0012 결정 20).
- **확인**: 테스트가 한 계정이 지켜보기 셋에 마감을 번갈아 올려도 지켜보기마다 120건을 넘지 않는지 본다(검토 B1). 운영에서는
  QStash 콘솔의 하루 메시지 수와 `watch.deadlines` 기록의 `failed` 수를 함께 본다.

### 걸림 표시를 지우는 순간 들어온 구독·함께 있음 끄기·마감 다시 넣기

- **증상**: 예약 처리가 `SKIP_NO_SUB`·`SUB_GONE`·`SKIP_MUTED`·`SKIP_CHANGED`로 끝났는데 `retry`가 참이라 QStash가 다시 부른다.
- **원인**: 이 넷은 걸림 표시(`a:`)를 지워 나중에 다시 걸 수 있게 한다. 그런데 구독, 함께 있음 끄기, 마감 다시 넣기는 먼저 쓰고
  그 뒤에 다시 걸기가 날짜 기록을 읽는다. 둘이 엇갈리면 다시 걸기는 아직 남은 `a:`를 보고 건너뛰고, 예약 처리는 그 뒤 `a:`를
  지운다. 아무도 다시 걸지 않아 알림을 놓친다.
- **대응**: 예약 처리는 `a:`를 지우는 `HDEL`과 이유 다시 읽기(구독은 `EXISTS`, 함께 있음·마감 목록은 `HGETALL`)를 한 배치로
  보낸다. 지운 뒤 이유가 사라졌으면 `retry: true`로 끝내 다시 불리고, 그때 보낸다. 반대쪽은 쓰기가 먼저, 다시 걸기의 읽기가
  나중이다. 이 순서 덕분에 어느 한쪽은 반드시 다른 쪽을 본다. 구독은 구독을 쓴 뒤에, 함께 있음 끄기는 `m`을 지운 뒤에 다시 건다.
  순서를 바꾸지 않는다. 권리(`p:`)를 쥔 뒤라면 `p:`도 같은 `HDEL`로 돌려놓는다(따로 지우면 그 사이 다시 걸기가 '보내는 중'을 보고
  건너뛴다). 구독은 남았는데 풀 수 없으면(봉인 키 설정 문제) `EXISTS`가 참이라 늦은 한도까지 다시 불린다. QStash 재시도 횟수와
  늦은 한도(`SKIP_LATE`)가 위를 막는다.
- **확인**: 테스트가 네 경우(검토 N2·N3·N4와 마감 다시 넣기)에서 다시 불린 예약 처리가 살아 있는 구독으로 한 번만 보내는지 본다.

### 다시 등록과 출국일 변경이 겹치면 한쪽 변경이 사라진다

- **증상**: 다시 등록으로 쓰기 토큰을 바꾼 직후, 새 토큰으로 보낸 요청이 `NOT_FOUND`이고 옛 토큰이 다시 통한다. 또는 다시 등록
  둘이 모두 `ok`였는데 토큰 하나만 통하고 등록 횟수는 하나만 늘었다.
- **원인**: 마감 올리기는 출국일이 바뀌면 앞에서 읽은 지켜보기 레코드에 출국일만 바꿔 통째로 쓴다. 그 사이 다시 등록이 쓰기 토큰을
  바꿨으면 옛 토큰으로 되돌린다(검토 N5). 다시 등록도 읽은 레코드로 통째로 쓰므로, 둘이 겹치면 늦게 쓴 쪽만 남는다(검토 N6).
- **대응**: 클라이언트(A-2)는 지켜보기 하나에 등록·출국일 변경을 한 번에 하나만 보내고, 앞 요청이 끝나기 전에는 다음을 보내지
  않는다. 한 기기가 보내는 요청이라 이 순서를 지키면 생기지 않아 저장소에 비교 후 쓰기를 들이지 않았다. 등록 횟수 상한(5)은 겹친
  등록을 하나로 세므로 느슨해질 수 있지만, 등록 횟수 제한(계정당 시간당 10)이 위를 막는다.
- **확인**: A-2 화면 테스트에서 등록 중 출국일을 바꿔도 요청이 겹치지 않는지 본다.

### 계정당 지켜보기 셋을 넘길 수 있다

- **증상**: 한 계정의 지켜보기가 3개(`maxWatchesPerOwner`)보다 많다.
- **원인**: 새 지켜보기를 만들 때 소유 집합을 세어 본 뒤 만든다. 세기와 만들기가 원자적이지 않아 같은 계정이 새 지켜보기를 동시에
  만들면 둘 다 세기를 통과한다.
- **대응**: 받아들인 한계다. 넘는 수는 만들기 횟수 제한(계정당 시간당 10)이 막는다. 만들기는 소유 집합에 먼저 넣고 그다음 지켜보기를
  만들므로, 응답을 잃어도 내 정보 전체 삭제가 찾아 지운다(검토 E2).
- **확인**: 저장소에서 소유 집합의 크기(`SCARD`)를 본다. 3을 넘는 계정이 잦으면 클라이언트가 등록을 겹쳐 보내는지 본다.

### 구독과 출국일 변경이 겹치면 구독이 옛 만료로 남을 수 있다

- **증상**: 출국일을 늘린 뒤 옛 출국일 + 7일이 지나자 보호자 구독이 사라진다(지켜보기는 남아 있다). 상태 조회의
  `subscriptionActive`가 거짓이다.
- **원인**: 구독 쓰기는 구독을 쓰는 같은 배치에서 지켜보기를 다시 읽고, 출국일이 달라졌으면 구독의 만료를 다시 맞춘다. 이 맞추기는
  따로 보내는 요청이라, 그 사이 출국일이 또 바뀌면 구독이 한 단계 옛 만료로 남는다.
- **대응**: 받아들인 한계다. 마감 올리기는 출국일이 같아도 매번 구독 만료를 다시 맞추므로(`touchExpiry`) 다음 업로드가 고친다.
  보호자 화면(A-3)은 `subscriptionActive`가 거짓이면 다시 구독하게 한다.
- **확인**: 테스트가 구독과 출국일 연장이 겹쳐도 구독이 늘어난 출국일까지 남는지(검토 E4), 만료 맞추기가 한 번 실패해도 다음
  업로드가 고치는지(검토 E1) 본다.

### 예약 처리 서명은 경로만 맞춰 보고 호스트는 보지 않는다

- **증상**: 서명 검증 코드가 서명의 `sub`(목적지 주소)에서 호스트를 무시한다. 다른 배포로 보낸 예약의 서명도 경로가 같으면 통과한다.
- **원인**: 미리보기 배포는 배포마다 호스트가 다르고, 운영도 사용자 도메인과 `vercel.app` 주소를 함께 쓴다. 호스트까지 맞추면
  기준 주소 설정 하나가 어긋날 때마다 모든 예약이 401이 된다.
- **대응**: 받아들인 한계다. 서명은 본문 SHA-256과 만료(`exp`)·`nbf`에 묶여 있어 본문을 바꿀 수 없다. 다른 환경으로 옮겨도 본문의
  저장 키는 그 환경의 소유 비밀로 만든 것이 아니고 저장소 접두사도 달라 `SKIP_NO_WATCH`로 끝난다. 운영과 미리보기의 QStash 서명
  키를 따로 두면 이 경로도 막힌다.
- **확인**: 서명 검증 테스트가 다른 경로의 서명을 거부하는지 본다.

### 테스트 안에서 stdout을 통째로 가로채면 실행기 보고가 섞인다

- **증상**: 처리기를 부르는 동안 `process.stdout.write`를 가로채 "기록 줄 말고는 아무것도 없다"를 단언하면, 처리기가 아무것도
  쓰지 않아도 알 수 없는 바이트 조각이 잡혀 시험이 실패한다.
- **원인**: `node --test`가 띄운 테스트 파일 프로세스는 같은 stdout에 실행기 보고(직렬화한 `test:start`·`test:pass` 등)를 쓴다.
  보고는 비동기로 흘러가므로 처리기의 `await` 사이에 끼어든다.
- **대응**: 출력 전체를 봐야 하는 시험은 실행기가 없는 별도 프로세스로 돌린다(`test/watch-routes-child.js`를 `spawnSync`로 띄우고
  stdout·stderr를 그대로 받는다. 부모가 쓸 값은 fd 3으로 받는다). 같은 프로세스 안에서는 기록 줄만 골라 모으고 나머지는 흘려보낸다.
- **확인**: 자식 스크립트를 직접 돌려(`node test/watch-routes-child.js 3>/dev/null`) 기록 줄만 나오는지 본다.

### 이 기계의 grep으로는 대시 검사가 늘 통과한다

- **증상**: 문서에 엠대시·엔대시를 넣었는데 `grep '\x{2013}\|\x{2014}'` 같은 검사가 아무것도 찾지 못한다.
- **원인**: 이 기계의 `grep`은 ugrep이다. 기본 문법에서 `\|`를 글자 그대로 읽어 '또는'이 되지 않는다. 그래서 예전 명령은 늘 통과했다.
- **대응**: perl로 검사한다. `git diff -U0 | grep '^+' | perl -CSD -ne 'print if /[\x{2013}\x{2014}]/'`의 결과가 없어야 한다.
- **확인**: 대시가 든 줄을 일부러 넣고 위 명령이 그 줄을 출력하는지 한 번 본다.
