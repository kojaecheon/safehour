## 1. 제품 정의

**서비스명:** SafeHour 세이프아워

**한 줄 정의:** 성형외과·피부과 수술 또는 시술을 받은 외국인 환자와 동반 보호자에게
**병원이 발행한 회복 지침**(제한조건·복귀 마감·병원 안내문)을 그대로 전달하고, 그 지침을
지킬 수 있을 때만 관광 선택지를 제공하며, 현장 변화가 생기면 코스를 축소·대체·중단하는
모바일 반응형 웹 서비스.

**지정과제:** 여행 중 날씨, 혼잡, 휴무, 진료시간 변경 등 실시간 변수 대응.

**제품 원칙:**
- 관광 추천보다 **안전한 미추천과 정시 복귀**를 우선한다.
- 병원이 판단하고 SafeHour는 **해석하지 않는다.** 채널 B의 문장을 파싱해 판정에 쓰는 것은 금지.
- 환자에게 조건을 **묻지 않는다.** 물으면 해석 부담이 환자에게 남는다.

## 3. 문제 정의

### D01-PRB001 환자가 한국어 안내문을 해석하고 판단하는 위치에 있다

- 대상: D01-UG001
- **문제 (재정의)**: 관광 추천이 부족한 것이 문제가 아니다. 병원은 금식·외출 제한·자외선
  회피·보행 한도·복귀 시각을 **종이나 구두로, 대개 한국어로** 안내하고, **환자가 그것을
  번역하고 해석해 스스로 판단해야 한다.** v1.0은 이 문제를 "조건을 반영한 관광 추천이
  없다"로 서술했는데, 그렇게 보면 해법이 "조건 입력 폼"이 되고 해석 부담은 그대로 환자에게
  남는다.
- 파생 문제: 옮겨 적다 틀리면 판정도 틀리고, 누가 언제 그렇게 판단했는지 기록이 남지 않는다.
- 심각도: 높음
- 빈도: 수술·시술 전후 외출을 고려할 때 반복
- 현재 대안: 숙소 대기, 병원 코디네이터에게 수동 문의, 일반 지도 검색
- 한계: 과도한 숙소 대기 또는 안전조건을 확인하지 않은 임의 관광
- **해법의 방향**: 병원이 발행하고 환자는 코드만 넣는다. 병원 조건은 읽기 전용이며
  사용자가 고칠 수 없다. 수기 입력 화면은 **남겨두지 않았다** — 남기면 이 결함이 그대로 남는다.
- 근거: `docs/PRODUCT_DEFINITION.md` §1·§9-3, `docs/PRD.md` Part 1 장면 1 / Part 2 PRB001,
  AX-221 (수기 입력 제거)
- 확인일: 2026-08-27
- Confidence: 높음 (문제 진술) · 중간 (해법이 실제 병원 운영에서 성립하는가는 미검증)

### D01-PRB002 실시간 변화가 생기면 기존 코스의 안전성이 깨진다

- 대상: D01-UG001, D01-UG002
- 문제: 휴무, 날씨 악화, 교통 급증, 진료시간 변경, 환자 호출이 발생해도 기존 추천은 그대로
  남아 사용자가 직접 재판단해야 한다.
- **v1.1 추가**: 병원 지침 자체가 바뀌는 경우가 생겼다 — 계획 만료·철회, 조건 변경,
  확인하지 않은 중요 변경. 이미 **나가 있는 사람**에게 "만료됐습니다"만 띄우면 위험하다.
- 심각도: 높음
- 현재 대안: 검색을 처음부터 반복하거나 관광을 포기
- 해법의 방향: 변화 시 1단계부터 재판정하고 전후 비교로 제거·대체·축소를 보여준다.
  외출 중 만료·철회는 세 시점(화면 진입·만료 타이머·탭 복귀)에서 감시한다 (AX-220).
- 근거: 지정과제 1, `docs/LIVE_SCENARIO_EVIDENCE.md`, `docs/PRODUCT_DEFINITION.md` §7
- Confidence: 높음

### D01-PRB003 보호자의 관광과 환자 안전을 함께 만족시키기 어렵다

- 대상: D01-UG002
- 문제: 보호자는 환자를 최우선으로 돌보지만 대기시간 전체를 숙소에서 보내기 어렵고,
  분리 가능한 거리와 복귀 마감을 판단할 기준이 없다.
- **v1.1 추가**: 정보 분리 문제가 함께 있다. 보호자에게 상세 진단·전체 시술 기록·전체
  약물 목록이 보여서는 안 되고, 이 축약은 **환자 앱이 받은 뒤 거르는 것이 아니라
  게이트웨이가 발행 단계에서** 해야 성립한다.
- 심각도: 중간 이상
- 근거: 사업계획 페르소나 정의, `docs/PRODUCT_DEFINITION.md` §6.2, `src/recovery/gateway.js`
- Confidence: 중간

### D01-PRB004 외국어·접근성 관광정보의 연결이 불완전하다

- 대상: D01-UG001, D01-UG002
- 문제: 국문·영문·무장애 데이터의 식별자와 콘텐츠 유형이 달라 잘못 연결하거나 번역이
  누락될 수 있다.
- 근거: 강남 3km 실API 분석에서 국문 후보 100건 중 영문 자동 연결 10건, 무장애 연결 27건
  (`docs/GANGNAM_DATA_ANALYSIS.md`)
- **v1.1 추가 — 더 아픈 자리**: 화면 전체는 한국어·영어를 지원하지만(ADR-0003),
  **병원 안내문 원문은 번역 대상이 아니다.** 병원이 한국어로만 발행하면 외국인 환자는
  한국어를 그대로 받는다. 해법은 앱의 자동번역이 아니라 병원의 다국어 발행이며,
  그것은 병원 파트너가 생긴 뒤의 일이다.
- **확인된 오역 1건**: `SPLIT_NEARBY` 상태의 한국어("보호자**만** 가능")와 영어
  ("Companion **may** take a nearby activity")가 의미가 다르다 — 영어는 환자 가부를
  말하지 않는다 (`docs/SIGNOFF_CHECKLIST.md` 5절)
- Confidence: 높음

### D01-JTBD001 환자의 안전한 짧은 외출

병원이 외출을 허용했을 때, 환자는 자신의 증상을 앱이 진단하게 하지 않고 **자기가 조건을
옮겨 적지도 않은 채로**, 병원이 발행한 조건과 복귀 마감 안에서 가능한 짧은 활동만 보고 싶다.
그래야 안전조건을 지키면서 숙소 대기 스트레스를 줄일 수 있다.

### D01-JTBD002 보호자의 근거리 분리 활동

환자가 쉬고 병원이 분리를 허용했을 때, 보호자는 환자 호출 시 즉시 돌아올 수 있는 근거리
활동을 찾고 싶다. 그래야 돌봄 책임을 유지하면서 자신의 체류 경험도 확보할 수 있다.

### D01-JTBD003 변화 발생 시 즉시 재판정

선택한 장소의 휴무, 날씨 악화, 진료시간 변경이 발생했을 때, 사용자는 검색을 다시 하지 않고
기존 조건으로 대체·축소·중단 결과와 이유를 받고 싶다.

### D01-JTBD004 지금 이 지침을 믿어도 되는지 알기 *(v1.1 신설)*

외출을 결정하기 전에, 사용자는 지금 보고 있는 것이 **어느 병원이 언제 발행한 몇 번째
버전이고 언제까지 유효한지**, 그리고 확인하지 않은 변경이 남았는지 알고 싶다. 그래야
"앱이 알아서 걸러줬겠지"가 아니라 근거를 보고 나갈 수 있다.

## 5. 성공 행동과 리텐션 트리거

### D01-SB001 병원 지침 연결 완료 *(v1.1 재정의)*

로그인 후 병원이 발행한 코드로 지침을 연결하고, 발행처·유효기간·버전이 화면에 표시된
상태에 도달한다. *(v1.0의 "조건 입력 완료"는 폐기)*

### D01-SB002 복귀 마감 준수

추천 활동을 선택한 사용자가 표시된 출발 마감과 복귀 마감을 준수한다. 복귀 마감은
**병원 복귀 시각·복약 시각·다음 진료 중 가장 이른 것**으로 정해진다.

### D01-SB003 변화 후 대체 행동

실시간 변수 발생 시 변경 이유를 확인하고 대체 코스 선택 또는 즉시 복귀를 실행한다.

### D01-SB004 병원 안내 확인 완료 *(v1.1 신설)*

확인하지 않은 **중요** 안내(활동·외출 / 동행 / 다음 진료 / 이상 상황 대응)를 읽고
확인 처리해 판정의 대기 강등을 해소한다.

### D01-RT001 세션 재진입

재진·처치·다음 날 외출 전, 병원이 지침을 갱신하거나 복귀 마감이 바뀌면 다시 판정한다.

### D01-RT002 병원 단위 반복 사용

병원이 후속 외국인 환자에게 동일한 발행 절차를 반복 사용한다.
*(v1.0의 "동일한 조건 입력·확인 흐름"에서 발행 흐름으로 재정의)*

## 6. 제품 성과 지표 후보

> 목표값은 **사람이 정한다.** 아래에서 목표가 비어 있는 항목은 임의로 채우지 않는다.

### KPI-01 유효 지침 기반 판정 성공률

- 산식: 정상 추천 또는 설명 가능한 미추천을 반환한 세션 ÷ 유효 지침이 연결된 세션
- **기준선 (2026-08-27 실행)**: 자동 테스트 **301건 / 72 suites 전부 통과**.
  브라우저 종단 테스트 93건 / 6파일은 문서 기준 2026-08-22 값
  *(v1.0의 "46개 자동 테스트" 기준선은 폐기)*
- 제품 목표 후보: 99% 이상
- 기간: 1차 심사 전 회귀 테스트
- Guardrail: 오류를 숨기기 위해 무조건 추천하면 실패

### KPI-02 지원 이벤트 재계산 가시 변화율

- 산식: 축소·대체·상태변경·취소 중 하나가 발생한 이벤트 ÷ 실제 결과 변경이 필요한 지원 이벤트
- 기준선: 휴무 실데이터 시연 100%
- 목표: 100%
- Guardrail: 알림만 표시되고 코스가 유지되면 출시 보류

### KPI-03 복귀 SLA 위반 건수

- 산식: SafeHour가 추천한 활동 때문에 병원 복귀 마감이 초과된 확인 사례 수
- 기준선: 현장 운영 데이터 없음
- 목표: 0건
- 중단 기준: 1건이라도 확인되면 관련 추천 규칙 즉시 비활성화 및 원인 검토

### KPI-04 영문 또는 명시적 폴백 표시율

- 산식: 영문 원문 또는 needsTranslation 상태가 명시된 노출 후보 ÷ 전체 노출 후보
- 목표: 100%
- Guardrail: 확인되지 않은 자동번역을 원문처럼 표시하지 않음
- **적용 범위 주의**: 이 지표는 **관광정보**에만 적용된다. 병원 안내문(채널 B)은
  번역 대상이 아니므로 이 지표로 관리하지 않는다

### KPI-05 사용자 완료율

- 산식: 지침 연결 후 결과 화면 도달 세션 ÷ 지침 연결 시작 세션
- 기준선·목표: \[확인필요\] 사용성 테스트 후 설정

### KPI-06 병원 지침 연결·확인 완료율 *(v1.1 신설)*

- 산식: 지침 연결 + 중요 안내 확인까지 완료한 세션 ÷ 연결 화면에 진입한 세션
- 측정 의도: PRB001의 해법이 실제로 작동하는지는 "환자가 코드 하나로 끝냈는가"로 드러난다
- 기준선·목표: \[확인필요\] 사용성 테스트 전까지 설정하지 않는다
- Guardrail: 확인 버튼을 형식적 클릭으로 만들어 완료율을 올리지 않는다
  (중요 4분류만 판정을 막는 현재 설계를 임의로 넓히거나 좁히지 않는다)

### KPI-07 연결 게이트 차단의 설명 가능성 *(v1.1 신설)*

- 산식: 사유 코드와 함께 차단된 세션 ÷ 연결 게이트가 차단한 전체 세션
- 측정 의도: "이유를 알 수 없는 차단"은 안전 방향이어도 신뢰를 깬다
  (유효기간 72시간 vs 조건 최신성 24시간 충돌 사례 — §11 참조)
- 기준선·목표: \[확인필요\]

## 7. 1차 범위

### 포함

- 모바일 반응형 웹 · 화면 9종 (`/` `/login` `/link` `/today` `/guide` `/plan` `/result`
  `/place/{id}` `/privacy`) · 내부 API 10종
- **병원이 발행한 회복 지침 연결** — 코드 입력, 발행처·버전·유효기간·확인 상태 표시
- **채널 A 제한조건 14종** — 외출 허용, 실내 한정, 최대 보행시간, 최대 편도 이동시간,
  자외선 제한, 열 노출 제한, 수중 활동 금지, 동행 필수, 분리 허용, 식음 제한,
  금식 종료 시각, 복귀 마감, 복약 시각 목록, 다음 진료 일시
- **채널 B 병원 안내문** — 7분류(활동·외출 / 복약 / 음식·음료 / 생활 / 동행 / 이상 상황 대응 /
  다음 진료) 읽기 전용 표시, 번역·요약·편집 없음
- **연결 게이트** — 지침 없음·만료·철회·미확인 중요 변경 시 관광지 미표시. 사유 코드 5종 추가
  (`NO_HOSPITAL_PLAN` `PLAN_EXPIRED` `PLAN_REVOKED` `PLAN_UNCONFIRMED_UPDATE` `MEDICATION_WINDOW`)
- **게이트웨이** — 허용목록 밖(진단명·시술기록·전체 약물목록) 차단, 보호자 축약 발행
- **소셜 로그인** (Google `openid` · Kakao 선택 동의 0개), 서버 회원 테이블 없이 서명 쿠키만
- **전 화면 한국어·영어**, 안전 문구는 두 언어 병기
- 지침에 담긴 기준점 · 국문·영문·무장애 TourAPI 실시간 후보 · 기상청 초단기실황
- 휴무·날씨·교통·진료시간 변경·환자 호출 재계산, 외출 중 만료·철회 감시
- 추천 3개(엔진 최대 5), 제외 이유, 복귀 마감과 그 사유, 출처 표시
- **병원 연동 데모 모드** — 비식별 계획 3종, 화면에 `병원 연동 데모` 배지 상시 표시

### 제외 (설계 판단)

- 앱의 증상 해석·회복일차 진단·의학적 외출 허가
- **채널 B 문장의 파싱·판정 활용** — 그것이 곧 재해석이다
- **병원 안내문의 번역·요약·편집**
- **약물명·진단명·시술기록 수신**
- 의료기관 목록·순위·추천·알선
- 사용자 현재 GPS 수집·전송 (`Permissions-Policy: geolocation=()` 로 브라우저 레벨 차단)
- **수기 조건 입력** — 폐기, 폴백으로도 남기지 않는다
- 지도·경로 사업자 연동 — **의도적 보류.** 위치정보 사전검토 회신(문의 2540) 대기 + 공급자·
  폴백·비용 미결. 기준점 좌표 복사로 대체
- 이미지 다운로드와 원천 관광정보 수정
- 확인되지 않은 영업 여부·실내 여부·접근성 단정
- 앱스토어 네이티브 앱

### 아직 없는 것 (미구현 — 제외가 아니다)

- 보호자 기기용 화면(`/share`) — 축약 함수만 있고 호출하는 곳도 볼 화면도 없다
- QR 카메라 스캔 — 문구로는 안내하지만 실제 입력 수단은 텍스트 코드 하나
- 계획 서명·위조 검증 — 계획이 판정 근거이므로 안전 요건인데 미결
- 병원 지침 **변경** 신호 → 재판정 배선 (만료·철회는 감시, 변경은 미연결)
- 판정 API 자체의 연결 게이트 — 화면 경로에는 걸려 있으나 API 직접 호출에는 없다
- 채널 A 중 **열 노출 제한·수중 활동 금지는 화면에 배지로만 뜨고 판정에 쓰이지 않는다.**
  금식 종료 시각은 조건 변환에 자리가 없다
- 복약 마감 사유 코드(`MEDICATION_WINDOW`)가 정의만 되고 어디서도 방출되지 않는다
- 병원용 발행 도구 화면

## 8. 통과·보완·중단 기준

### 통과

- 세 사용자 그룹과 네 문제의 근거가 사람 검토를 통과한다.
- 1차 기능이 문제·시나리오·KPI에 연결된다.
- KPI 산식과 안전 Guardrail이 승인된다.
- **채널 A 제한조건 14종 목록을 의료진이 "병원이 실제로 발행할 수 있는 범위"로 확인한다.**

### 보완

- 환자·보호자·병원 코디네이터 인터뷰가 0건이므로 정량 목표는 후보로 유지한다.
- 위치정보지원센터 문의번호 2540 답변을 D07에 반영한다.
- 실제 출발·복귀 현장 측정으로 이동 버퍼와 유형별 보행시간 상수를 보정한다.
- 안전 임계값 넷(조건 유효 24시간 · 최소 활동 45분 · 환자 가산 10분 · 교통 변동 25%)의
  임상 근거를 확보한다.
- 영문 안전 문구 검수 — `SPLIT_NEARBY` 오역이 확인됐다.

### 중단 또는 범위 축소

- 의료 판단 또는 의료기관 알선 없이는 핵심 가치 제공이 불가능하다고 판단되는 경우
- **병원 파트너를 확보하지 못해 지침 발행 주체가 성립하지 않는 경우** — 이 구조에서
  가장 큰 단일 리스크다
- 현 위치 서버 전송 없이 지정과제 시연이 불가능해지는 경우
- 복귀 SLA 위반 또는 위험한 추천이 재현되는 경우

## 11. 미해결 항목

### D01-UNRESOLVED-001 사용자 검증

- 질문: 환자와 보호자가 판정 결과를 신뢰하기 위해 반드시 확인해야 할 정보는 무엇인가?
- 확인된 사실: 병원 발행처·버전·유효기간, 복귀 마감과 그 사유, 거리, 실내 여부, 출처가 핵심 후보
- 미확정: 정보 우선순위와 문구
- **실제 환자·보호자·코디네이터 인터뷰 0건** — 세 페르소나의 Confidence가 전부 "중간"인 이유
- Blocking Level: design_blocker
- 담당자·기한: 기획 리드 · \[지정필요\] · 1차 사용성 테스트 전

### D01-UNRESOLVED-002 KPI 목표값

- 질문: 완료율·선택률·재사용률·연결 완료율(KPI-05·06·07)의 현실적 목표는 무엇인가?
- 임시 가정: 첫 사용성 테스트 결과를 기준선으로 사용
- Blocking Level: non_blocking
- 만료: G1 승인 전

### D01-UNRESOLVED-003 Project Key 승인

- 질문: project_key 후보 safehour를 공식 식별자로 승인할 것인가?
- 담당자: 프로젝트 오너, 플랫폼 오너 · \[지정필요\]
- Blocking Level: development_blocker

### D01-UNRESOLVED-004 병원 파트너 확보 *(v1.1 신설)*

- 질문: 회복 지침을 실제로 발행할 병원을 어디서 확보하는가?
- 확인된 사실: **연동 병원 0곳.** 현재 열리는 것은 비식별 데모 계획 3종뿐이다
- 종속: 채널 A 목록 검증, UG003의 실효성, 파일럿 전체가 여기 달려 있다
- Blocking Level: development_blocker (실환자 오픈 기준) · 공모전 제출 자체는 막지 않는다
- 담당자: \[지정필요\]

### D01-UNRESOLVED-005 채널 A 제한조건 목록의 의료진 확인 *(v1.1 신설)*

- 질문: 14종 제한조건이 병원이 실제로 발행할 수 있고 발행하려는 범위인가? 빠진 것은 없는가?
- 확인된 사실: 목록은 코드로 확정돼 있으나 **의료진이 검토한 기록이 없다**
- Blocking Level: development_blocker
- 담당자: 협력 병원 의료진 · \[지정필요\]

### D01-UNRESOLVED-006 안전 임계값의 임상 근거 *(v1.1 신설)*

- 질문: 조건 유효 24시간 · 최소 활동 45분 · 환자 가산 10분 · 교통 변동 25%를 누가 어떤
  근거로 승인하는가?
- 확인된 사실: 전부 설계값이며 임상 근거가 없다. 코드 주석 스스로 "현장 측정 후 보정 필요"
- 포함된 결함: **계획 유효기간 72시간과 조건 최신성 24시간이 충돌한다.** 30시간 전 발행된
  계획(유효기간 내)으로 판정하면 `STALE_HOSPITAL_CONDITION` 으로 막히는데, 사용자에게는
  "유효기간 내"로 보인다
- Blocking Level: development_blocker · 기능 동결 전 판정 필요
- 담당자: 자문 의사 · \[지정필요\]

### D01-UNRESOLVED-007 보호자 화면과 공유 범위 기본값 *(v1.1 신설)*

- 질문: 보호자 기기 화면(`/share`)을 어느 범위까지 만들고, 공유 기본값을 "공유 안 함"으로
  할 것인가? 환자가 보호자를 부르는 수단은 무엇인가?
- 확인된 사실: 축약 함수는 구현·테스트됐으나 호출하는 서버 경로도, 보호자가 볼 화면도 없다.
  "환자 호출"은 시스템이 받는 사건으로만 존재한다
- Blocking Level: design_blocker (PRB003의 해결이 여기 달려 있다)
- 담당자: \[지정필요\]

### D01-UNRESOLVED-008 민감정보 별도 동의 설계 *(v1.1 신설)*

- 질문: 채널 B(병원 안내문)를 화면에 표시하는 것만으로 건강정보 처리이므로 별도 동의가
  필요하다. 문구·시점·철회 방법을 어떻게 설계하는가?
- 확인된 사실: **"안 받으니 동의 불필요" 전략은 더 이상 쓸 수 없다.** 병원→앱 제공은
  제3자 제공이고, 보호자 공유는 다시 제3자 제공이다
- 부속 미결: 감사 기록 보관 주체(병원 보관으로 확정할지), `/privacy` 의 개인정보 보호책임자·
  문의처·분쟁관할 지정
- Blocking Level: development_blocker (실환자 오픈 기준)
- 담당자: 개인정보보호 담당자 · \[지정필요\]

### D01-UNRESOLVED-009 표시되지만 판정에 쓰이지 않는 조건 *(v1.1 신설)*

- 질문: 열 노출 제한·수중 활동 금지를 판정에 반영할 것인가, 화면에서 "표시 전용"으로
  구분할 것인가?
- 확인된 사실: 두 조건은 `/plan` 화면에 배지로 뜨지만 안전 게이트가 읽는 목록에 없다.
  병원이 "사우나·찜질 금지"를 발행해도 찜질방이 후보에서 빠지지 않는다
- 왜 중요한가: "병원이 허용한 것만 보여준다"가 제품의 주장이므로, 적용되지 않는 조건을
  적용되는 것처럼 보여주는 것은 아예 안 보여주는 것보다 나쁘다
- Blocking Level: development_blocker
- 담당자: \[지정필요\]
