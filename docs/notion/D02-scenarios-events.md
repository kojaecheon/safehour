## 1. 시나리오 지도

1. 로그인 (Google · Kakao) — "같은 계정이 다시 왔다"만 확인
2. **병원 발급 코드로 회복 지침 연결** — 게이트웨이가 허용 항목만 통과시킨다
3. 병원 안내(채널 B) 열람과 **중요 안내 확인**
4. 오늘의 회복 상태 확인 — 가능 / 대기 / 불가와 복귀 마감
5. **연결 게이트** 판정 (지침 유효성)
6. 현재 상황(동행·휴식) 선택 → TourAPI 실시간 후보 생성
7. 안전 게이트와 복귀 SLA 판정
8. 추천 3개 또는 설명 가능한 미추천 노출
9. 현장 변수·지침 변화 발생 시 유지·축소·대체·중단 재계산
10. 복귀 행동과 판정 운영 로그 기록

> 1~3단계가 이번 개정으로 새로 생긴 앞단이다. 4단계 이후는 기존 흐름이 그대로
> 살아 있으나, 입력의 출처가 사용자에서 병원으로 바뀌었다.

## 2. 사용자 시나리오

### D02-S001 환자·보호자 공동 초단거리 활동 (개정)

- 연결 사용자: D01-UG001, D01-UG002
- 해결 문제: D01-PRB001
- 목표: 병원이 발행한 제한조건과 복귀 마감 안에서 함께 가능한 실내·저부담 활동을 찾는다.
- 사전조건: 로그인 완료, **유효기간 내 병원 회복 지침이 연결됨**, 철회되지 않음,
  미확인 중요 안내 없음, `외출허용=true`, 필수 동행 충족
- Trigger: 사용자가 `/today`에서 "안전 외출 확인"을 선택
- 정상 흐름:
  1. 연결 게이트가 지침 유효성을 확인한다 (없음·만료·철회·미확인 중요 변경 아님).
  2. `/plan`이 **병원이 발행한 조건을 읽기 전용으로 표시한다.** 사용자는 고칠 수 없다.
  3. 사용자는 **지금 상황만** 고른다 — 보호자 동행 여부, 환자 휴식 여부, 보호자 분리 허용.
  4. 기준점은 병원 지침에 담겨 온 좌표를 쓴다. **사용자가 좌표를 고르지 않는다.**
  5. 복귀 마감은 복귀 시각·복약 시각·다음 진료 **셋 중 가장 이른 것**으로 계산된다.
  6. 시스템이 국문·영문·무장애 후보를 조회하고 정규화한다.
  7. 안전 게이트와 왕복 SLA를 통과한 상위 3개를 제시한다 (엔진 최대 5, 화면 3).
  8. 사용자는 제외 이유, 예상 이동·체류, 출발 마감, 마감 사유, 출처를 확인한다.
- 대체 흐름: 영문 원문이 없으면 국문 폴백과 "번역 필요" 배지를 표시한다.
- 실패 흐름:
  - 지침이 없거나 만료·철회면 **연결 게이트에서 NO_TOURISM** (관광지 자체를 표시하지 않는다).
  - 지침은 유효하나 조건이 상충하거나 오래됐으면 기존 안전 게이트가 NO_TOURISM을 낸다.
- 종료·후조건: 판정 상태·사유 코드·후보 수·조건 신선도 구간이 **판정 운영 로그**에 한 줄 남는다
  (D02-LOG001). 세션 감사기록은 서버에 저장하지 않는다.
- 중요도: Critical
- 채널: 모바일 반응형 웹 (한국어·영어)
- 성공 판정: D09-AC001, D09-AC002, D09-AC003
- 검증 질문: 사용자는 일반 관광 추천과 안전 판정의 차이를 이해하는가?
- 현재 상태: **구현됨.** 단, 이동시간이 직선거리 기반 추정치이고 장소별 보행시간이
  콘텐츠 유형별 상수다 (§7 UNRESOLVED-011)

### D02-S002 환자 휴식·보호자 근거리 분리 활동 (개정)

- 연결 사용자: D01-UG002
- 해결 문제: D01-PRB003
- 목표: 환자가 쉬는 동안 호출 시 돌아올 수 있는 보호자 코스를 찾는다.
- 사전조건: 연결 게이트 통과, 보호자 동행, 병원이 `분리허용=true`로 발행, `동행필수=false`
- Trigger: 보호자만 활동 모드 선택 — 또는 **환자 조건으로는 통과 후보가 하나도 없는 경우**
- 정상 흐름:
  1. 시스템이 SPLIT_NEARBY 가능 여부를 판단한다.
     세 조건이 모두 참일 때만 열린다 — 보호자 있음 · 병원이 분리 허용 · 필수 동행 아님.
  2. 보호자 기준 체류시간과 복귀 SLA로 후보를 다시 계산한다 (환자 가산 10분 미적용).
  3. 원터치 복귀 행동과 환자 호출 우선 안내를 함께 표시한다.
- 대체 흐름: 시간창이 짧으면 STANDBY와 병원 인근 대기를 제시한다.
- 실패 흐름: 필수 동행이거나 병원이 분리를 허용하지 않았으면 분리 추천을 생성하지 않고,
  **토글을 이유와 함께 잠근다** (숨기지 않는다).
- 성공 판정: D09-AC004, D09-AC005
- 검증 질문: 보호자는 환자 호출이 추천보다 우선한다는 점을 즉시 이해하는가?
- 현재 상태: **판정은 구현됨.** 보호자 **기기** 화면은 없다 — 지금 이 시나리오는
  환자 앱 안에서 보호자 몫의 코스를 계산하는 데까지다 (§7 UNRESOLVED-009)

### D02-S003 식음 제한·금식 상태 (개정)

- 연결 사용자: D01-UG001
- 해결 문제: D01-PRB001
- 사전조건: 병원이 **채널 A로** `식음제한=true` 또는 `금식종료=시각`을 발행
- 정상 흐름: 식음 후보를 제외하고 나머지 안전 후보를 판정한다. 제외 사유(`FASTING_REQUIRED`)를
  사용자에게 노출한다.
- 실패 흐름:
  - 앱이 금식 시작·종료시간을 스스로 결정하거나 음식 섭취를 허용하지 않는다.
  - **채널 B의 문장("매운 음식은 2주간 피하세요")을 파싱해 후보를 거르지 않는다.**
    그것은 재해석이며 금지다. 문장은 표시만 한다.
- 성공 판정: D09-AC006
- 검증 질문: 식음 후보가 모두 제외되고 그 이유가 노출되는가?
- 현재 상태: **부분.** `식음제한` 플래그는 판정에 쓰인다. `금식종료 시각`은 참·거짓으로만
  읽히고 **시각 자체는 판정에 쓰이지 않는다** — 금식이 끝나는 순간을 반영하지 못한다
  (§7 UNRESOLVED-007)

### D02-S004 외출 금지 또는 위험신호

- 연결 사용자: D01-UG001, D01-UG002
- Trigger: 병원이 `외출허용=false`로 발행 · 또는 위험신호(RISK_SIGNAL) 이벤트 수신
- 정상 결과: NO_TOURISM — **관광지가 하나도 나오지 않는다.** 조건을 완화해 추천을
  만드는 것은 금지돼 있다.
- 사용자 행동: 단일 액션이 "병원에 연락하세요"로 바뀐다. **액션은 사라지지 않고 성격만 바뀐다.**
- 금지: 증상 해석, 위험도 진단, 임의 관광 추천
- 성공 판정: D09-AC007
- 현재 상태: **구현됨** (데모 코드 `DEMO-B`가 이 경로를 보여준다)

### D02-S005 휴무·날씨 변화 후 코스 대체

- 연결 사용자: D01-UG001, D01-UG002
- 해결 문제: D01-PRB002
- 사전조건: 추천 코스가 존재
- Trigger: 1순위 장소 휴무(CLOSURE), 기상 악화(WEATHER), 혼잡·지연 상승(TRAFFIC_SURGE)
- 정상 흐름:
  1. 이벤트를 수신한다.
  2. **연결 게이트와 안전 게이트를 처음부터 다시 실행한다.** 기존 코스를 손보지 않는다.
  3. 부적합 후보를 제거한다.
  4. 다음 안전 후보를 대체 제시하거나 체류시간을 축소한다 (15분 미만으로는 줄이지 않는다).
  5. 변경 전후와 이유를 비교 표시한다.
- 대체 흐름: 대체 후보가 없으면 STANDBY 또는 NO_TOURISM으로 강등한다. 대체 장소가
  복귀 마감에 걸리면 **대체 자체가 취소된다.**
- 실패 흐름: 알림만 표시하고 기존 코스를 유지하는 것은 금지다.
- 후조건: `delta.hasVisibleChange=true`. 변화가 필요한데 보이는 변화가 없으면 출시 보류 사유다.
- 성공 판정: D09-AC008, D09-AC009
- 현재 상태: **재판정 로직은 구현됨.** 휴무·교통을 **자동 감지하는 실데이터 공급자가 없다** —
  기상만 기상청 실API가 붙어 있고 나머지는 시연에서 상황을 주입한다 (§7 UNRESOLVED-002)

### D02-S006 진료시간 변경·복약 마감·환자 호출 후 즉시 복귀 (개정)

- Trigger: 진료시간 앞당김(APPOINTMENT), 복약 시각 도래, 환자 또는 병원의 복귀 요청(PATIENT_RECALL)
- 정상 흐름:
  1. **복귀 마감은 세 후보 중 가장 이른 것이다** — 병원 복귀 시각 · 복약 시각 · 다음 진료.
     화면은 어느 것이 마감을 정했는지 한 줄로 붙인다 ("복약 시각이 더 이릅니다").
  2. 진료시간이 바뀌면 마감을 갱신하고 SLA를 재계산한다.
  3. 체류 축소로 가능하면 새 마감을 표시한다.
  4. 불가능하거나 환자 호출이면 관광을 중단하고 즉시 복귀를 켠다.
- 금지: 약물명·용법을 받는 것. **시각 하나면 마감을 계산할 수 있다.**
- 성공 판정: D09-AC010, D09-AC011
- 현재 상태: **구현됨.** 환자 호출 시 추천 전량 무효화에는 끌 수 있는 스위치가 없다.
  다만 복약 때문에 마감이 앞당겨졌다는 **사유 코드(`MEDICATION_WINDOW`)가 정의만 되고
  어디서도 내보내지지 않는다** — 화면 문구로는 보이므로 사용자가 정보를 잃지는 않으나
  판정 기록에는 남지 않는다 (§7 UNRESOLVED-008)

### D02-S007 외부 API 실패와 안전한 폴백

- Trigger: TourAPI·기상 API 오류, 429, timeout, 빈 결과
- 정상 흐름: 최소 캐시 또는 보수적 이동시간 폴백을 적용하고 **불확실성을 화면에 표시한다**
  ("추정", "영업 확인 필요").
- 실패 흐름: 안전 판정 입력을 확보할 수 없으면 추천하지 않는다.
- 성공 판정: D09-AC012
- 연결 예외: D06-E003, D06-E004, D06-E005, D06-E010
- 현재 상태: **구현됨.** 오퍼레이션별 800회 경고 · 1,000회 차단 · 캐시 15분.
  지도·경로 API는 **의도적으로 연동하지 않았다** (위치정보 사전검토 회신 대기)

### D02-S008 병원 회복 지침 연결 (신규)

- 연결 사용자: D01-UG001, D01-UG002
- 해결 문제: D01-PRB001 — **환자가 한국어 안내문을 해석하는 위치에 놓이는 것**
- 목표: 환자가 조건을 옮겨 적지 않고, 병원이 발행한 것을 그대로 받는다.
- 사전조건: 병원이 회복 지침을 발행하고 연결 코드를 환자에게 전달
- Trigger: `/` 또는 `/today`에서 "병원 연결하기" 선택
- 정상 흐름:
  1. **로그인을 요구한다.** 코드만으로 열면 코드가 유출됐을 때 누구나 남의 지침을 본다.
  2. 사용자가 병원에서 받은 코드를 입력한다 (`/link`).
  3. **게이트웨이가 허용 목록 밖을 잘라낸다** — 계획 최상위 12개, 발행처 2개, 기준점 3개,
     제한조건 14개, 안내 6개. 진단명·전체 약물목록은 관문 밖에서 떨어진다.
  4. 형식 검증을 통과하면 계획을 내주고, 어긋나면 **계획 자체를 내주지 않는다.**
  5. 계획은 **단말에만 보관**된다. 채널 B(안내문)는 판정 요청에 실리지 않는다.
  6. 화면이 발행 병원·역할·유효기간·`병원 연동 데모` 배지를 표시한다.
- 대체 흐름: 알 수 없는 코드 → "이 코드로 연결된 회복 지침을 찾지 못했습니다" (404).
  형식 불량 → "회복 지침 형식이 올바르지 않아 연결하지 않았습니다" (422).
- 실패 흐름: 로그인하지 않으면 연결이 진행되지 않는다 (401).
- 종료·후조건: 이후 모든 판정은 이 지침을 근거로 한다. 지침이 없으면 §D02-S010의 차단 경로.
- 중요도: Critical
- 성공 판정: [확인필요] — D09에 연결 흐름 인수조건이 아직 없다
- 검증 질문: 사용자는 "로그인 = 계정 확인"과 "코드 = 본인 확인"이 다른 층위임을 이해하는가?
- 현재 상태: **구현됨. 단, 실제 병원 파트너는 0곳이다.** 지금 열리는 것은 비식별 데모 계획
  3종(`DEMO-A` 정상 · `DEMO-B` 외출 제한 · `DEMO-C` 만료)이며 화면에 데모 배지를 상시 띄운다.
  **QR 카메라 스캔은 없다** — 문구로는 QR을 안내하지만 실제 입력 수단은 텍스트 코드뿐이다.
  **계획 서명·위조 검증도 없다** (§7 UNRESOLVED-005)

### D02-S009 병원 안내 확인 — 미확인 시 대기 강등 (신규)

- 연결 사용자: D01-UG001, D01-UG002
- 해결 문제: D01-PRB002 — 병원이 조건을 바꿨는데 사용자가 모르는 상태로 나가는 것
- 목표: 확인 버튼이 형식적 클릭이 되지 않으면서도, 사소한 안내가 외출을 막지 않게 한다.
- 사전조건: 지침 연결됨, 확인하지 않은 안내가 있음
- Trigger: `/today`가 "확인하지 않은 병원 안내 N건"을 표시 → `/guide` 진입
- 정상 흐름:
  1. 병원 안내를 **일곱 갈래**로 표시한다 — 활동·외출 / 복약 / 음식·음료 / 생활 /
     동행 / 이상 상황 대응 / 다음 진료.
  2. 각 카드에 "병원에서 제공한 안내" 배지와 발행 시각을 붙인다.
  3. **번역·요약·편집하지 않는다.** 원문 언어를 표기만 하고 그대로 출력한다.
     카드를 위 일곱 분류로 묶는 것은 배치이지 문장 변경이 아니다.
  4. 사용자가 "확인했습니다"를 누르면 그 안내의 확인 상태가 바뀐다.
- 대체 흐름: **일곱 중 넷만 판정을 막는다** — 활동·외출, 동행, 다음 진료, 이상 상황 대응.
  나머지 셋(복약·음식·생활)은 미확인이어도 외출을 막지 않는다.
- 실패 흐름: 중요 분류에 미확인이 남아 있으면 연결 게이트가 판정을 **STANDBY로 강등**한다
  (차단이 아니다 — 읽으면 풀린다). 사유 코드 `PLAN_UNCONFIRMED_UPDATE`.
- 종료·후조건: 확인 상태는 단말에 남고, 판정 요청에는 "확인했는가"만 실린다.
  **안내문 본문은 실리지 않으며, 섞여 들어오면 계약 위반으로 거부된다.**
- 중요도: Critical
- 성공 판정: [확인필요] — D09에 확인 게이트 인수조건이 아직 없다
- 검증 질문: 사용자는 "대기" 상태가 자기 행동(확인)으로 풀린다는 것을 아는가?
- 현재 상태: **구현됨.** 다만 **병원 원문은 번역하지 않으므로**, 병원이 한국어로만
  발행하면 외국인 환자는 한국어를 그대로 받는다 (§7 UNRESOLVED-010)

### D02-S010 지침 없음·만료·철회 — 외출 중 포함 (신규)

- 연결 사용자: D01-UG001, D01-UG002
- 해결 문제: D01-PRB001, D01-PRB002
- 목표: 근거 없는 추천을 만들지 않고, **이미 나가 있는 사람을 안전하게 되돌린다.**
- Trigger (넷):
  - 연결된 지침이 없음 → `NO_HOSPITAL_PLAN`
  - 유효기간 경과 → `PLAN_EXPIRED`
  - 병원이 철회 → `PLAN_REVOKED`
  - 미확인 중요 변경 → `PLAN_UNCONFIRMED_UPDATE` (강등, §S009)
- 정상 흐름 (외출 전):
  1. 연결 게이트가 판정 이전에 차단한다.
  2. **관광지를 아예 표시하지 않는다.** 후보 조회조차 하지 않는다.
  3. 상태에 맞는 단일 액션을 남긴다 — 불가 → "병원에 연락하세요", 대기 → "병원 안내 확인하기".
- 정상 흐름 (외출 중):
  1. **세 시점에서 지침을 다시 확인한다** — 화면 진입 시, 만료 타이머 발동 시,
     탭 복귀(visibilitychange) 시.
  2. 만료·철회를 감지하면 **추천을 비우고 즉시 복귀 시트를 자동 표시한다.**
     환자 호출(PATIENT_RECALL)과 같은 모양이다.
  3. 시연용 상황 주입 패널도 함께 차단한다.
  4. 미확인 중요 변경은 **외출을 중단시키지 않는다** — 강등일 뿐 무효화가 아니다.
- 실패 흐름: 만료를 알리기만 하고 코스를 유지하는 것은 금지다.
- 종료·후조건: 즉시 복귀 안내는 안드로이드 뒤로가기로 벗어날 수 없다 (시트만 닫힌다).
- 중요도: Critical
- 성공 판정: [확인필요] — D09-AC013(PATIENT_RECALL)과 같은 계열의 인수조건 신설 필요
- 검증 질문: 밖에 나가 있는 사용자가 만료 시 무엇을 해야 하는지 5초 안에 아는가?
- 현재 상태: **화면 경로는 구현됨 (AX-220).** 그러나 **연결 게이트가 판정 API 자체에는
  걸려 있지 않다** — 화면을 따라가는 사용자는 막히지만 API를 직접 호출하면 만료된
  지침으로도 추천이 나온다 (§7 UNRESOLVED-004). 그리고 **병원이 조건을 바꿨다는 신호와
  재판정 파이프라인의 배선이 아직 없다** — 만료·철회만 감시한다 (§7 UNRESOLVED-006)

### D02-S011 병원이 허용범위 밖 정보를 보냈을 때 (신규)

- 연결 사용자: 병원(D01-UG003 · [확인필요] — D01의 병원 사용자 그룹 ID 확인 필요)
- 해결 문제: D01-PRB001 — 민감정보를 앱이 보유하면 재해석 경계가 무너진다
- 목표: **받지 않은 것은 지킬 필요가 없다.**
- Trigger: 병원 시스템이 진단명·시술기록·전체 약물목록을 함께 실어 보냄
- 정상 흐름:
  1. 게이트웨이가 허용 목록에 없는 키를 **통과시키지 않는다.**
  2. 통과한 결과에 형식 검증을 적용한다.
  3. 새 필드를 통과시키려면 목록에 명시적으로 추가해야 한다 — 조용히 새지 않는다.
- 실패 흐름: 형식이 어긋나면 계획 자체를 내주지 않는다. 부분 통과는 없다.
- 금지: 다 받아놓고 화면에서 거르는 방식. 그 경우 데이터는 이미 넘어온 것이라
  "안 받는다"는 약속이 성립하지 않는다. **보호자 축약도 같은 이유로 게이트웨이가 한다.**
- 중요도: Critical
- 성공 판정: [확인필요]
- 검증 질문: 병원 담당자는 "보내도 안 들어간다"를 발행 단계에서 이해하는가?
- 현재 상태: **최소화·축약 함수 모두 구현됨.** 다만 **보호자 축약 함수는 아직 아무도
  부르지 않는다** — 테스트에서만 실행된다 (§7 UNRESOLVED-009)

### D02-S012 영어권 사용자의 진입과 안전 문구 (신규)

- 연결 사용자: D01-UG001 (외국인 환자)
- 해결 문제: D01-PRB004
- 목표: 대상 사용자가 **조작 없이** 자기 언어로 제품을 읽는다.
- 정상 흐름:
  1. 언어 결정 순서 — 세션 저장값 → 브라우저 언어 → 한국어.
     **한국어 태그만 한국어로 좁히고 나머지는 전부 영어로 본다.**
  2. 전 화면(9종)이 사전을 통해 렌더된다.
  3. **상태 배너와 즉시 복귀 시트는 두 언어를 함께 표시한다** — 환자와 보호자의
     언어가 다를 수 있다.
  4. 언어는 서버로 보내지 않는다. 판정은 언어와 무관하다.
  5. 관광 원문은 번역하지 않고 원문 언어를 `lang`으로 표기한다. 영문이 없으면
     국문 폴백에 "번역 필요" 배지.
- 실패 흐름: 검증되지 않은 자동번역을 안전 지시로 내보내지 않는다.
- 성공 판정: D09-AC016, D09-AC019
- 검증 질문: 영어 사용자가 "미추천"을 오류가 아니라 안전 결과로 읽는가?
- 현재 상태: **구현됨. 그러나 영문 안전 문구 검수는 0건이다.** 확인된 오역이 있다 —
  `SPLIT_NEARBY`의 한국어는 "보호자**만**"이라는 배타인데 영어는 허가로만 읽혀
  환자 가부를 말하지 않는다 (§7 UNRESOLVED-012)

## 3. 계측 — 판정 운영 로그 (ADR-0002 선택지 B)

> **범위 변경 (2026-08-11 · ADR-0002 승인).**
> 사용자 행동 계측은 **구현하지 않는다.** D02-EVT001–EVT007은 **2차 범위로 이동**하며
> 문서에서 삭제하지 않는다 (§3.2). 대신 D07 4절이 감사 증적으로 이미 요구하던
> **판정 결과 운영 로그**를 만든다.
>
> 판단 기준: SafeHour가 증명할 것은 사용자 참여도가 아니라 **안전 판정이 실제로
> 작동한다는 것**이다.

> 🔐 현재 GPS, 병원 원문, 건강 상세정보, 이름·연락처는 어떤 기록에도 넣지 않는다.
> 좌표는 기록하지 않는다 — TourAPI 호출 로그의 `mapX`/`mapY`도 `REDACTED`로 가린다.

### 3.1 D02-LOG001 판정 운영 로그 (1차 범위 · 구현 완료)

- 목적: 판정이 어떤 상태·사유로 나왔는지 남겨 **위험 추천 0건을 증명**하고,
  D07-POL001(의료 판단 경계)의 위반 탐지 수단인 "런타임 reason code 검사"를 성립시킨다.
- 성격: **운영 로그.** 되읽지 않는 쓰기 전용 기록이며 분석 동의와 분리된다.
- 발생 조건: 판정 API(`/api/recommend`) 및 재판정 API(`/api/recalculate`) 처리 종료
- 기록 위치: **stdout 한 줄(JSON).** 파일·DB·외부 분석 도구를 새로 만들지 않는다 —
  저장소를 두는 순간 보존 정책(AX-104)이 선행 조건이 되고, 서버리스에서는 인스턴스마다
  흩어져 어차피 정밀 집계되지 않는다.
- 남기는 필드:

| 필드 | 내용 |
| --- | --- |
| `evt` `route` | `decision` · `recommend`/`recalculate` |
| `outcome` | `DECIDED`(미추천 포함) · `PAUSED`(kill switch) · `FAILED`(입력 확보 실패) |
| `state` `reasons` | 4상태와 **닫힌 enum을 통과한 사유 코드만** |
| `courseCount` `excludedCount` `excludedReasons` `candidateCount` | 개수와 사유만 |
| `conditionAge` | 발행시각 **원값 대신 구간** — FRESH / RECENT / AGING / STALE / FUTURE / UNKNOWN |
| `trigger` | 재판정 트리거 (허용 6종 밖은 `UNKNOWN`) |
| `stateBefore` `visibleChange` `removedCount` `addedCount` `shortenedCount` | 재판정 전후 |
| `errorCode` | `SAFEHOUR_*` 형식만. 외부 오류 원문은 넣지 않는다 |
| `engine` `ms` | 엔진 버전, 소요시간 |

- **남기지 않는 것**: 좌표, 병원 조건 원문, 조건 발행시각 원값, 장소 이름·주소,
  session 식별자, `condition.version`, 인증키, 외부 URL, 외부 오류 원문.
- 설계 원칙: **allowlist.** 호출자가 무엇을 넘기든 조립 함수가 만든 필드만 나간다.
  엔진이 새 필드를 반환해도 로그는 따라 커지지 않는다.
- 실패 처리: 로그 실패가 요청 처리를 막지 않는다. 관측 때문에 사용자가 추천을
  못 받는 일은 없어야 한다.
- 연결: D07 4절(감사 증적), D07-POL001, D07-POL008, D02-S001–S012
- 검증: `test/decision-log.test.js` — 개인정보를 잔뜩 담은 요청을 넣고 로그 출력에
  그 값들이 하나도 나타나지 않음을 단언한다. 필드를 늘릴 때 이 테스트가 먼저 막는다.

#### 사유 코드는 "건강 상세"인가 — 열린 판단

`FASTING_REQUIRED`·`OUTING_FORBIDDEN`·`RISK_SIGNAL`·`PATIENT_RECALLED`는 환자 상태를
어느 정도 드러낸다. 그럼에도 남기는 이유는 셋이다 — ① POL001이 이것을 위반 탐지
수단으로 지정했다 ② 조건 값이나 원문이 아니라 **판정이 어느 규칙에서 멈췄는지를
가리키는 코드 하나**로 가장 거친 표현이다 ③ session 식별자도 조건 버전도 남기지 않아
**요청 간에 이어붙일 수 없다.**

**개인정보 담당자 확인이 필요한 항목이다** · [확인필요] (`SIGNOFF_CHECKLIST` 2번 영역).
받아들여지지 않으면 차단 사유를 단일 코드(`BLOCKED`)로 뭉개는 선택지가 있고,
그 경우 POL001의 탐지 정밀도가 떨어진다는 대가를 함께 기록한다.

### 3.2 D02-EVT001–EVT007 — 2차 범위 (미구현)

아래 7종은 **설계를 그대로 보존한다.** 실사용자 트래픽이 생기면 그대로 쓸 수 있고,
그때는 동의 UI·처리방침·보존 정책이 어차피 필요하다. **지금은 구현하지 않는다.**

| ID | 이벤트 | 목적 | 2차 범위에서 갱신할 것 |

| D02-EVT001 | `plan_input_submitted` | 유효한 판정 입력 제출 측정 | **이름·property 재정의 필요.** "입력 제출"이 더 이상 없다 — `plan_linked`(지침 연결)로 바뀌어야 한다. `condition_version` → `plan_id`+`plan_version` |

## 4. 로그·이벤트 품질 계약

### 4.1 판정 운영 로그 (1차 범위)

- 사유 코드: **닫힌 enum 통과분만.** 자유 문자열은 버린다
- 조건 신선도: 원값 금지, 구간만
- 개수 필드: 배열이 아니면 0
- Timestamp: 플랫폼이 부여한 수신 시각을 쓴다. 우리가 시각을 따로 넣지 않는다
- 순서 검증: 없음 — session 식별자를 남기지 않으므로 요청 간 연결이 성립하지 않는다.
  **이것은 결함이 아니라 설계다**
- Guardrail: 재판정에서 변화가 필요한데 `visibleChange=false`이면 D07-BAN008 위반 신호
- 보존기간: **플랫폼 기본값을 따른다.** 우리가 저장소를 운영하지 않으므로 보존 주체는
  배포 플랫폼이다 — 확인만 하면 된다 (AX-104) · [확인필요]
- Dashboard: **별도 대시보드를 만들지 않는다.** AX-201은 "플랫폼 로그 조회 절차"로 축소됐다
- Consent: 필요 없다 — 서비스 제공·감사에 필요한 운영 로그이므로 선택 분석 동의와 분리된다

### 4.2 D02-EVT001–EVT007 (2차 범위 · 구현 시 적용)

- event_version: 최초 v1
- Timestamp: 서버 수신 ISO 8601과 클라이언트 발생 시각을 분리
- 중복 제거: event_id UUID와 session_id + sequence
- 순서 검증: linked → decided → presented → optional recalculated
- 누락 경고: `recommendation_decided` 이후 10초 안에 `recommendation_presented`가 없으면 관측 경고
- Dashboard: 판정 퍼널, 상태 분포, 재계산 변화율, API 성공률
- Consent: 필수 서비스 로그와 선택 분석 로그 분리 — **구현 시점에 동의 UI가 선행 조건**

### D02-UNRESOLVED-010 병원 원문 번역 부재 — 대상 사용자에게 남은 가장 큰 불편 (신규)
- 사실: 화면 문구는 한국어·영어를 지원하지만 **병원 안내문 원문은 번역하지 않는다.**
  병원이 한국어로만 발행하면 외국인 환자는 한국어를 그대로 받는다.
- 왜 이 선택인가: 검증 없는 자동번역을 안전 지시로 내보내지 않기 위해서다.
  해결책은 앱의 번역이 아니라 **병원이 다국어로 발행하는 것**이다 — 병원 파트너가
  생긴 뒤의 일이다.
- Blocking Level: design_blocker (제품 목적에 직결)
- Owner: [지정필요]

### D02-UNRESOLVED-011 이동·보행 추정치의 근거 (신규)
- 사실: 이동시간이 실제 도로 경로가 아니라 **직선거리 기반 보수적 추정치**이고,
  병원이 발행한 보행 한도와 비교되는 **장소별 보행시간은 실측값이 아니라 콘텐츠
  유형별 상수**다.
- 왜 문제인가: 병원 조건은 정확한데 그것을 대는 자가 거칠다. 현장 측정으로 이 상수를
  교정하는 것이 남은 일 중 **안전에 가장 직접 닿는다.**
- 함께 열린 것: 안전 임계값 넷(조건 유효 24시간·최소 활동 45분·환자 가산 10분·
  교통 변동 25%)이 **임상 승인 0건**이고, 계획 유효기간 72시간과 조건 최신성 24시간이
  충돌한다 (25~72시간 구간에서 이유 없이 차단됨)
- Blocking Level: release_blocker
- Owner: 의료 자문 · [지정필요]

### D02-UNRESOLVED-012 영문 안전 문구 미검수 (신규)
- 사실: 전 화면 영문이 생겼으나 **검수 0건**이다. 확인된 오역이 있다 —
  `SPLIT_NEARBY`의 한국어 "보호자**만** 근거리 활동이 가능합니다"는 배타이고,
  영어 "Companion may take a nearby activity"는 허가일 뿐 환자 가부를 말하지 않는다.
  외국인 환자가 같이 나갈 수 있다.
- Blocking Level: release_blocker
- Owner: 콘텐츠·다국어 검수자 · [지정필요]

### D02-UNRESOLVED-013 신규 시나리오의 인수조건이 없다 (신규)
- 사실: D02-S008~S012는 D09에 대응하는 인수조건(AC)이 없다. 기존 AC001–AC020은
  수기 입력 구조를 전제로 쓰였다.
- 필요한 것: 연결·확인 게이트·외출 중 만료·게이트웨이 최소화에 대한 AC 신설,
  그리고 D09의 자동 테스트 수 갱신 (현재 **301건 / 72 suites 통과**)
- Blocking Level: design_blocker
- Owner: [지정필요]
