# 보안 정책

## 무엇을 지키나

이 제품에는 서버 데이터베이스가 없다. 지켜야 할 자산은 **사용자 기기 안의 데이터**와 **경계를 넘는
순간의 데이터**다.

| 자산 | 어디에 있나 | 위험 |
| --- | --- | --- |
| 조건 기간 값(식이·복약·보행·동행 등) | 기기 저장소. 판정 요청에 실려 서버 메모리를 스쳐 지나간다 | 건강 관련 민감정보. 로그·캐시·외부 전송에 남으면 안 된다 |
| 숙소·병원 좌표와 주소 | 기기 저장소. 좌표만 서버로 간다 | 체류 장소가 드러난다. 지도 사업자·관광공사 캐시에 남으면 안 된다 |
| 병원 안내문 원문 | 기기 저장소(연동 사본) | 의료 정보. 서버·로그·번역 대상이 되면 안 된다 |
| 보호자 스냅샷 | 링크의 URL 조각 안. 보호자 기기에 사본 | 링크가 메신저에 남는다. 우연히 열리면 안 된다 |
| 계정 식별자 | 어디에도 저장하지 않는다 | 저장하면 기기 데이터와 실제 계정이 연결된다 |
| 외부 API 키 | 서버 환경변수 | 클라이언트 번들·로그·URL에 새면 안 된다 |

## 인증

모든 기능에 로그인이 필요하다. 수단은 구글(`openid` 범위만)과 카카오(선택 동의 0개)다. 이메일·프로필을
요청하지 않는다 — 안 쓸 정보를 받으면 그 순간부터 지켜야 할 자산이 된다.

**흐름과 각 단계의 실패 경로**

1. 로그인 시작 — 서버가 PKCE 검증값과 상태값을 만들어 짧은 수명 쿠키에 넣고 제공자로 보낸다.
   - 세션 서명 키가 없거나 32자 미만이면 **로그인 기능 자체가 꺼진다**. 약한 키로 서명한 쿠키를
     발급하는 것보다 로그인을 막는 쪽이 낫다.
   - 콜백 주소는 요청 헤더가 아니라 **설정된 배포 도메인 값**으로 조립한다. 헤더로 만들면 호스트 헤더
     주입으로 인가 코드를 남의 주소로 보낼 수 있다.
2. 콜백 — 상태값이 쿠키와 일치하지 않으면 거부한다. 인가 코드 교환이 실패하면 로그인 화면으로
   되돌리고 제공자의 오류 원문은 사용자에게 그대로 보여주지 않는다.
3. 세션 발급 — 제공자 토큰은 **저장하지 않고 즉시 버린다.** 서버가 만드는 것은 서명 쿠키 하나뿐이고
   수명은 12시간이다. 회복기 사용자가 하루에 여러 번 열어도 재로그인이 잦지 않을 길이로 잡았다.
4. 세션 검증 — 서명이 맞지 않거나 만료됐으면 로그인하지 않은 것으로 본다. 라우트는 401과
   `SAFEHOUR_AUTH_REQUIRED`를 돌려준다.
5. 로그아웃 — 쿠키를 지운다. 기기 데이터는 지우지 않는다(그건 '내 정보 지우기'의 일이다).
   오프라인에서 '내 정보 지우기'를 눌렀으면 로그아웃 요청이 서버에 닿지 못한 표시를 기기에 남기고,
   그 표시가 있는 동안에는 세션이 남아 있어도 **로그인 상태로 보지 않는다.** 온라인이 되면 다시 보낸다.

데모 로그인 경로는 환경변수가 정확히 `1`일 때만 열린다. 운영에서 켜면 인증이 무의미해진다.

## 권한

사용자 데이터가 기기에만 있으므로 서버 판정은 **요청자 자신에게만 영향을 준다.** 남의 데이터를
읽거나 고칠 경로가 없다. 그래서 권한 모델은 단순하다.

| 주체 | 할 수 있는 것 | 조건 | 명시적으로 할 수 없는 것 |
| --- | --- | --- | --- |
| 로그인하지 않은 방문자 | 시작 화면, 로그인, 개인정보 고지, 긴급 연락 | — | 판정 요청, 주소 검색, 지침 연결, 장소 상세 조회 |
| 로그인이 만료된 기기 주인 | 긴급 연락, 한국어 카드, 오늘·내일 일정과 복귀 마감, 보호자 사본 안전 정보 — **보기 전용** | 이 기기에 마지막으로 로그인한 계정의 사본이 있을 때 | 생성·편집·연동·공유 |
| 로그인한 기기 주인 | 전부 | 세션 유효 | 다른 계정 이름공간 접근(키를 모른다) |
| 보호자 | 스냅샷 사본 보기 | 로그인 + 올바른 PIN + 만료 전 | 환자 조건·병원 정보 열람(스냅샷에 없다) |

보기 전용 상태에서는 화면에 '보기 전용 — 로그인이 필요합니다'를 표시한다(오프라인이면 로그인 문제가 아니므로
'인터넷 연결 없음, 저장된 일정만 보여 줘요'를 표시하고 로그인 링크를 두지 않는다). 조용히 읽기 전용으로
만들면 사용자는 편집이 저장된 줄 안다. 보호자가 받은 링크를 여는 화면(`/g`)은 이 배너 대신 막힌 일마다 그 자리에서
이유를 말한다(링크 열기의 로그인·오프라인 안내, 알림 스위치의 안내와 로그인 버튼). 이 화면에서 쓰는 일은 그 둘뿐이다.

## 기기 저장소와 계정 이름공간

브라우저 영구 저장소를 쓰고 키는 전부 `safehour.v2.` 아래에 둔다.

- 계정 데이터: `safehour.v2.<계정 키>.<항목>`
- 기기 기록: `safehour.v2.device.<항목>` (언어, 마지막 로그인 계정 키, 로그아웃 미전송 표시)
- 탭 임시 보관: `safehour.v2.tab.<항목>`

**계정 키는 불투명하다.** 서버 비밀값으로 계정 식별자에서 유도한 값이고, 되돌릴 수 없으며, 원래 식별자는
어디에도 저장하지 않는다. 기기 저장소를 통째로 보더라도 그게 누구 것인지 알 수 없다.

탭 단위 저장소(`sessionStorage`)에 데이터를 두는 것은 **한 가지 경우**뿐이다 — 보호자 링크를 로그인하지
않은 채 열었을 때, 로그인 왕복 동안 URL 조각의 암호문을 임시 보관한다. 가져오기가 끝나거나 1시간이
지나면 지운다. 암호문 외에는 아무것도 담지 않는다.

그 밖에 탭 저장소를 쓰는 곳이 한 군데 더 있다: '내 정보 지우기' 직후 화면에 안내를 한 번 띄우기 위한
표시(`safehour.cleared`)다. 값은 `1` 하나이고 처음 읽을 때 지워지며 사용자 데이터가 아니다. 다만
`safehour.v2.` 접두사 밖에 있어 일괄 삭제가 닿지 않는다 — **새 표시를 이런 식으로 늘리지 않는다.**

계정 데이터 중 `overdueSeen`은 이미 낸 마감 지남 알림의 id와, 닫은 경우 1 시트의 `외출 id@복귀 마감 시각`만 담는다
(각각 최대 50개). 마감 시각은 기기의 일정(tripPlan)에 이미 있는 값이라 새로 드러나는 정보가 아니다. 날짜(KST)가 바뀌면 지우고, '이 기기에서 내 정보 지우기'와 체류 삭제 대상이다.
장소 이름·주소·사본 id는 담지 않는다.

'이 기기에서 내 정보 지우기'는 `safehour.v2.` 아래 영구 저장 키를 **언어만 빼고 전부** 지우고
로그아웃한다. 새 저장 항목을 이 접두사 아래 두면 자동으로 삭제 대상이 된다.

## 민감정보 동의

첫 본인 체크 입력 전, 또는 병원 연동 전에 **반드시** 받는다. 동의 문구 버전과 동의 시각을 기기에
저장하고, 화면에 '동의 문구 법무 검토 전' 배지를 표시한다.

거부하면 경계일 전 자유일 일정만 쓸 수 있다. 철회하면 본인 체크 기간과 연동 지침 사본을 지우고,
해당 날짜를 `NEEDS_INPUT`(`SENSITIVE_CONSENT_REQUIRED`)으로 만든 뒤 재계획한다.

보호자 공유 동의는 **링크를 만들 때마다** 받는다. 한 번 받아두고 재사용하지 않는다.

## 보호자 링크

- 환자가 정한 6자리 PIN에서 키를 유도한다: PBKDF2-HMAC-SHA256, 무작위 salt 16바이트, 반복 600,000회.
  반복 횟수는 널리 쓰이는 암호 저장 권고값을 따른다.
- 인증 암호화는 AES-GCM 256비트, 무작위 IV 12바이트, 태그 128비트다.
- 암호문은 링크의 `#` 뒤에만 담는다. 브라우저는 조각을 서버 요청에 싣지 않으므로 **서버는 암호문을
  받지도 저장하지도 않는다.** 경로·쿼리에 실린 값은 암호문으로 받아들이지 않는다.
- 평문은 `형식 표지 1바이트 + 정규 JSON`이고, 쓸 수 있으면 표준 `CompressionStream('deflate-raw')`로
  **암호화 전에** 압축한다(표지 0x01, 못 쓰면 0x00 그대로). 압축 해제는 5 MB에서 멈춘다.
- 링크는 입국일과 만든 날(KST) 중 늦은 날부터 **7일**만 담는다(출국일에서 멈춤). 담는 날짜를 줄이면 링크 길이가 체류 길이와
  무관해지고(7일 최악 크기 6,490자, 메신저 기준 8 KB 안), 보호자 기기에 놓이는 장소·시각도 7일어치로 준다.
  복호화 뒤 정규화도 같은 규칙(만든 날보다 이른 날짜를 버리고 남은 가장 이른 날부터 7일)을 스냅샷 자신의
  날짜·만든 시각으로 다시 적용해, 손으로 늘린 사본도 7일을 넘지 못한다. 범위는 새 필드 없이
  `days[].date`에서 읽는다. 그 뒤 일정은 환자가 새 링크로 보낸다.
- 암호문 길이로 알 수 있는 것은 담긴 날짜 수와 일정의 대략적인 양뿐이다(압축률은 정거장 이름·주소 같은
  표시 문자열에 따라 달라진다). 조건 값은 평문에 아예 없으므로 길이로도 드러나지 않는다.
- PIN이 5회 연속 틀리면 그 기기에서 그 링크를 1시간 잠근다.
- 6자리 PIN은 완벽한 보호가 아니라 **우연한 열람을 막는 수준**이다. 이 한계를 화면에 그대로 밝힌다.
- PIN은 링크와 따로 전달하라고 안내한다.

## 병원 데이터

지침은 게이트웨이의 **허용 목록**을 지난 필드만 들어온다. 목록 밖 필드는 버린다. 형식이 어긋나면
지침 전체를 거부한다 — 일부만 받아들이면 어떤 값이 적용됐는지 알 수 없다.

병원 안내문은 **표시 전용**이다. 번역·요약·편집하지 않고 판정 입력으로 쓰지 않는다. 안내문 원문을
서버로 보내지 않고 로그·테스트 데이터에도 남기지 않는다.

## 기록

**남기는 것**

- 판정 한 번에 stdout 한 줄: 엔진 버전, 요청 날짜 수, 상태별 날짜 수, 사유 코드 집합,
  출처 종류별 개수, 언어, 경로·결과 구분, 자체 오류 코드, 처리 시간, 관광공사 실패 분류(`upstream`).
- 관광공사 조회 실패의 서버 오류 줄은 `[itinerary.plan] candidate load failed: SAFEHOUR_EXTERNAL_API upstream=<분류>`
  모양이다. 분류는 닫힌 목록(`SELF_LIMIT` `QUOTA` `AUTH` `UPSTREAM_ERROR` `PARSE` `NETWORK`, 모르면 `UNKNOWN`)의
  문자열뿐이라 키·URL·외부 오류 원문이 들어갈 자리가 없다. 같은 값이 502 응답의 `upstream`과 호출 기록 줄에도 실린다.
  허용 목록(`src/tour-api/upstream.js`) 밖 값은 응답·판정 로그에서 버린다.
- `GET /api/health`는 오늘 operation별 자체 호출 횟수와 한도를 알린다. 카운터 파일의 operation 이름과
  숫자만 내보내고 키·URL·매개변수는 담지 않는다.
- 관광공사 호출 기록과 응답 캐시는 파일로 남는다(서버가 파일을 쓰도록 지정한 경로 아래).
  호출 기록의 좌표 매개변수는 지워서 쓰고, 캐시 본문에도 기준점 좌표를 남기지 않는다.
  하루 호출 한도를 세기 위해 필요한 기록이고, 사용자 데이터는 들어가지 않는다.

**남기지 않는 것** — 좌표, 날짜, 장소 이름, 주소, 조건 값, 계정 키, 병원 정보, 기간·숙소 id,
외부 오류 원문·URL·키. 사용자 행동도 기록하지 않는다.

로그 줄은 **조립 함수가 만든 필드만** 내보낸다. 호출자가 무엇을 넘기든, 엔진이 새 필드를 반환하든,
요청 본문이 커지든 로그는 따라 커지지 않는다. 파일이나 데이터베이스를 만들지 않는 것도 의도다.

## 비밀값

API 키는 서버에서만 읽는다. Gemini 키는 헤더로만 보내고 URL에 넣지 않는다 — URL은 중간 기록에 남는다.
전체 조회 URL을 로그·문서·테스트 데이터에 남기지 않는다(키가 질의 문자열에 들어 있다).

`NEXT_PUBLIC_`으로 시작하는 값은 **빌드 때 번들에 새겨지는 공개 값**이다. 비밀값을 여기에 두지 않는다.
현재 이 접두사를 쓰는 것은 일본어·중국어 안전 문구 검수 스위치 둘뿐이고, 바꾸려면 다시 빌드해야 한다.

## 위치 정보

현재 위치를 **수집하지 않는다.** 위치 권한을 요청하는 코드가 하나도 없어야 하고, 모든 화면에서 권한
요청이 0건임을 테스트로 고정한다. 기준점은 사용자가 직접 고른 숙소·병원 고정 좌표뿐이다.

지도 링크에는 목적지 이름과 좌표만 넣는다. 출발지 매개변수를 넣으면 숙소 좌표가 지도 사업자에게 간다.

## 미래 범위

병원 측 감사 기록, 지침 서명·위조 검증, 서버 계정 저장은 아직 없다. 실제 병원과 연동하거나 기기 간
동기화를 붙일 때 필요하다. 서버 저장을 도입하면 이 문서의 '무엇을 지키나'가 통째로 바뀐다 —
지금은 지킬 서버 자산이 없다는 것이 이 모델의 전제다.
