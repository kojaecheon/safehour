# SafeHour PRD — 설계 결정

- 설계 승인: 2026-08-19 · 작성 완료: 2026-08-24
- 산출물: `docs/PRD.md` (저장소) + 노션 `03. SAFEHOUR` 하위 페이지
- 상태: 완료

> **중간에 한 번 갈아엎었다.** 이 설계를 승인받은 뒤 초안을 완성했는데, 그것을
> **3주 묵은 브랜치를 근거로 썼다.** 그 사이 제품이 "환자가 조건을 입력하는 앱"에서
> "병원이 지침을 발행하는 플랫폼"으로 바뀌어 있었고, 초안은 한 세대 전 제품을
> 서술하고 있었다. 구조(서사 뼈대 + 페인포인트 색인, 빈틈 갈래별 분리, 페르소나는
> 가정)는 그대로 두고 사실만 전부 새로 썼다.
>
> 아래 「근거를 무엇으로 삼는가」의 수치는 그 초안 시점(옛 브랜치)의 것이다.
> 최종 수치는 `docs/PRD.md` Part 3 에 있다 — 테스트 295건, E2E 93건, 커버리지 96.62%.
> 기록으로 남겨 둔다.

## 무엇을 만드는가

SafeHour의 **공모전 심사위원용 PRD**. 기획 정본 D01–D09를 사람 언어로 옮기되,
페인포인트를 축으로 "지금 어떻게 푸는가 / 아직 못 푸는 것은 무엇인가"를 나란히 적는다.

## 왜 이 문서가 따로 필요한가

이미 사업계획서 초안(v0.9, 626문단)이 있다. 그것은 **평가 배점**
(안전 30 / 기술 25 / 사업 20 / 현장 15 / 확산 10) 순서로 짜여 있다. 점수를 받기엔
좋은 구조지만, 그 칸막이 때문에 **사용자 한 명의 이야기가 다섯 조각으로 흩어진다.**

PRD는 배점이 아니라 **사람**을 축으로 삼아 그 자리를 메운다. 사업계획서와 겹치는
시장 통계·배점 대응은 넣지 않고 참조만 건다.

## 결정한 것

### 1. 주 독자 — 공모전 심사위원

2026-09-21 제출이 코앞이라 가장 값이 크다. 개발·협업자용이 아니므로 요구사항 명세보다
"왜 이 문제가 진짜이고 이 해법이 최적인가"를 앞세운다.

### 2. 문서 성격 — 점검형

현재 구현을 설명하는 데 그치지 않고, 페인포인트 기준으로 현재 해법의 빈틈까지 짚는다.
안전 제품은 한계를 아는 팀이 더 믿음직하고, 9/18 동결 전에 고칠 수 있는 것이 드러날 수 있다.

### 3. 구조 — 서사를 뼈대로, 페인포인트를 색인으로

```
0. 한 장 요약                     심사위원이 30초에 읽는 것
1. 이 문서를 읽는 법

Part 1 · 이틀, 두 사람            ← 서사
   장면 1  병원에서 종이를 받는다      PRB001
   장면 2  어디까지 가도 되나          PRB001
   장면 3  오늘은 나갈 수 없는 날      PRB001 · "미추천도 결과다"
   장면 4  1순위가 문을 닫았다         PRB002
   장면 5  보호자의 두 시간            PRB003
   장면 6  영어가 없는 장소            PRB004
   장면 7  환자에게서 전화가 온다       PRB002

Part 2 · 페인포인트 색인          ← 표
Part 3 · 요구사항과 수용 기준      D09 인수조건 20건을 사람 말로 + 검증 상태
Part 4 · 아직 못 푸는 것
부록    용어 · 정본 대응표
```

각 장면은 200단어 안쪽. 왼쪽에 "일반 관광앱이라면", 오른쪽에 "SafeHour는"을 나란히 둔다.

**Part 3을 넣는 이유**: 서사만 있으면 PRD가 아니라 소개서다. 심사위원이 점수를 매길 때는
"이게 실제로 되는가"를 확인해야 하고, 그때 되짚을 항목이 필요하다.

### 4. 빈틈을 다루는 방식 — 세 갈래로 나눈다

정본이 미해결이라 적은 34건을 성격별로 갈라 다르게 쓴다.

| 갈래 | 무엇인가 | 어떻게 쓰는가 |
| --- | --- | --- |
| **① 의도적 제외** | 안 하기로 정한 것 | **강점으로** 쓴다 |
| **② 사람 승인 대기** | 코드로 못 푸는 것 | 절차와 리드타임을 명시 |
| **③ 검증 미완** | 해야 하는데 아직 안 한 것 | 언제·어떻게 닫는지 |

**①을 빈틈에서 빼는 것이 핵심이다.** "지도 연동 없음"은 결함이 아니라 위치정보 규제
회신 전까지의 의도적 절제이고, 안전 제품에서는 오히려 논거다. 약점 목록에 넣으면
스스로 감점한다.

장면마다 한 줄씩 인라인으로 붙이고 Part 4에서 모아 본다. 마지막에만 몰면
"좋은 얘기 하다가 갑자기 고백"처럼 읽히고, 인라인으로 흩으면 매 장면이
"이 팀은 자기 제품을 안다"로 끝난다.

### 5. 넘지 않을 선 — 페르소나는 가정이다

D01의 페르소나 Confidence가 "중간"이고 실제 환자·보호자 인터뷰가 **0건**이다.
Mina와 Alex를 실존 인물처럼 쓰지 않고, 첫 등장에서 **가정한 인물**임을 한 번 명시한다.

안전 제품에서 검증 안 된 것을 검증된 것처럼 쓰면 그 한 줄 때문에 문서 전체의 신뢰가 깎인다.
D07-POL010도 AI가 정책·승인·KPI를 임의 확정하는 것을 금지한다.

## 근거를 무엇으로 삼는가

**노션 정본은 2026-07-30 기준이고, 구현은 그보다 3주 앞서 있다.** 정본을 그대로 베끼면
PRD가 제품을 실제보다 못하게 그린다.

| 정본이 말하는 것 | 실제 |
| --- | --- |
| 모바일 웹 UI 전체 미구현 | 4개 화면 구현, E2E 28건 통과 |
| 기상청 실API 미연결 | AC011 통과 — 배포본 실관측 응답 |
| 접근성 검증 전량 미실행 | axe 8화면 위반 0, 키보드 4, 반응형 7 통과 |
| API 한도 경계 테스트 미작성 | AC017 통과 |
| 내부 API 스키마 미확정 | 계약 확정 + 계약 테스트 |

따라서 빈틈 34건은 **노션에서 베끼지 않고 코드로 한 건씩 걸러서** 쓴다.
정책·의도는 정본을, 현재 상태는 코드를 근거로 삼는다.

**정본 현행화는 이 작업 범위 밖이다.** 운영자가 별건으로 진행하기로 했다.

## 검증 기준

- Part 4의 모든 항목이 코드·문서·명령 출력로 뒷받침될 것. 정본만 근거인 항목은 넣지 않는다.
- 수치는 실측만 쓸 것.
- 검증되지 않은 것을 검증된 것처럼 쓰지 않을 것.
- 사업계획서와 중복되는 시장 통계를 재생산하지 않을 것.

## 검증 결과

52개 에이전트가 네 렌즈(과장·누락·정직성·독자)로 점검하고 각 지적을 반증 시도했다.
**확정 17건을 전부 반영했다.** 과장 유형은 반증 기준을 반대로 걸었다 — 조금이라도
의심스러우면 남겼다. 심사 문서에서 과장은 치명적이기 때문이다.

문서를 쓰다가 제품 결함 셋을 실측으로 발견했다.

1. **배포본에서 로그인이 불가능하다** — Google·Kakao·demo 셋 다 미설정. 지침 연결이
   로그인을 요구하므로 URL 로 들어오는 사람은 홈 화면 너머를 볼 수 없다.
   상태 점검이 로그인 설정을 보고하지 않아 배포 검증 13건을 통과하면서도 제품은 쓸 수 없었다.
2. **계획 유효기간 72시간 vs 조건 최신성 24시간** — 그 사이 구간은 화면상 유효한데 차단된다.
3. **연결 게이트가 판정 API 에는 없다** — 화면과 오늘 상태 경로에만 걸려 있다.

## 이 작업에서 남길 교훈

**문서를 쓰기 전에 `git fetch` 로 main 과의 차이를 먼저 확인한다.** 이번에 3주 묵은
브랜치에서 작업해 한 세대 전 제품을 서술한 문서를 한 번 완성했다. 검증 결과가 어긋났을 때
처음에는 검증 쪽이 틀렸다고 판단했는데, 실제로는 이쪽이 틀렸다.

**제품이 문서보다 정확한 경우가 있다.** 앱의 개인정보 화면은 "좌표가 관광공사·기상청으로
나가고 지도 사업자에게는 나가지 않는다"를 정확히 적고 있었는데, 초안은 "제3자에게 좌표를
보내지 않는다"고 뭉뚱그렸다. 화면 문구를 근거로 삼을 때 코드가 더 믿을 만하다.
