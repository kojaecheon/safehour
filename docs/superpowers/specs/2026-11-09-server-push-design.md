## 1. 왜 하는가

갈래 1(PR #32, #33)은 서버 없이 할 수 있는 만큼 했다. 남은 빈틈은 세 가지이고, 셋 다 서버에 무언가를 두지 않으면 닫히지 않는다.

| 빈틈 | 지금 동작 | 서버 없이 못 닫는 이유 |
| --- | --- | --- |
| 보호자 알림은 앱이 열려 있을 때만 확실하다 | 보호자 기기가 받은 사본의 마감 시각에 스스로 울린다(`COMPANION_RETURN_PASSED`). 앱이 닫혀 있으면 오지 않을 수 있고, 60분 안에 다시 열 때만 늦게 낸다 | 웹은 앱이 닫힌 동안 정해진 시각에 기기 알림을 낼 방법이 없다. 서비스 워커는 수시로 잠들고, 예약 알림 API(Notification Triggers)는 표준이 되지 못했다 (확인 필요). 닫힌 앱을 깨우는 길은 서버가 보내는 푸시뿐이다 |
| 앱은 환자가 돌아왔는지 모른다 | 보호자 화면은 마감이 지나면 '마감 지남'을 그날 끝까지 보인다. 이미 돌아온 환자의 보호자도 같은 알림을 받는다 | 환자 기기에서 누른 확인을 보호자 기기로 옮길 통로가 없다. 위치를 쓰지 않으므로(선 2) 자동으로 알 방법도 없다 |
| 기기를 잃으면 일정도 잃는다 | 체류·확정 일정·동의·보호자 사본이 브라우저 저장소에만 있다 | 다른 기기로 옮길 사본이 어디에도 없다 |

**실제 사용자가 기대하는 것**

- 보호자: "환자가 늦으면 내 휴대폰이 알려 준다. 앱을 켜 두지 않아도." 그리고 "돌아왔으면 괜히 놀라게 하지 않는다."
- 환자: "돌아왔다고 한 번 누르면 보호자가 안다." 메신저로 따로 알리지 않아도 된다.
- 둘 다: "휴대폰을 바꾸거나 잃어도 남은 일정이 사라지지 않는다." (단계 B, 6절)

이 문서의 핵심 제안은 단계 A다: **마감 시각과 '돌아왔어요' 확인 여부, 보호자 알림 주소만** 서버에 두고, 마감 + 유예 시각에
확인이 없으면 보호자에게 푸시를 보낸다.

## 2. 최소 저장 범위

### 2.1 레코드 세 종류

서버가 갖는 것은 아래 세 레코드뿐이다. 모두 **옵트인**이다. 환자가 켜지 않으면 레코드는 하나도 생기지 않고 지금과 똑같이 동작한다.

**(1) 지켜보기(watch): 보호자 링크 계열 하나에 하나**

| 필드 | 값 | 왜 필요한가 | 보관 |
| --- | --- | --- | --- |
| 저장 키 | `HMAC(서버 비밀, 'watch/v1' + watchId)` | 레코드를 찾는 키. 원래 `watchId`는 서버에 남기지 않는다 | 레코드와 같이 |
| `ownerHash` | `HMAC(서버 비밀, 'watch-owner/v1' + 계정 키)` | 환자가 새 기기에서 로그인해 '서버에 남은 내 정보 지우기'를 할 수 있게 한다. 계정 키는 이미 되돌릴 수 없는 값이고, 한 번 더 문맥을 붙여 해시한다 | 레코드와 같이 |
| `writeHash` | `SHA-256(writeToken)` | 환자 기기만 마감을 올리고 '돌아왔어요'를 표시할 수 있게 한다. 원래 토큰은 환자 기기에만 있다 | 레코드와 같이 |
| `expiresAt` | 출국일 23:59 KST | 보관 기한 계산 | 레코드와 같이 |

- 보관: 출국일 23:59 KST + 7일까지(저장소 TTL로 자동 삭제). 기기 쪽 '출국 7일 뒤 삭제'와 맞춘 값이다. 8절 질문 10.
- `watchId`(무작위 16바이트)와 `writeToken`(무작위 32바이트)은 환자 기기가 만든다. `watchId`만 보호자 사본(암호문) 안에 들어간다.

**(2) 보호자 알림 주소(subscription): 지켜보기 하나에 최대 1개**

| 필드 | 값 | 왜 필요한가 | 보관 |
| --- | --- | --- | --- |
| `subId` | 서버가 만든 무작위 16바이트 | 보호자 기기가 구독을 지울 때 쓴다 | 레코드와 같이 |
| `endpoint` | 푸시 서비스 주소 | 푸시를 보낼 곳 | 저장 시 암호화(AES-GCM, 서버 환경변수 키) |
| `keys.p256dh`, `keys.auth` | 브라우저가 준 공개키·인증 비밀 | 푸시 본문 암호화(RFC 8291) | 저장 시 암호화 |
| `lang` | ko·en·ja·zh 중 하나 | 서버가 보호자 언어로 문구를 만든다 | 레코드와 같이 |

- 보관: 지켜보기와 같은 기한. 푸시 서비스가 404·410(구독 만료)을 돌려주면 그 자리에서 지운다.
- '환자 1명 + 동반 보호자 1명' 전제에 맞춰 새로 구독하면 이전 구독을 덮어쓴다. 8절 질문 14.
- 보호자의 계정 키나 그 해시는 **저장하지 않는다.** 저장하면 서버 안에서 환자 계정과 보호자 계정이 이어진다. 보호자 쪽 삭제는 보호자 기기에 있는 `subId`로 한다.

**(3) 날짜 기록(day): 지켜보기 하나 × 날짜 하나**

| 필드 | 값 | 예 |
| --- | --- | --- |
| 날짜 | KST `YYYY-MM-DD` (저장 키에 포함) | `2026-11-20` |
| `deadlines` | 그날 환자 복귀 마감 시각 목록, `HH:MM`만 | `["14:30", "18:00"]` |
| `confirmed` | '돌아왔어요'가 눌린 마감 시각 | `["14:30"]` |
| `pushed` | 마감 지남 푸시를 이미 보낸 마감 시각 | `["18:00"]` |

- 보관: 그 날짜 23:59 KST + 1일. 날짜 기록은 지켜보기보다 짧게 둔다. 지난 날의 마감은 쓸모가 없다.
- 외출 id, 출발 시각, 정거장, 복귀 장소 종류는 두지 않는다. 마감 시각을 키로 쓰면 '같은 시각은 하나로' 규칙과도 맞는다.
  - 복귀 장소 종류(숙소/병원)를 넣지 않는 이유: 병원으로 돌아가는 외출이 있다는 사실이 시술 정황을 드러낸다. 푸시 문구에도 필요 없다.
  - 마감이 바뀌면 새 시각은 확인되지 않은 마감으로 본다. 이미 돌아온 환자라도 바뀐 마감은 새로 확인받는 쪽이 안전하다.

### 2.2 저장하지 않는 것

조건 항목 값(식이·복약·보행·자외선·열·물·동행), 조건 기간, 판정 결과·사유 코드, 병원 이름·주소·전화·안내문·일정,
숙소 이름·주소, **좌표 전부**, 정거장과 장소 이름, 외출 출발 시각, 계정 식별자(공급자·sub), 계정 키 원문, 보호자 계정 정보,
제공자 토큰, PIN, 보호자 사본 암호문, IP 주소, 기기 정보(User-Agent).

### 2.3 절대 넘지 않는 선과 맞춰 보기

| 선 | 이 설계에서 |
| --- | --- |
| 1. 의료 판단을 만들지 않는다 | 서버는 시각 비교만 한다(마감 + 유예 < 지금, 확인 없음). 조건을 보지 않으므로 해석·완화할 것이 없다. 문구에 '안전'을 쓰지 않는다 |
| 2. 현재 위치를 수집하지 않는다 | '돌아왔어요'는 사람이 누르는 확인이다. 위치·좌표·지오펜스를 쓰지 않는다. 좌표는 서버로 가지도 않는다 |
| 3. 병원 목록·추천·순위·제휴 없음 | 해당 없음. 병원 정보가 서버에 없다 |
| 4. 조건 값은 계산 뒤 버리고, 토큰은 보관하지 않는다, 저장소는 보고 뒤에 | 조건 값은 이 레코드들에 들어갈 경로가 없다(허용 목록 양쪽). 제공자 토큰은 그대로 버린다. `writeToken`·`watchId`는 해시만 둔다. 이 문서가 그 보고다 |
| 5. 불확실한 것을 사실로 바꾸지 않는다 | 서버가 아는 것은 "확인 버튼이 눌리지 않았다"뿐이다. 푸시는 "복귀 확인이 없어요"라고 쓰고 "돌아오지 않았어요"라고 쓰지 않는다. 마감이 오래된 값일 수 있다는 사실도 동의 문구에 밝힌다 |

## 3. 흐름

### (a) 보호자가 `/g`에서 푸시를 구독한다

1. 보호자가 받은 일정 화면의 '복귀 마감 알림 받기' 스위치를 켠다(갈래 1과 같은 스위치). 사본에 `watchId`가 있고 서버 푸시가 켜진 배포면, 스위치 아래에 '앱이 닫혀 있어도 받기' 항목이 하나 더 보인다.
2. 누르는 순간에만 `Notification.requestPermission()`을 부른다(사용자 동작 안에서만 물을 수 있다).
3. `GET /api/push/config`로 VAPID 공개키와 스위치 상태를 받는다. 공개키를 `NEXT_PUBLIC_`으로 굽지 않는 이유: 키를 바꾸거나 끌 때 다시 빌드하지 않으려고.
4. 서비스 워커 `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`.
5. `POST /api/watch/subscribe` 본문 `{ watchId, subscription: { endpoint, keys: { p256dh, auth } }, lang }`. 보호자 로그인 필요(지금도 사본을 보려면 로그인이 필요하다). 서버는 `endpoint` 호스트를 허용 목록(5.3)과 맞춰 보고, 지켜보기가 살아 있으면 구독을 저장하고 `{ subId }`를 돌려준다. 지켜보기가 없거나 만료됐으면 언제나 같은 404를 준다.
6. 보호자 기기는 `subId`를 계정 이름공간(`safehour.v2.<계정 키>.guardianPush`)에 둔다. '이 기기에서 내 정보 지우기' 대상이다.

**아이폰**: 홈 화면에 추가한 웹 앱에서만, iOS·iPadOS 16.4 이상에서 웹 푸시를 받는다. Safari 탭에서는 구독할 수 없다. 화면은 이 조건을 먼저 확인하고(standalone 여부, `PushManager` 존재), 안 되면 '홈 화면에 추가' 안내를 보인다.

- 함정 (확인 필요): 아이폰의 홈 화면 웹 앱은 Safari와 저장소를 나눠 쓰는 것으로 알고 있다. 그렇다면 Safari에서 가져온 사본이 홈 화면 앱에는 없다. 홈 화면 앱 안에서 링크를 붙여 넣고 PIN을 다시 넣는 '링크 붙여넣기' 입력이 필요하다. 로그인 쿠키도 따로일 수 있다. 실기기 시험 항목으로 둔다.

### (b) 환자 기기가 마감을 올린다

**지켜보기 만들기**: 환자가 보호자 링크를 만들 때(지금 흐름), 공유 동의 화면에 '서버 알림 사용' 선택 항목을 하나 더 둔다(기본 꺼짐, 5.5 문구). 켜면:

1. 기기가 `watchId`, `writeToken`을 만든다(같은 체류에 이미 있으면 다시 쓴다. 링크를 다시 보내도 보호자 구독이 이어진다).
2. `POST /api/watch` 본문 `{ watchId, writeToken, expiresAt }`. 환자 로그인 필요. 서버는 `ownerHash`를 세션에서 계산해 넣는다.
3. 스냅샷에 `watchId` 필드 하나를 더해 암호화한다(링크가 약 30자 늘어난다. 8절 질문 11).
4. 기기는 `{ watchId, writeToken, expiresAt }`를 계정 이름공간(`safehour.v2.<계정 키>.guardianWatch`)에 둔다.

**마감 올리기 (`PUT /api/watch/deadlines`)**

- 본문: `{ watchId, writeToken, days: [{ date, deadlines: ["HH:MM", ...] }] }`. 날짜는 오늘(KST)부터 출국일까지, 보호자 사본의 `patientReturn[].by`와 **같은 계산**(같은 함수)으로 만든다. 보호자가 이미 갖고 있는 정보와 같은 범위다. 8절 질문 5.
- 언제 올리나:
  1. 확정 일정을 저장할 때마다(계획·재계획·편집·사건 반영). `lib/trip`의 저장 지점 한 곳에 붙인다.
  2. 지켜보기를 만들 때.
  3. 앱을 열 때와 날짜가 바뀔 때, 마지막으로 올린 내용과 다르면.
- 서버는 날짜별로 `deadlines`를 통째로 바꾼다. `confirmed`·`pushed`는 새 목록에 남은 시각만 유지한다.
- 오프라인이면: 기기에 '올리지 못함' 표시(`safehour.v2.<계정 키>.guardianWatch.pending`)를 남기고 `online`·화면 복귀 때 다시 보낸다. 로그아웃 미전송 표시와 같은 방식이다. 그동안 서버는 마지막으로 받은 마감을 쓴다. 즉 **바뀐 마감이 늦게 반영될 수 있다.** 이 한계를 동의 문구와 보호자 화면에 적는다.
- 외출 중 재계획(`OUTING_OVERDUE`)으로 마감이 지금으로 당겨진 외출은 올리지 않는다. 그 값은 실제 마감이 아니다(지금 알림 규칙 `isOverdueClampedDay`와 같은 기준).
- 즉시 복귀 원인(환자 호출·지침 철회·만료)이 켜진 날은 실제 마감이 남아 있으므로 그대로 올린다.

### (c) 마감 + 유예에 확인이 없으면 보호자에게 푸시

1. 예약: 마감을 받을 때 각 `(지켜보기, 날짜, 시각)`마다 `마감 + 유예` 시각의 작업을 하나 건다(4.2의 방식에 따라 지연 메시지 또는 분 단위 크론이 집는 대기열).
2. 실행 시 **지금 상태를 다시 읽는다.** 아래가 모두 맞을 때만 보낸다:
   - 스위치가 켜져 있다(5.6 kill switch 꺼짐).
   - 지켜보기와 구독이 살아 있다.
   - 그 시각이 아직 그날 `deadlines`에 있다(바뀐 마감이면 건너뛴다).
   - `confirmed`에 없다.
   - `pushed`에 없다(한 번만).
   - 지금 < 마감 + 60분(`returnPassedGraceMin`). 실행이 크게 밀렸으면 보내지 않는다. 기기 알림의 늦은 알림 규칙과 같은 창이다.
3. 보내면 `pushed`에 시각을 더한다. 예약 작업은 다시 실행돼도 2번에서 걸러지므로(멱등) 취소하지 못해도 괜찮다.
4. 푸시 본문(암호화됨): `{ title, body, url: '/g', tag }`. 문구는 서버가 보호자 `lang`으로 i18n 사전에서 만든다.
   - ko: "일행의 복귀 마감 {time}이 지났고 아직 복귀 확인이 없어요. 함께 있지 않다면 지금 연락해 보세요"
   - en: "Your companion's {time} return time has passed with no check-in yet. If you're not together, contact them now"
   - ja·zh는 검수 전 번역을 같은 방식으로 둔다. 금지어 검사(`test/notify-schedule.test.js`의 `FORBIDDEN`)를 통과해야 한다.
   - 잠금 화면에 뜨므로 '환자'·'병원'·장소 이름을 쓰지 않는다. 넣는 값은 `{time}` 하나다.
5. 서비스 워커 `push` 이벤트는 받은 제목·본문을 그대로 `showNotification`한다. `data.url`은 기존 허용 목록(`/today`, `/g`) 안에서만 쓴다(`public/sw.js`와 `lib/notify/device.js`를 같이 고친다).
6. 푸시 헤더: `TTL` 3600초(60분 창과 같게), `Urgency: high`, `Topic`은 날짜·시각을 드러내지 않는 해시 (확인 필요: Topic 길이·문자 제한).

**유예 시간**: 새 기본값 `DEFAULTS.notifications.serverPushGraceMin`이 필요하다. 제안 10분. 마감 직후 몇 분 늦는 것은 흔하고, 갈래 1 기기 알림이 마감 시각에 이미 한 번 울린다. 판정 숫자는 아니지만 `src/stay/defaults.js` 한 파일에 두는 규칙에 따라 보고한다. 8절 질문 6.

**갈래 1과 함께 둘 때**: 보호자 기기 알림(마감 시각, 앱이 열려 있을 때)은 그대로 둔다. 서버 푸시는 마감 + 유예에 확인이 없을 때만 온다. 둘은 뜻이 다르다(마감 도래 / 확인 없음). 보호자 기기가 온라인이면 (d)의 상태 조회로 이미 확인된 마감은 갈래 1 알림을 내지 않게 할 수 있다(단계 A의 선택 과제).

### (d) 환자가 '돌아왔어요'를 누른다

- 위치: 경우 1 시트('복귀 마감 시각이 지났어요')와 경우 2 시트에 '돌아왔어요' 버튼. 그리고 외출 중일 때 오늘 화면의 외출 카드에도 둔다(마감 전에 돌아오면 푸시 자체가 나가지 않게). 8절 질문 7.
- `POST /api/watch/back` 본문 `{ watchId, writeToken, date, by }`. 서버는 `confirmed`에 `by`를 더한다. 이미 있으면 그대로 성공(멱등).
- **보기 전용 상태(세션 만료)에서도 누를 수 있어야 한다.** 그래서 이 경로는 세션이 아니라 `writeToken`으로 권한을 확인한다. '돌아왔어요'는 일정 편집이 아니라 확인 신호라 보기 전용 규칙의 예외로 둔다. 8절 질문 8. 오프라인이면 기기에 대기 표시를 두고 다시 보낸다. 화면에는 "연결되면 보호자에게 전달돼요"라고 쓰고 "전달했어요"라고 쓰지 않는다.
- 누른 뒤 시트는 지금처럼 닫힌다. 일정은 바꾸지 않는다(판정을 새로 하지 않는 표시 신호다).
- **보호자 '복귀 확인' 푸시 (선택)**: 마감 지남 푸시를 이미 보낸 마감(`pushed`에 있음)이 확인되면 한 번 보낸다. "일행이 {time} 마감 뒤 복귀를 확인했어요". 푸시를 보내지 않은 마감은 조용히 둔다(소음 줄이기). 8절 질문 9.
- **보호자 화면 상태 조회 (선택)**: `POST /api/watch/status` 본문 `{ watchId }`로 오늘 `confirmed` 목록만 돌려준다. `watchId`를 쿼리에 싣는 GET은 쓰지 않는다(URL은 중간 기록에 남는다). `/g`는 확인된 마감에 '복귀 확인' 표시를 붙인다. 확인이 없는 마감은 지금처럼 '마감 지남'이다.

| 날짜 23:59 KST + 1일 | 그 날짜 기록 | 저장소 TTL |

| 환자 '서버에 남은 내 정보 지우기'(새 화면 항목) | 이 계정의 `ownerHash`로 찾은 지켜보기 전부 | 로그인 필요. 기기를 잃은 경우의 길이다. `ownerHash` 보조 색인이 필요하다 |

| 보호자 스위치 끄기, 사본 삭제·만료, 보호자 '내 정보 지우기' | 그 구독 | `DELETE /api/watch/subscribe` 본문 `{ watchId, subId }` |

## 4. 기술 선택지 (Vercel, 서울 리전 `icn1`)

### 4.1 저장소

| 선택지 | 붙이는 법 | 맞는 점 | 걸리는 점 | 비용·운영 부담 |
| --- | --- | --- | --- | --- |
| **Upstash Redis** (Vercel Marketplace, 예전 'Vercel KV'의 후속) | REST API를 `fetch`로 부른다. 패키지 불필요 | 키마다 TTL로 보관 기한을 저장소가 지킨다. 정렬 집합으로 예약 대기열을 만들 수 있다. 원자적 집합 연산(`SADD`)으로 멱등 처리가 쉽다 | 리전: 서울 리전이 있는지 확인 필요(없으면 도쿄 등 국외 저장, 처리방침에 국외 이전 고지). 무료 한도 확인 필요 | 무료 등급으로 시작 가능할 것으로 보임 (확인 필요). 운영 부담 낮음 |
| Vercel Postgres 후속(Neon 등 Marketplace) | 보통 드라이버 패키지를 쓴다. HTTP 질의 엔드포인트를 `fetch`로 부를 수 있는지 확인 필요 | 질의가 자유롭다 | TTL이 없어 정리 작업을 따로 돌려야 한다. 스키마·이전 관리가 생긴다. 이 규모에 무겁다 | 무료 등급 있음 (확인 필요). 운영 부담 중간 |
| Vercel Blob | 객체 저장. REST 가능 (확인 필요) | 단계 B(암호문 백업 파일)에는 맞는다 | TTL·원자 연산이 없다. 작은 레코드를 자주 고치는 용도에 맞지 않는다 | 단계 A에는 부적합 |
| 함수 `/tmp` 파일 | 지금 관광공사 캐시 방식 | 추가 서비스 없음 | 인스턴스마다 따로이고 언제든 사라진다. 저장소가 아니다 | 불가 |

**추천: Upstash Redis.** TTL이 '보관 기한'을 코드가 아니라 저장소 성질로 지켜 주고, `fetch`만으로 붙어 새 패키지가 없다.
저장 위치가 국외라면 개인정보 처리방침의 국외 이전·처리 위탁 항목이 필요하다(법무 확인 필요).

키 구성(예): `sh:w:<watchKey>`(해시: owner, write, exp), `sh:s:<watchKey>`(구독, 암호문), `sh:d:<watchKey>:<date>`(해시 또는 집합 셋),
`sh:o:<ownerHash>`(집합: 지켜보기 키들, 기기 분실 삭제용), `sh:q`(정렬 집합: 예약 대기열, 4.2의 크론 방식일 때만).

### 4.3 웹 푸시와 VAPID

- 서명 키: P-256 키 쌍. 환경변수 `SAFEHOUR_VAPID_PUBLIC_KEY`, `SAFEHOUR_VAPID_PRIVATE_KEY`, `SAFEHOUR_VAPID_SUBJECT`(운영자 연락처 `mailto:` 또는 `https:` 주소, 푸시 서비스에 전달된다). 키 생성은 `node:crypto`의 `generateKeyPairSync('ec', { namedCurve: 'prime256v1' })`로 하는 저장소 안 스크립트로 한다(`npx web-push` 금지).
- 요청 하나에 필요한 것:
  1. VAPID JWT(RFC 8292): ES256 서명, `aud` = 푸시 서비스 출처, `exp` 24시간 이하, `sub` = 연락처. `Authorization: vapid t=<JWT>, k=<공개키>`.
  2. 본문 암호화(RFC 8291, `Content-Encoding: aes128gcm`): 임시 P-256 키로 ECDH, HKDF-SHA256으로 키·nonce 유도, AES-128-GCM, 레코드 헤더(salt 16바이트, 레코드 크기, 키 id).
- 푸시 서비스 주소 예: Chrome 계열 `fcm.googleapis.com`, Firefox `updates.push.services.mozilla.com`, Safari `web.push.apple.com` (확인 필요: 전체 호스트 목록).
- 아이폰: iOS·iPadOS 16.4 이상, 홈 화면에 추가한 웹 앱만, 권한 요청은 사용자 동작 안에서만. 푸시마다 반드시 알림을 보여야 한다(`userVisibleOnly`). 보여 주지 않는 푸시가 반복되면 구독이 끊길 수 있다 (확인 필요).

**패키지 문제: `web-push` 라이브러리 vs 표준 기능으로 직접 서명**

| | `web-push` 패키지 | `node:crypto`로 직접 |
| --- | --- | --- |
| 규칙 | 잠금 파일이 바뀐다. 운영자 허락 필요(standards.md 의존성) | 규칙 안. PIN 암호화·좌표 변환·외부 호출과 같은 선례 |
| 가능성 | 검증된 구현 | 가능하다. 필요한 기본 연산(`createECDH('prime256v1')`, `hkdfSync('sha256')`, `createCipheriv('aes-128-gcm')`, `sign(..., { dsaEncoding: 'ieee-p1363' })`)이 Node 22에 모두 있다 |
| 분량 | 0.5일 | 서명·암호화 합쳐 약 150~250줄, 2일 |
| 위험 | 패키지와 하위 의존성의 취약점 권고(지금도 `npm run check`가 audit에서 실패한다) | 바이트 배치 실수. RFC 8291 부록의 시험 벡터를 단위 테스트로 고정하면 결정적으로 잡힌다. 실기기 3종(안드로이드 Chrome, 아이폰 홈 화면, 데스크톱 Firefox) 수신 확인 필요 |

**추천: 직접 구현.** 실현 가능성은 높다고 본다. 막히면(시험 벡터 불일치를 두 번 시도해도 못 풀면) 멈추고 패키지 허락을 묻는다.
최후 대안으로 **본문 없는 푸시**가 있다. 암호화가 필요 없고 VAPID 서명만 하면 된다. 대신 서비스 워커가 시각 없이 고정 문구
("일행의 복귀 마감이 지났어요. 받은 일정을 확인해 보세요")만 낼 수 있고, 언어는 서비스 워커가 IndexedDB에 둔 값을 읽어야 한다.

## 5. 보안과 개인정보

### 5.1 계정 범위와 신원 분리

- 서버는 계정 식별자도 계정 키 원문도 저장하지 않는다. 환자 쪽은 `ownerHash`(계정 키에 문맥을 붙인 HMAC)만 둔다.
- 보호자 구독은 `watchId`로만 지켜보기에 묶인다. `watchId`는 PIN으로 잠긴 사본 안에서만 보호자에게 간다. 서버는 보호자가 누구인지 모르고, 환자 계정과 보호자 계정을 잇는 기록도 없다.
- 저장소가 통째로 새도 보이는 것: 해시된 키, 날짜와 `HH:MM` 목록, 암호화된 구독. 누구의 것인지, 어디에 있는지, 무슨 시술인지는 알 수 없다. 구독 암호화 키(`SAFEHOUR_PUSH_STORE_KEY`)는 저장소 밖(환경변수)에 있다.
- 세션 서명 키를 바꾸면 `ownerHash`가 달라져 '서버에 남은 내 정보 지우기'가 예전 레코드를 못 찾는다. TTL로 결국 지워지지만, 키 교체 절차에 이 사실을 적는다.

### 5.2 경로별 권한

| 경로 | 권한 확인 | 비고 |
| --- | --- | --- |
| `GET /api/push/config` | 없음 | 공개키와 스위치 상태만 |
| `POST /api/watch` | 환자 세션 | 계정당 동시 지켜보기 수 제한(예: 3) |
| `PUT /api/watch/deadlines` | `writeToken` (+ 세션이 있으면 `ownerHash` 일치) | 날짜 수 ≤ 체류 최대 45박 + 1, 날짜당 시각 ≤ 10 |
| `POST /api/watch/back` | `writeToken` | 세션 없이도 됨(보기 전용 예외) |
| `DELETE /api/watch` | `writeToken` 또는 세션의 `ownerHash` | |
| `POST·DELETE /api/watch/subscribe` | 보호자 세션 + `watchId` (삭제는 `subId`도) | |
| `POST /api/watch/status` | 보호자 세션 + `watchId` | 오늘 `confirmed`만 |
| 예약 처리 경로 | QStash 서명 또는 `CRON_SECRET` | 외부에서 부르면 401 |

모든 경로는 허용 목록으로 본문을 깎고(클라이언트·서버 양쪽), 토큰 비교는 `timingSafeEqual`로 한다. 모르는 `watchId`, 만료, 틀린 토큰은 모두 같은 404를 준다(어느 쪽인지 알려 주지 않는다. 세션 검증과 같은 원칙).

### 5.3 위협과 대응

| 위협 | 대응 |
| --- | --- |
| 구독 주소 탈취(저장소 유출 등)로 보호자에게 스팸 푸시 | 구독은 저장 시 암호화. 푸시를 보내려면 VAPID 개인키도 있어야 한다(푸시 서비스가 공개키와 맞춰 본다). 개인키는 환경변수에만 둔다 |
| 공격자가 `endpoint`에 내부 주소를 넣어 서버가 그곳을 부르게 함(SSRF) | `endpoint`는 `https:`이고 호스트가 푸시 서비스 허용 목록에 있을 때만 받는다. 리디렉트를 따라가지 않는다 |
| 재전송(같은 '돌아왔어요'·마감 요청 반복) | 모든 쓰기가 멱등(집합 연산, 통째 바꾸기). 재전송해도 상태가 같다. 예약 처리도 `pushed`로 한 번만 |
| 열거(`watchId` 추측) | 16바이트 무작위값. 응답을 하나로 통일. 세션당·IP당 횟수 제한 |
| 오래된 마감으로 오경보 | 실행 시 현재 `deadlines` 재확인. 오프라인 반영 지연은 화면·동의 문구에 밝힌다 |
| 링크가 메신저에 남아 제3자가 `watchId`를 얻음 | `watchId`는 PIN 암호문 안에 있다. PIN이 6자리라 '우연한 열람 방지 수준'이라는 지금 한계를 그대로 물려받는다. 얻은 사람이 할 수 있는 것은 구독 덮어쓰기(보호자 알림 가로채기)와 오늘 확인 목록 읽기다. 구독이 바뀌면 이전 구독에 "알림 받는 기기가 바뀌었어요" 푸시를 한 번 보내 알아차리게 한다 |
| 푸시 문구가 잠금 화면에 보임 | '일행'·시각만. 금지어 검사 |
| 보호자가 환자 위치를 추적하는 용도로 오해 | 서버에 위치가 없다. 화면에 "앱은 위치를 모릅니다. 환자가 누른 확인만 전달합니다"라고 적는다 |

**횟수 제한** (Redis `INCR` + TTL, 값은 제안): 지켜보기 만들기 계정당 시간당 10, 마감 올리기 지켜보기당 시간당 60, 돌아왔어요 지켜보기당 하루 50,
구독 지켜보기당 시간당 10, 상태 조회 지켜보기당 시간당 120, 보내는 푸시 지켜보기당 하루 20. 넘으면 429와 새 오류 코드. 숫자는 `src/stay/defaults.js`가 아니라 서버 설정 상수로 둘지 8절에서 함께 정한다(판정 값은 아니다).

### 5.4 기록

`docs/security.md` '기록'을 그대로 따르고 조립 함수만 필드를 만든다.

- 남기는 것: 경로 구분, 결과 구분(성공·거부·없음·제한), 자체 오류 코드, 처리 시간. 예약 처리 한 번에 한 줄: 대상 수, 보낸 수, 건너뛴 이유별 수, 푸시 서비스 응답 상태 **구간**(2xx·404/410·4xx·5xx), 처리 시간.
- 남기지 않는 것: `watchId`·저장 키·`ownerHash`·`subId`, endpoint 주소와 호스트, 날짜·시각, 언어, 토큰, 푸시 서비스 오류 원문, IP.

### 5.5 동의 문구 추가 (법무 검토 전 배지 표시)

**환자, 보호자 링크 만들 때 '서버 알림 사용'(기본 꺼짐)**

> 보호자에게 앱이 닫혀 있어도 알림을 보내려면 아래 정보를 SafeHour 서버에 보관합니다.
> - 보관하는 것: 남은 체류 기간의 날짜별 복귀 마감 시각, '돌아왔어요'를 눌렀는지 여부
> - 보관하지 않는 것: 장소, 위치, 몸 상태와 조건, 병원 정보
> - 보관 기간: 출국 7일 뒤 자동 삭제. 설정에서 언제든 지울 수 있습니다
> - 휴대폰이 오프라인이면 바뀐 마감이 늦게 전달될 수 있습니다
> - 마감이 지나도 '돌아왔어요'를 누르지 않으면 보호자에게 알림이 갑니다. 앱은 위치를 모르므로 실제로 돌아왔는지는 알 수 없습니다
> - 저장 위치: (업체·국가 확정 후 기재)

**보호자, '앱이 닫혀 있어도 받기' 켤 때**

> 이 휴대폰의 알림 주소를 SafeHour 서버에 보관합니다. 환자의 출국 7일 뒤, 또는 스위치를 끄면 지워집니다.

개인정보 고지(`/privacy`) 개정, 처리 위탁(Vercel, Upstash) 및 국외 이전 여부 고지가 함께 필요하다(법무 확인 필요).

### 5.6 운영 스위치

- `SAFEHOUR_SERVER_PUSH`: 기능을 **켜는** 스위치. 정확히 `1`일 때만 켜진다. 꺼져 있으면 `/api/push/config`가 꺼짐을 알리고, 화면은 서버 알림 항목을 숨기며, 모든 `/api/watch*`는 503 + 새 오류 코드.
- `SAFEHOUR_KILL_SERVER_PUSH`: 기능을 **끄는** 안전 스위치. `1`·`true`·`on`을 켜짐으로 읽는다. 켜지면 예약 처리가 아무것도 보내지 않고, 쓰기 경로는 503, 삭제 경로는 계속 동작한다(지우는 길은 막지 않는다).
- 두 값은 `runtimeFlagsSnapshot()`과 `/api/health`에 드러낸다. 꺼져도 갈래 1 기기 알림은 그대로 동작한다.

## 6. 단계적 도입

### 단계 A: 옵트인 보호자 푸시와 '돌아왔어요'

범위: 3절 (a)~(e) 전부, 5.6 스위치, 문서 개정(아래). 갈래 1은 바탕으로 그대로 둔다.

A 안에서의 순서:

1. A-1 저장소·푸시 발송 기반(서버만, 화면 없음). 스위치 꺼진 채 병합 가능.
2. A-2 환자 쪽: 동의, 지켜보기, 마감 올리기, '돌아왔어요'.
3. A-3 보호자 쪽: 구독, 서비스 워커 `push` 처리, 아이폰 안내, 상태 표시(선택).
4. A-4 운영: 미리보기 배포에서 스위치 켜고 실기기 시험, 그 뒤 운영 스위치.

함께 고칠 문서: `docs/security.md`('무엇을 지키나'를 통째로 다시 쓴다. 지금 모델의 전제가 바뀐다), `docs/architecture.md`(서버에 남는 것),
`docs/contracts.md`(새 경로), `docs/business-rules.md`(보호자·알림), `docs/operations.md`(환경변수·데이터 초기화),
`docs/platform/PRODUCT_DEFINITION_V3.md` 4.2절(제외 목록에서 서버 푸시 해제), `lib/notify/AGENTS.md`('서버 푸시는 맡지 않는다' 문장),
`.env.example`, ADR-0012, `HUMAN_ACTIONS.md`(법무 항목).

### 단계 B: 같은 저장소로 기기 백업·복원

- 무엇: 체류·확정 일정·동의 기록의 사본을 서버에 두고 새 기기에서 복원한다.
- **조건이 붙는다.** 체류에는 조건 기간(건강 관련 민감정보)과 좌표가 들어 있다. 평문으로 서버에 두면 선 4("조건 값은 계산 뒤 버린다")를 정면으로 어긴다. 그래서 B는 **종단 간 암호화**일 때만 성립한다: 기기에서 사용자만 아는 복구 코드(예: 무작위 24자, 화면에 한 번 보여 주고 적어 두게 함)로 키를 유도해(보호자 링크와 같은 PBKDF2 + AES-GCM) 암호문만 올린다. 서버는 복구 코드를 받지도 저장하지도 않는다.
- 그래도 남는 질문: "암호문이라도 서버에 조건 값이 있다"를 선 4 위반으로 볼지는 운영자가 정할 일이다. 복구 코드를 잃으면 복원할 수 없다는 한계도 있다.
- 저장: 크기가 수십 KB일 수 있어 Redis보다 Blob이 맞을 수 있다 (확인 필요: Redis 값 크기 한도, Blob 비공개 접근 지원).
- 추천: **이번에는 하지 않는다.** A가 운영에서 안정된 뒤 따로 설계한다. 그 전까지의 대안은 9절의 '암호화 파일 내보내기'.

- **단위**(`node --test`, 외부 호출 0): VAPID JWT 형식·서명 검증, RFC 8291 시험 벡터, 저장소 어댑터(메모리 구현으로 TTL·멱등), 예약 처리 판정표(확인됨·이미 보냄·마감 바뀜·60분 초과·스위치 꺼짐·구독 없음), 허용 목록 밖 필드 버림, endpoint 호스트 허용 목록, 로그 조립 함수가 금지 값을 내지 않음, 새 문구 4개 언어 금지어·자리표시자 검사, 서비스 워커 `push` 처리(지금 `test/pwa-sw.test.js`처럼 `sw.js`를 실제로 돌린다).
- **계약**: 환자·보호자 클라이언트의 실제 요청 조립 함수가 만든 본문을 실제 라우트 처리기에 넣는다(standards.md 규칙).
- **화면 테스트**(외부 호출 0 유지): 저장소는 메모리 어댑터(`SAFEHOUR_STORE_MODE=memory`, 데모 로그인일 때만 허용), 푸시 서비스는 로컬 가짜 엔드포인트(허용 목록에 테스트 호스트를 더하는 것도 데모 모드에서만). 시나리오: 환자가 켜고 마감 올림, 시계를 마감 + 유예로 옮겨 예약 처리 호출, 가짜 엔드포인트가 암호문 1건을 받고 복호화하면 문구가 맞음, '돌아왔어요' 뒤에는 0건, 보호자가 끄면 0건. 실제 브라우저의 푸시 수신은 화면 테스트로 흉내 낼 수 없으므로 실기기 시험으로 둔다.
- **실기기**: 안드로이드 Chrome(앱 닫힘), 아이폰 홈 화면 앱(앱 닫힘, 잠금 화면), 데스크톱 Firefox. `docs/DEVICE_TEST_CHECKLIST.md`에 항목을 더하는 것은 그 파일이 제출 산출물인지 먼저 확인한다.

| 3 | 예약은 QStash 지연 메시지로 하는가? (아니오면 Vercel Pro + 매분 Cron) | **예** | Hobby 유지, 마감마다 정확히 한 번. Pro 계획이 있으면 아니오도 무방 |

| 5 | 마감은 남은 체류 기간 전체(보호자 사본과 같은 범위)를 올리는가? (아니오면 오늘만) | **예** | 환자가 그날 앱을 안 열어도 푸시가 동작한다. 보호자가 이미 가진 정보와 같은 범위다 |
| 6 | 서버 푸시 유예를 마감 + 10분으로 하고 `defaults.js`에 새 값으로 두는가? | **예** | 마감 시각에는 갈래 1 기기 알림이 이미 울린다. 사람 검토 전 임시값으로 표시 |
| 7 | '돌아왔어요'를 시트 두 곳과 외출 카드(마감 전)에 모두 두는가? | **예** | 마감 전에 돌아온 환자의 보호자에게 푸시가 가지 않게 한다 |
| 8 | 보기 전용(세션 만료) 상태에서도 '돌아왔어요'를 허용하는가? (`writeToken` 권한) | **예** | 확인 신호가 로그인 때문에 막히면 오경보가 난다. 편집이 아니다 |
| 9 | 확인이 들어오면 보호자에게 '복귀 확인' 푸시를 보내는가? (마감 지남 푸시를 보낸 경우만) | **예** | 보낸 경보를 닫아 준다. 보내지 않은 마감은 조용히 둔다 |
| 10 | 지켜보기·구독 보관을 출국일 + 7일로 하는가? (아니오면 출국일 끝) | **예** | 기기 보관 규칙과 같아 설명이 하나다. 더 짧게 원하면 아니오 |
| 11 | 보호자 스냅샷에 `watchId` 필드를 더하는가? (링크 약 30자 증가) | **예** | 보호자와 지켜보기를 잇는 가장 작은 방법이고 PIN 암호문 안에 머문다 |
| 12 | 단계 B(기기 백업·복원)를 이번에 함께 하는가? | **아니오** | 조건 값 암호문 보관이라는 별도의 선 4 판단이 필요하다. A 안정화 뒤 따로 |
| 13 | 법무 검토 전에는 미리보기 배포에서만 켜고 운영 스위치는 끄는가? | **예** | 처리방침·국외 이전 고지가 정리되기 전 실제 사용자 데이터를 받지 않는다 |
| 14 | 보호자 구독은 지켜보기당 1개(새 구독이 덮어씀)로 하는가? | **예** | 제품 전제가 보호자 1명이다. 바뀔 때 이전 기기에 알림 |
| 15 | 갈래 1 보호자 기기 알림을 그대로 두는가? | **예** | 서버가 꺼지거나 실패할 때의 바탕이다 |

## 9. 대안: 서버 저장을 하지 않는다면

정직하게 남는 선택지와 한계다.

| 대안 | 하는 일 | 한계 |
| --- | --- | --- |
| 갈래 1 그대로 | 보호자 기기가 앱이 열려 있을 때 마감 시각에 알린다 | 닫힌 앱에는 오지 않을 수 있다. 환자가 돌아왔는지 모른다. 이미 있는 상태다 |
| '돌아왔어요'를 메신저로 보내기 | 환자가 버튼을 누르면 Web Share(또는 `sms:` 링크)로 "{time} 마감, 복귀했어요" 문장을 카카오톡 등으로 보낸다 | 보호자는 메신저 알림으로 받으므로 앱이 닫혀 있어도 온다. 대신 환자가 매번 공유 화면에서 대상을 골라 보내야 하고, 보내지 않은 것을 서버가 알아차려 경보하지는 못한다. 서버 저장 0 |
| 보호자 달력 파일(.ics) | 보호자 화면이 사본의 마감 시각으로 달력 일정(알림 포함) 파일을 만들어 휴대폰 달력에 넣게 한다 | 달력 알림은 앱이 닫혀 있어도 울린다. 하지만 마감이 바뀌면 다시 넣어야 하고, 복귀 확인과 무관하게 매번 울린다. 달력 제목이 잠금 화면에 보이므로 중립 문구여야 한다. 서버 저장 0, 파일은 기기 안에서 만든다 |
| 상태 없는 서버 + 외부 지연 메시지만 | 자체 저장소 없이 QStash에 "이 시각에 이 구독으로 보내라"는 메시지만 맡긴다 | 그 업체가 구독 주소와 시각을 보관하므로 저장소를 업체로 옮긴 것일 뿐이다. 확인 취소도 할 수 없다. 선 4를 피하는 방법이 아니다 |
| 백업을 파일로 내보내기 | 기기에서 복구 코드로 암호화한 파일을 내려받아 사용자가 보관하고, 새 기기에서 불러온다 | 기기 분실에 대비하려면 사용자가 미리 내보내 둬야 한다. 서버 저장 0 |

서버 저장을 하지 않는다면 추천 조합은 **갈래 1 + '돌아왔어요' 메신저 공유 + 보호자 달력 파일**이다. 약 3~4일. 다만 "확인이 없으면 알린다"는
핵심 동작은 어떤 조합으로도 만들 수 없다.

## 10. 이 문서가 바꾸지 않는 것

- 판정 경로는 그대로 하나다. 서버 푸시는 엔진이 이미 저장한 마감 시각을 비교만 한다(두 번째 판정 경로가 아니다).
- 위치 권한 요청은 여전히 0건이다.
- 보호자 사본은 여전히 받은 시점 그대로이고 자동 갱신되지 않는다(서버는 마감 시각과 확인 여부만 전달한다).

## 11. 확인 필요 목록

1. Vercel Cron 요금제별 한도(Hobby 하루 1회·시각 흔들림, Pro 매분)와 2025년 이후 변경 여부, `CRON_SECRET` 헤더 동작.
2. Upstash Redis 서울 리전 유무, 무료 등급 한도, Vercel Marketplace 연동 시 환경변수 이름.
3. QStash 지연 정밀도, 서명 헤더 형식, 중복 제거 id 지원, 무료 한도, 메시지 저장 리전.
4. Neon HTTP 질의를 패키지 없이 쓸 수 있는지(Postgres를 고를 경우만).
5. Vercel Blob 비공개 접근 지원과 크기 한도(단계 B).
6. 웹 푸시 서비스 호스트 전체 목록(허용 목록), `Topic` 헤더 제한, 무료 여부.
7. 아이폰 홈 화면 웹 앱과 Safari의 저장소·쿠키 분리 여부, 보여 주지 않는 푸시에 대한 구독 해지 정책.
8. Notification Triggers(예약 알림) API가 어느 브라우저에서도 쓰이지 않는다는 점.
9. 개인정보 처리방침의 처리 위탁·국외 이전 고지, 동의 문구(법무).
