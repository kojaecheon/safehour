# 풀리지 않은 문제

그 자리에서 고칠 수 있었던 것은 여기 없다. 지금 당장 풀 수 없는 것만 적는다.

## 1. 의존성 권고 3건이 남아 있다

**무엇이**: `npm run audit`가 실패한다(치명 1건, 높음 1건으로 집계).

- 프레임워크: Windows에서 호스팅한 서버의 원격 코드 실행(`GHSA-p293-qw3h-jr36`)
- 프레임워크: 이미지 최적화 경로에서 AVIF 파일을 쓸 때의 원격 코드 실행(`GHSA-2xp9-vwfh-vxw4`)
- 이미지 처리 라이브러리: libheif 관련 취약점(`GHSA-rgj7-g3m4-5g8c`)

**영향 범위**: 현재 배포는 리눅스 환경이라 첫 번째 권고의 조건에 해당하지 않는다. 두 번째·세 번째는
프레임워크의 이미지 최적화 경로에 걸려 있는데, 이 앱은 장소 사진을 **참조만** 하고 서버에서 가공하지
않는다(이미지 최적화 컴포넌트를 쓰지 않는다). 그래서 현재 코드 경로로는 도달하지 않는다고 본다.
다만 프레임워크가 그 경로를 기본으로 열어두므로 "도달 불가"라고 단정하지는 않는다.

**왜 지금 못 푸나**: 해결하려면 의존성 버전을 올려야 하는데, 잠금 파일을 바꾸지 않는 것이 현재 작업의
전제다(공모전 심사가 현재 배포본으로 진행 중이라 동작이 바뀌면 안 된다). 잠금 파일과 `package.json`은
이 작업 이전 상태와 바이트 단위로 같다 — 이번 작업이 만든 문제가 아니다.

**가능한 접근**: 심사와 시상이 끝난 뒤 프레임워크와 이미지 라이브러리를 올리고, 올린 뒤 전체 검증과
화면 테스트를 다시 돌린다. 버전 상승 폭이 크면 변경점을 먼저 확인한다.

## 2. 보호자 링크가 긴 체류에서 메신저로 보내기 어려워진다

**무엇이**: 링크 길이가 체류 길이에 비례해 늘어난다. 측정값은 7박 최악 일정 7,216자, 14박 12,249자,
45박 33,966자다. 메신저로 보내기 좋은 기준으로 잡은 8KB를 7박까지만 만족한다.

**영향 범위**: 2주 이상 머무르는 사용자가 보호자 링크를 메신저로 보낼 때 잘리거나 거부될 수 있다.
잘린 링크는 복호화에 실패하므로 보호자가 일정을 볼 수 없다. 데이터가 새지는 않는다.

**왜 지금 못 푸나**: 줄일 수 있는 것은 이미 줄였다 — 허용 목록으로 필드를 최소화하고, 오늘 이후
날짜만 담고, 표준 압축을 적용했다. 더 줄이려면 보호자가 보는 정보를 빼야 하는데 그건 제품 결정이고,
아니면 서버에 스냅샷을 두어야 하는데 그건 '서버에 저장하지 않는다'는 설계와 정면으로 충돌한다.
둘 다 운영자 판단이 필요하다.

**가능한 접근**: 링크를 날짜 구간별로 나눠 여러 개 보내기, 또는 보호자 화면이 '오늘~3일'만 담는
짧은 링크를 기본으로 제공하기. 어느 쪽도 사용자가 보는 것이 줄어드는 거래다.

## 3. 오늘 시각에 따라 건너뛰는 화면 테스트가 있다

**무엇이**: 오늘 남은 정거장이 있어야 성립하는 시나리오(휴무 사건으로 자동 대체가 일어나는지 보는
검증)가 늦은 시각에 실행하면 건너뛴다. 낮에 돌리면 건너뛰지 않으므로 실행 결과만으로는 드러나지 않는다.

**영향 범위**: 저녁 이후에 검증을 돌리면 그 경로가 실제로는 검증되지 않은 채 "전부 통과"로 보인다.
자동 대체는 변화 대응의 핵심 경로라 검증 공백이 그대로 남는다.

**왜 지금 못 푸나**: 시각을 고정하려면 화면 테스트가 쓰는 현재 시각을 통째로 가짜로 바꿔야 한다.
판정에 쓰는 시각은 라우트 계층이 서버 시계에서 채워 넣지만, 브라우저 쪽 날짜 전환·매일 확인·알림 예약이 모두 실제 시계를
본다. 한 곳만 바꾸면 다른 곳과 어긋나 더 잘못된 통과를 만든다. 시계 주입 지점을 정리하는 것은
별도 작업 크기다.

**가능한 접근**: 클라이언트 시계를 한 곳에서만 읽도록 모으고, 화면 테스트에서 그 한 곳을 고정한다.
정리 전까지는 이 경로를 바꿨을 때 낮 시간대에 한 번 더 돌려 확인한다.

## 4. 예전 판정 경로가 아직 코드에 남아 있다

**무엇이**: 단일 외출 흐름 시절의 판정 모듈(`src/engine/recommend.js`)과 그것이 쓰는 함수들
(`src/engine/safetyGate.js`의 병원 조건 최신성 게이트·후보 순위 매기기·사건 적용)이 그대로 있다.
화면과 API 경로는 모두 퇴역했고 운영 코드에서는 아무도 부르지 않는다. 남아 있는 호출자는
심사 증빙을 만드는 스크립트(`scripts/run-live-safehour-scenario.mjs` →
`docs/LIVE_SCENARIO_EVIDENCE.md`)와 그 시나리오 테스트(`test/scenarios.test.js`)뿐이다.

**영향 범위**: 이 모듈은 자체 엔진 버전, 자체 상태 결정, 자체 최소 외출 창 상수를 들고 있고,
조정 가능한 기본값 파일을 읽지 않는다. 이번에 추가된 열·물·식이·날짜 기준 휴무 게이트도 거치지
않는다. **같은 질문에 다르게 답하는 두 번째 판정 경로**이고, 판정 경로가 두 벌이 되는 것은 이
제품에서 가장 위험한 결함으로 정해 둔 것이다. 지금은 운영 경로에서 닿지 않으므로 사용자에게
잘못된 답이 가지는 않는다. 위험은 앞으로 누군가 이 모듈을 "살아 있는 코드"로 보고 손대거나
다시 연결하는 것이다. 그때 판정이 갈라진다.

**왜 지금 못 푸나**: 운영자가 공모전 최종 심사·시상(2026-11-05)이 끝난 뒤에 정리하기로 정했다.
지금 지우면 심사 증빙 문서를 만든 근거가 끊긴다.

**가능한 접근**: 심사가 끝나면 여섯 개 시나리오를 현재 일정 엔진 위로 옮기고, 이 모듈과
같이 쓰이던 퇴역 함수들을 함께 지운다. 그때까지는 운영 코드가 이 모듈을 불러오지 않는다는 것을
테스트로 묶어 둔다.

## 5. 코드 주석이 사라질 문서를 가리킨다

**무엇이**: 약 70개 소스 파일의 머리 주석이 작업용 임시 문서의 장 번호를 가리킨다(예: "명세 4장",
"인계 4장"). 그 문서들은 저장소에 없다 — 주석만 남고 가리키는 곳이 없다.

**영향 범위**: 코드는 정상 동작한다. 다만 규칙의 근거를 찾으려는 사람이 없는 문서를 찾게 되고,
"왜 이렇게 했는가"가 주석에서 끊긴다. 안전 판정 규칙이 몰려 있는 파일일수록 손해가 크다.

**왜 지금 못 푸나**: 70개 파일을 한꺼번에 고치면 이번 작업의 변경 범위가 크게 흔들린다. 검토가
끝난 직후에 전 파일을 건드리는 것은 위험 대비 이득이 없다. 어디를 가리키게 바꿀지도 파일마다
다르다 — 도메인 규칙, 보안 정책, 계약 중 어느 쪽인지 파일별로 판단해야 한다.

**가능한 접근**: 파일을 건드릴 일이 생길 때마다 그 파일의 주석만 지금 있는 문서를 가리키도록
고친다. 한 번에 다 바꾸지 않는다.
