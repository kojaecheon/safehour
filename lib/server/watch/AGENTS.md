# 서버 알림 (`lib/server/watch/`)

ADR-0012(`docs/decisions/0012-server-minimal-storage-guardian-push.md`)의 서버 쪽이다. 환자가 복귀 마감을 확인하지 않으면
마감 + 10분에 보호자 기기로 웹 푸시를 한 번 보낸다. 스위치(`SAFEHOUR_SERVER_PUSH`)가 꺼져 있는 동안에는 아무것도 저장하지 않는다.

## 맡는 것

- 환경변수 읽기와 준비 상태(`config.js`), WatchCtx 조립(`context.js`)
- 저장소 어댑터(`kv.js`), 키 유도와 형식 정규식(`keys.js`), 구독 봉인(`seal.js`), 횟수 제한(`limits.js`)
- 네 레코드 읽기·쓰기(`records.js`)
- 예약 어댑터와 서명 검증(`scheduler.js`), 예약 걸기(`arm.js`), 예약 처리 판정표(`due.js`)
- 바깥 호출 시간 한도(`timeout.js`). `AbortSignal.timeout`을 쓰지 않는다(`docs/engineering-notes.md`의 Node 22 항목)
- 서버 푸시 문구(`text.js`)와 보호자에게 보내기(`notify.js`)
- 환자 쪽 동작(`patient.js`), 보호자 쪽 동작(`guardian.js`)
- 요청 본문 읽기와 허용 목록(`requests.js`), 기록 한 줄(`log.js`), 라우트 처리기(`handlers.js`)

## 맡지 않는 것

- 판정. 여기서 보는 것은 '확인이 있었는가'뿐이다. 복귀 마감 계산, 조건, 일정은 `src/engine/`, `src/stay/`가 맡는다.
- 화면. 환자 화면과 보호자 화면, 서비스 워커는 `app/`, `components/`, `public/`이 맡는다.
- 위치. 서버는 위치를 모르고 받지도 않는다. 날짜와 `HH:MM` 마감 시각만 다룬다.
- 웹 푸시 프로토콜(VAPID, 본문 암호화, endpoint 검증): `src/push/`
- 기기 안 알림 예약: `lib/notify/`

## 항상 지켜야 하는 것

- **저장하는 것은 ADR-0012의 네 레코드(지켜보기, 알림 주소(구독), 날짜 기록, 횟수 제한 계수기)와 그 레코드를 찾는 색인 둘뿐이다.**
  색인은 소유 집합(계정 표시 해시 → 지켜보기 키, 결정 17)과 날짜 색인(날짜 → 지켜보기 키, 하루 1회 예약용)이다.
  필드를 더하지 않는다. 더해야 할 것 같으면 멈추고 운영자에게 보고한다.
- **Redis 명령 배치를 아는 곳은 `records.js`뿐이다.** 서비스 함수는 `records.js`의 함수만 부른다(횟수 제한 계수기는 `limits.js`).
- **마감 올리기는 지켜보기 하나에 한 번에 하나씩, 늘 가장 최근 상태 전체를 보낸다.** `replaceDays`는 읽기와 쓰기가 exec 두 번이라
  원자적이지 않다. 같은 지켜보기의 업로드 둘이 겹치면 확인 표시를 잃거나 날짜 하나가 통째로 빠질 수 있다. 클라이언트는 앞 업로드의
  응답을 받은 뒤 다음을 보내고, 바뀐 날짜만 보내지 않는다.
- **`armFailed`가 0보다 크면 클라이언트가 잠시 뒤 같은 전체를 다시 올린다.** 예약 업체 실패로 걸지 못한 마감 수다. 응답 상태는 200 그대로다.
  다시 올려도 이미 건 마감은 다시 걸지 않는다(`a:` 표시). 다시 올리지 못해도 하루 1회 예약(`/api/cron/watch-arm`)이 어제·오늘·내일을 다시 건다.
- **보냄 표시(`p:<HH:MM>`)는 두 단계다.** 보낼 권리를 얻을 때(`HSETNX`) `'1'`(보내는 중), 푸시 서비스가 받으면 `'s'`(보냄)로 바꾼다.
  보내지 못한 결과(구독 없음, 한도, 구독 만료, 거절, 다시 시도)는 모두 표시를 지운다. `readDay`의 `pushed`는 `'s'`인 시각만,
  보내는 중인 시각은 `claimed`에 따로 담는다. '돌아왔어요'는 `'s'`일 때만 복귀 확인 알림을 보낸다. 보낸 뒤의 저장소 실패는 던지지 않고
  `SENT`로 끝낸다(알림은 이미 나갔다).
- **마감 올리기와 '돌아왔어요'는 쓰기 토큰을 먼저 확인하고 센다.** 토큰이 맞으면 `deadlines`·`back`, 틀리거나 모르는 id면
  `deadlinesBad`·`backBad`를 센다. 실패 한도를 미리 엿보고 막지 않는다(그러면 틀린 토큰으로 환자를 다시 막을 수 있다).
- **예약 발행은 지켜보기당 하루 120건(`arm`)이고, 예약 업체가 받은 것만 센다.** `armDay`가 발행 전에 `peekRate`로 엿보고, 받았을 때만
  걸림 표시를 쓰기 전에 `countRate`로 센다. 한도에 닿으면 남은 마감은 실패로 세고 멈춘다. 실패한 발행은 `armFail`(하루 40건)에 따로
  센다. 넘으면 그 호출에서 그 지켜보기의 남은 마감을 시도하지 않지만, 다음 호출의 성공은 막지 않는다. 실패를 `arm`에 세면 예약 업체
  장애 동안의 다시 올리기가 그날의 한도를 써 버려, 업체가 돌아와도 하루 이틀 알림이 나가지 않는다(최종 검토 I1).
  오늘 함께 있음이 켜진 날은 걸지 않는다(끄면 다시 건다).
- **예약 표시(`a:`)를 지우는 판정은 지우기와 이유 다시 읽기를 한 배치에서 한다**(`clearArmedAndReadDay`,
  `clearArmedAndReadSubExists`). 이유가 사라졌으면 `retry: true`로 다시 부르게 한다. 구독(`writeSub` 뒤 `armPending`),
  함께 있음 끄기(`m` 지운 뒤 `armPending`), 마감 올리기(`replaceDays` 뒤 `armPending`)는 **먼저 쓰고 나중에 다시 건다.** 이 순서를
  바꾸면 둘 다 상대를 못 보고 마감 하나가 조용히 사라진다.
- **기록·예외 메시지·오류 응답에 넣지 않는 것**: `watchId`, 저장 키(`watchKey`), `ownerHash`, `subId`, `writeToken`, 계정 키,
  endpoint 주소와 호스트, 날짜, 시각, 언어, 푸시 서비스 응답 원문, 저장소 주소와 토큰, 예약 메시지 id, IP, User-Agent.
  성공 응답은 계약 표의 키만 담는다(`subId`, 상태 조회의 `date`·`confirmed`, 등록의 `expiresOn`은 계약에 있는 값이다).
  기록은 `log.js`의 `buildWatchLogEntry`가 만든 필드만 나간다. 받은 객체를 펼쳐 쓰지 않는다. 잡은 예외의 메시지와 속성은 읽지 않는다.
- **찾지 못한 경우는 모두 같은 404다.** 모르는 id, 만료, 틀린 토큰, 남의 id, 틀린 `subId`가 바이트까지 같은 응답을 받는다.
  어느 경우인지 알리면 `watchId` 추측의 단서가 된다.
- **시험 장치가 꺼진 곳(운영 배포, 데모 로그인 꺼짐)에서는 데모 세션을 세션이 없는 것으로 본다.** 데모 로그인은 누가 눌러도 같은
  신원(`demo-user`)이라 계정 키가 하나다. 받으면 소유 확인이 무의미해진다(남의 지켜보기 다시 등록, `{ all: true }`로 남의 것 지우기,
  계정 한도 공유). 등록과 전체 삭제는 401, 마감 올리기는 계정 없이 쓰기 토큰만, 보호자 경로는 로그인을 요구하는 설정이면 401이다.
  판단은 `handlers.js`의 `sessionOf` 한 곳에서 `cfg.testHooks`로만 한다. 그래서 운영 스위치를 켜기 전에 실제 소셜 로그인(구글·카카오)을
  운영에 설정해야 환자가 등록할 수 있다.
- **횟수 제한만으로는 저장소 명령 총량을 막지 못한다.** 한도는 계정·지켜보기 단위라 형식에 맞는 id를 바꿔 가며 보내면 새로 센다.
  삭제 경로 둘에는 한도가 없고 차단 스위치가 켜져도 열려 있다. 운영 스위치를 켜기 전에 Vercel Firewall의 횟수 제한 규칙을
  `/api/watch*`와 `/api/push/*`에 건다(`docs/operations.md` '서버 알림 켜기'). 저장소 할당량이 바닥나면 예약 처리까지 503이 된다.
- **삭제 경로는 스위치와 무관하다.** `DELETE /api/watch`와 `DELETE /api/watch/subscribe`는 스위치가 꺼져 있거나 차단 스위치가
  켜져 있어도 동작한다. 저장소 설정이 없을 때만 503 `SAFEHOUR_SERVER_PUSH_OFF`다. 쓰기 경로는 `enabled`가 아니면 503이다.
- **스위치 판단의 정본은 `watchConfig`다.** 처리기는 ctx의 `enabled`를 `cfg.enabled`로 덮어쓴 사본을 서비스에 넘긴다.
  메모리 저장소, 시험용 푸시 출처, `http` 되부를 주소, 데모 세션 허용은 `watchConfig`의 `testHooks`(데모 로그인이면서 운영 배포가
  아님)로만 켜진다. 다른 길을 더하지 않는다.
- **시계는 주입한다.** 서비스 함수 안에서 `Date.now()`를 부르지 않고 `ctx.now()`만 읽는다. 날짜·시각 계산은 `src/stay/time.js`의
  도우미로만 한다. 오프셋 없는 문자열을 `new Date()`로 읽지 않는다.
- **토큰과 식별 값의 원문을 저장하지 않는다.** `writeToken`은 SHA-256 해시, `watchId`·계정 키는 `SAFEHOUR_WATCH_OWNER_SECRET`으로 만든
  HMAC만 둔다. 구독은 봉인해 둔다. 식별 값은 요청 본문으로만 받고 경로·쿼리에 싣지 않는다.
- 예약 처리 경로는 QStash 서명(원문 본문으로 검증) 또는 `Authorization: Bearer <CRON_SECRET>`으로만 연다. 다시 불러야 하는 결과
  (`retry`가 참인 것. `RETRY`와 일찍 온 예약 `SKIP_EARLY`이고, 처리기는 outcome을 가리지 않는다)와 저장소 장애는 503이라
  예약 업체가 다시 부른다.
- **본문은 스트림을 바이트 단위로 세며 읽고 16KB를 넘는 순간 멈춘다**(`requests.js`의 `readJsonBody`). `request.text()`·`json()`으로
  읽지 않는다. 예약 처리 경로는 서명 검증 때문에 인증 전에 본문을 읽으므로, 끝까지 읽으면 인증 없는 큰 본문이 메모리를 쓴다.
  `raw`는 받은 바이트를 그대로 푼 문자열이다(잘못된 UTF-8은 400, BOM도 떼지 않는다).
- 서버 코드는 i18n을 직접 가져오지 않는다. 예외는 문구 모듈 `text.js` 하나다(`test/i18n-languages.test.js`의 허용 목록).
  `context.js`는 검수 스위치(`reviewed`)를 넣지 않는다.
- '안전합니다'라고 쓰지 않는다. 마감 지남 문구는 '확인이 없다'는 사실만 쓴다.

## 구현 방식

- 라우트 파일은 `createWatchHandlers()`에서 처리기를 꺼내기만 한다. 처리 순서: 스위치(또는 삭제 경로면 저장소) → 세션(데모 규칙) →
  본문(16KB, 허용 목록) → 서비스 함수 → `reason`을 상태로 → 예상 못 한 예외는 503 `SAFEHOUR_SERVER_PUSH_UNAVAILABLE` → 기록 한 줄.
- 예약 처리 경로만 순서가 다르다: 본문 읽기(서명 검증용) → 인증(401) → 본문이 JSON 객체인가(400) → 저장소 설정이 없으면 200 →
  필드 형식(400) → 판정. 인증을 저장소 설정과 본문 형식보다 먼저 본다.
- 보호자 경로(구독, 상태, 함께 있음)는 `SAFEHOUR_WATCH_GUARDIAN_NO_LOGIN`이 `'1'`이 아니면 세션을 요구한다. 해지는 세션을 요구하지 않는다.
  `'1'`이면 처리기가 ctx 에 `guardianOpen: true`를 넣고, `guardian.js`는 더 엄격한 `subscribeOpen`(하루 3)·`statusOpen`(시간당 30)·
  `muteOpen`(시간당 10)에 센다(ADR-0012 결정 22). 값이 없거나 참이 아니면 기본 항목이다.
- VAPID 서명기는 같은 키 묶음이면 인스턴스 안에서 하나를 다시 쓴다(`context.js`). 출처별 JWT 재사용이 요청마다 사라지지 않게 하려는 것이다.
- 하루 1회 예약은 15:10 UTC(00:10 KST)에 운영 배포에서만 돈다(`vercel.json`). 미리보기에서는 `/api/cron/watch-arm`과
  `/api/watch/due`를 Bearer로 직접 부른다. 예약 업체를 부르는 다섯 라우트(마감 올리기, 구독, 함께 있음, 예약 처리, 하루 1회 예약)는
  `maxDuration = 60`이다. 하루 1회 예약은 마감을 하나씩 걸고(동시에 여러 개를 발행하지 않는다), Vercel은 시간 초과한 예약 실행을
  다시 부르지 않는다. 그래서 `armIndexedDates`는 시작에서 `CRON_BUDGET_MS`(45초)가 지나면 멈추고 `partial: true`를 돌려준다.
  남은 마감은 다음 업로드나 다음 날의 하루 1회 예약이 건다.

## 테스트

- 단위 테스트는 외부 호출이 0건이다. 저장소는 메모리 구현, 예약과 푸시는 `test/watch-fixtures.js`의 기록기, 그 밖은 가짜 `fetch`를 쓴다.
- 경로마다 스위치 꺼짐, 세션 없음, 본문 형식, 404 동일성, 횟수 제한, 저장소 장애(503, 응답·기록에 내부 값 없음)를 확인한다
  (`test/watch-routes.test.js`).
- 기록 줄 전체에서 `watchId`·토큰·`subId`·endpoint·날짜·시각·계정 키를 찾아 하나도 없는지 단언한다.
- 처리기가 기록 줄 말고 아무것도 내지 않는지(stdout·stderr·`console.*` 전체)는 별도 프로세스(`test/watch-routes-child.js`)로 본다.
  테스트 실행기가 같은 프로세스의 stdout에 자기 보고를 쓰므로, 같은 프로세스에서 stdout을 가로채면 실행기 출력과 섞인다.
- 스위치가 꺼졌을 때의 예약 처리는 보낼 시각이 된 마감으로 시험한다. 이른 시각으로 부르면 `SKIP_EARLY`로도 보내지 않으므로
  스위치를 지워도 시험이 통과한다.
- 데모 세션은 운영 설정(`VERCEL_ENV=production`)과 미리보기 설정 둘 다로 시험한다.
- 적대적 endpoint(호스트 뒤에 붙인 도메인, 경로에 넣은 호스트, `@` 뒤 호스트, IP, 다른 포트, `http:`)와 16KB를 넘는 본문,
  `__proto__` 키를 넣어 본다.
